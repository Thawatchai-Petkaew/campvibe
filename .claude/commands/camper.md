`/camper "<anything>"` — give the orchestrator a free-form request that the three fixed commands (`/new-feature`, `/status`, `/release`) don't cover: investigate, fix, refactor, analyze, plan, or a small change.

The orchestrator (`.claude/agents/orchestrator.md`):
1. reads the request + project context (`docs/project/*`, `CLAUDE.md`, relevant `.claude/rules/*`)
2. runs lightweight Discovery to scope it → proposes/acts via the normal gates G1–G5
3. **always raises gates to the human** (no autopilot — there is no autonomous gate approval) and respects the **cost rule** (any monetary cost → stop and ask)

For a brand-new feature with a clear requirement, `/new-feature` is still the front door; use `/camper` for everything in between.

**Also from Telegram:** any message to the bot that isn't a gate reply is routed here as an ad-hoc request (via `repository_dispatch` → `camper-adhoc` workflow → headless orchestrator, draft PR only).

## Ticket delivery convention — orchestrator MUST follow when creating/tracking/breaking-down work
The `/status` dashboard reads the self-hosted delivery ticket DB **live** (`lib/delivery/status-adapter.ts` → `/api/tickets` → `buildModel` in `app/status/page.tsx`). Every piece of work is a row in that ticket DB (identifiers still `CAM-###`, one global sequence). Structure every piece of work so it shows correctly:

- **Epic** = a ticket created with `--type epic` and a `featureName` (`node scripts/ticket-sync.mjs create --type epic --title "..." --feature "<feature name>"`). Shows on /status even with 0 stories, grouped by `featureName`.
- **Story** = a ticket created with `--type story --epic <CAM-id-of-the-epic>` (`epicId` FK — a real join, not a title-string match) → appears as a *task inside the epic* on the /status **Epic tab**.
- **Current role on a story** = the `currentRole` column, not a title tag. `/status` still displays it as `[<role>]` in front of the title (synthesized by `lib/delivery/status-adapter.ts`, byte-for-byte the same shape the board already renders) — the STORED title stays clean. Set/change it via `node scripts/ticket-sync.mjs handoff <CAM-id> --role <role> [--state "In Progress"] [--note "..."]`, using the LONG role slugs /status maps to icon + Design→Build→Verify→Ship stage: `architect` `ux-designer` (Design) · `frontend-engineer` `backend-engineer` (Build) · `qa-engineer` `security-reviewer` (Verify) · `devops-release` (Ship) · `product-owner` `analyst`. **UPDATE the role as the story moves** (Designer → Frontend → QA → Security → DevOps) so /status always shows who is on it.
- **Role sub-tasks** (only when a story genuinely needs a granular per-role breakdown) = tickets created with `--type task --epic <the story's own CAM-id>` (a task's "epic" field is really its parent story here — same `epicId` FK, just one level deeper). Usually the rotating role on the story is enough — don't over-scaffold.
- **persona flag** = one of `host | camper | admin | platform` (`--persona <p>` on `create`, drives persona grouping on /status). **feature** = the `--feature "<name>"` string (free text, matches the epic's `featureName`).
- **Naming (owner rule 2026-07-04)** — lane (`featureName`), epic titles and story titles are **English and self-communicating**: say the capability/outcome so the board reads without opening any document (e.g. `Host lead inbox — leads from every channel in one place (OS1)`, never `โมเดล HostLead`). Keep blueprint codes (OS1, HM3, G1…) in parens at the end. Milestone codes (M0/M1/M1.2…) NEVER appear in board names — they live only in `docs/project/platform-blueprint.md` as sequence tags. The ticket BODY stays Thai per the template (AC copy verbatim). DONE/CANCELED tickets keep their historical titles.
- **Ticket body = files-as-SoT.** The spec content lives in `docs/specs/<feature>/<epic>/<CAM-id>-<story>/story.md` — the story ticket template (`.claude/templates/story.md`, **template v2 — English framework, Thai copy verbatim**; `## Why` removed — value lives in the Story's so-that clause): `## Story (As a <persona>, I want …, so that … + Scope + Depends on) / ## AC` (6-column table `# | Given | When | Then (user sees, Thai verbatim) | System effect | Neg/edge`) `/ ## Rules / ## Edge cases (EC-n) / ## Data / ## Seams & refs / ## Out of scope / ## Self-verify` — authored/edited via PR into the repo, not by editing the ticket description. The ticket's `description` field is only a **1-line summary + a pointer to the spec file path**; `node scripts/ticket-sync.mjs audit` checks the **file** first (`story.md` at its scaffolded path) and falls back to the ticket description only for a legacy ticket that predates a story file. No event-codes/class/testid/tech-jargon/em-dash in AC.
- **Gate policy v2 (owner-approved — full detail `.claude/rules/ops.md` §Gate policy v2)**: G1 stays full human tap for M/L stories (**spec-lite class** for S stories — no schema/migration · no new API contract · single file-surface · diff ≤ ~150 lines — ships `story.md` in the same PR as the code and folds G1 into the G3 packet, one owner tap; PO decides the class at intake); G5 stays full human tap; G2 pre-authorizes a **standard class** (reuse-only UI — existing tokens/components/flows, no new screen/flow/token, `check:ds`+`check:palette` green) that skips the separate G2 tap and folds into the G3 packet as one line (`G2: standard class (criteria met)`); G3 is an **exception-first packet** (verdict · exceptions/risks · $/story · the G2 class note) the owner approves on, reading diffs only when an exception is flagged; G4 clears in **one batched daily sitting** (SLA: 1 business day), packets staying atomic per story. Anti-rubber-stamp companions are mandatory: every retro replays all gate rejections + a real failure, the owner spot-audits standard-class passes, a graduated-autonomy ledger tracks per-class approve/reject counts (a new class needs ~20 clean approvals + explicit ratification), and any miss demotes the class back to full-tap.
- **`[NEEDS CLARIFICATION: …]` marker** — when Discovery leaves an open question inside a story file rather than blocking entirely, mark it inline as `[NEEDS CLARIFICATION: <question>]` in the relevant section instead of guessing silently. (PR-3 wires `ticket-sync.mjs audit` to detect this marker and flag the ticket so it cannot silently pass as ready.)
- **Create tickets via `scripts/ticket-sync.mjs create`** (no MCP — there is no Linear MCP call in this loop anymore): `node scripts/ticket-sync.mjs create --type epic|story|task --title "..." [--epic <CAM-id>] [--role <role>] [--persona <persona>] [--feature "<name>"] [--priority <0..4>] [--description-file <path>|--description "..."]`. Pass the filled `story.md` body via `--description-file` so the ticket's `description` matches the template on creation (audit-clean from the start).
- **Tracking / gate movement**: run `node scripts/ticket-sync.mjs set <CAM-id> --state "In Progress"` when a story starts, `--state Done` after localhost-verify (dev DB) + merge into `dev`; add label `on-staging` after the batched dev→staging promote, `node scripts/ticket-sync.mjs release <CAM-id>` (stamps `releasedAt`) after G5. These legacy-vocabulary `set` calls translate onto the real guarded state machine (`BACKLOG→TODO→IN_PROGRESS→AWAITING_GATE→DONE`, see `scripts/lib/ticket-sync-mapping.mjs`) — move state at **every** gate so the /status Epic tab shows live movement. Each gate is raised to the human with `node scripts/ticket-sync.mjs set <CAM-id> --add-label awaiting-you` (maps to the `raiseGate` verb → state `AWAITING_GATE`); the human clears it — approve via the Telegram tap, the `/status` UI Approve button, or `/status/map` Approve (all converge on the `approve` verb, which flips the ticket back to `IN_PROGRESS`). **`approve` and `complete` are not interchangeable** — `approve` clears an INTERMEDIATE gate and returns the story to work; the TERMINAL gate is `--state Done` (the `complete` verb). An owner saying "approve everything" over a finished batch means complete; using `approve` there re-opens all of them and forces a re-raise + re-complete on each (nine stories, 2026-07-28). Reject via Telegram "Send Back" or `/status/map` Reject (the `reject` verb — same state, `changesRequested=true`, `regressionRound` bumped, rework by the same role). Ongoing progress shows on the **Epic tab**.
- **Role handoff (MUST use `ticket-sync handoff`)**: when a story moves between roles, the orchestrator MUST run `node scripts/ticket-sync.mjs handoff <CAM-id> --role <role> [--state "In Progress"] [--note "..."]`. This command: (1) sets `currentRole` so /status's synthesized `[role]` tag always reflects the current actor, (2) pushes onto `roleHistory` — an append-only column that **accumulates, never removed**, so workload attribution builds a complete history, (3) fires a Telegram notification to the owner (same call, in-process — no separate step). Do NOT hand-edit the title to fake a role tag — that skips the `roleHistory` write and the Telegram notification, and `ticket-sync audit` flags a `currentRole`/`roleHistory` mismatch as a data-integrity gap.
- **Telegram notify policy** — single source: `lib/delivery/tickets.ts`, the one service module every mutation goes through, calls `buildEventMessage()` (`lib/notify-messages.ts`) and sends the Telegram message **in the same request that mutates the ticket** — there is no webhook to relay from (ADR-010 "single mutation path, no webhook"; the old `app/api/linear-webhook/route.ts` is retired). Copy is English, no emoji. Event matrix is unchanged (from `lib/notify-messages.ts` `NOTIFY_EVENTS`):
  - `started` on — state enters `IN_PROGRESS` for the first time
  - `handoff` on — `currentRole` changes (via `start`/`approve`/`handoff`)
  - `gate` on — `raiseGate` fires (state → `AWAITING_GATE`)
  - `approved` on — `approve` fires (a gate clears, not the terminal one)
  - `rejected` on — the Telegram Approve/Reject button (or `/status/map` Reject) fires `reject`
  - `blocked` on — `setBlocked(true)` fires
  - `done` on — `complete` fires (the terminal gate, state → `DONE`)
  - `released` on — `release` fires (`releasedAt` stamped)
  - `created` off — ticket-create event (default off, no spam)
  - `defect` off — default off
  Use `node scripts/ticket-sync.mjs notify "<text>"` to push free-form messages to Telegram (e.g. CI results). Requires `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` in `.env`.
- **Comms**: prefix every message to the owner with the active role + `(The Camper)` — e.g. `Orchestrator (The Camper)`, `Designer (The Camper)`. No emoji. Actually dispatch to role agents (`subagent_type` designer/frontend/qa/security/devops) — never run the whole epic solo.
- **Parallel agents (owner rule 2026-07-03, amended 2026-07-05)**: multiple agents MAY run concurrently, provided they cannot overwrite each other — (1) **at most TWO code-writing agents at once**, each with `isolation: "worktree"` on its own branch off `dev` (the MAIN working tree hosts none — it is the owner's dev server on `dev`); read-only/review/spec agents unlimited; a handoff note claiming "dispatched" must have an Agent call returning an agentId in the same turn (anti-phantom); (2) the orchestrator PARTITIONS file surfaces before dispatch — no two concurrent agents may edit the same story or overlapping files (list each agent's allowed files in its prompt); (3) read-only agents (Explore/Plan/read-only review) may run in parallel anywhere, unlimited; (4) worktree caveats: fresh worktrees have no node_modules — run `bash scripts/worktree-setup.sh` (CAM-579), NOT a bare `ln -s <main tree>/node_modules node_modules`. A single whole-tree symlink puts every worktree's generated Prisma client (`node_modules/.prisma/client`) on the SAME physical folder — a concurrent `prisma generate` in one worktree silently overwrites the client every other worktree reads, so the victim sees a confusing 500 / a wall of typecheck errors in code it never touched (reproduced in `docs/specs/platform-hardening/taxonomy-ui-foundation/CAM-579-worktree-isolation/story.md`). `worktree-setup.sh` symlinks everything ELSE (cheap, same speed as before) but gives each worktree its own real `.prisma` + `@prisma/client`, generated fresh from THAT worktree's own schema — a few seconds, nowhere near a full `npm ci`. `npm run dev`/`typecheck`/`test` also auto-run a fast pre-hook (`scripts/verify-prisma-client-fresh.mjs`) that fails loud and immediately if a client ever goes stale relative to its own worktree's schema, instead of a confusing downstream error. Turbopack `next build` still FAILS on cross-filesystem symlinks regardless (skip local build, note "build verified by CI" in the PR); (5) merges stay SEQUENTIAL under strict protection — one PR at a time, `gh pr update-branch` + CI re-run between merges.
- **Linear MCP (`.mcp.json`) is archive-read-only** — the old 275 legacy issues are kept there for history/reference only. Never call `save_issue`/`save_project`/`create_issue` through it for delivery work; all creates/reads/writes go through `scripts/ticket-sync.mjs` above. `.mcp.json` itself is left as-is by this convention change (untouched wiring, just no longer the write path).
- **Token/$ discipline** — dispatch envelopes (pointers + `done_when`, ≤ ~300 tokens), JSON-only agent returns (~400 tokens, detail→file), the inline-vs-spawn routing ladder, and checkpoint/resume live in `.claude/rules/efficiency.md`. The inline lane covers non-deliverables only — it never bypasses the story role rotation (`ticket-sync handoff` per stage; `complete()` blocks Done without a Verify-stage role in `roleHistory`).
