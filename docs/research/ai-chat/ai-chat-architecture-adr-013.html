CampVibe · ADR-013 · เอกสารประกอบการคุย ก่อนตัดสินใจ

โครงสร้างระบบแชท AI — จำได้ · รู้จักผู้ใช้ · ทำงานได้จริง

สรุปสถาปัตยกรรมที่เสนอสำหรับยกระดับน้องกองไฟตามความต้องการ 3 ข้อ: มีประวัติการคุยถาวร, personalized ตามผู้ใช้ที่ล็อกอิน, และคิดงานหลายขั้นได้ในคำถามเดียว — ทุกการตัดสินใจในหน้านี้ยังแก้ได้ (ยังไม่มีอะไร merge)

สถานะ: PROPOSED — รอคุยกับเจ้าของ ต่อยอด ADR-009 ไม่รื้อของเดิม กล่องสีน้ำเงิน = ของใหม่ กล่องสีเขียว = หน่วยความจำใหม่

ภาพที่ 2

หนึ่งคำถามเกิดอะไรขึ้นบ้าง — ตัวอย่างผู้ใช้ที่ล็อกอิน

"ทริปหน้าของผมคือเมื่อไหร่นะ แล้วแถวนั้นมีลานติดน้ำเพิ่มอีกไหม"

ประตูเข้าrate limit → ตรวจ payload → อ่าน session (รู้ว่าเป็นใคร)
หน่วยความจำโหลด 10 ข้อความล่าสุดของบทสนทนานี้จาก DB (client ไม่ต้องส่งประวัติมาเองอีกแล้ว)
สมอง รอบ 1เห็นคำว่า "ทริปหน้าของผม" → เรียก getMyBookings (userId มาจาก session ไม่ใช่จากโมเดล) → ได้: ดอยม่อนแคมป์ 25–27 ก.ค.
สมอง รอบ 2รู้จังหวัดแล้ว → เรียก searchCampsites (terrain = แม่น้ำลำธาร, จังหวัดเดียวกัน) → ได้การ์ด 6 ใบ
สมอง รอบ 3ข้อมูลครบ → เขียนคำตอบภาษาไทย + เลือกชิปคำถามต่อ (ไม่เรียกเครื่องมือแล้ว = จบ loop)
หน่วยความจำบันทึกคำถาม+คำตอบ+การ์ดที่แสดง ใน transaction เดียว — turn ล้มเหลว = ไม่เขียนอะไรเลย
ผู้ใช้เห็นคำตอบ + การ์ด — ปิดแอปแล้วกลับมาพรุ่งนี้ เปิดแชทเจอบทสนทนานี้ต่อได้เลย

สิ่งที่จงใจ "ไม่เก็บ"

  • ร่องรอยการเรียกเครื่องมือ — ผลการจอง/โปรไฟล์ไม่ถูกก๊อปไปนอนอยู่นอกที่ของมัน
  • error ดิบจากโมเดล, system prompt — turn ที่ล้มเหลวไม่เขียนอะไรลง DB แม้แต่แถวเดียว
  • ข้อมูลของผู้ใช้คนอื่น — เป็นไปไม่ได้เชิงโครงสร้าง เพราะเครื่องมือส่วนตัวรับ userId จาก session เท่านั้น
ตาราง

เครื่องมือ 3 ชั้น — หัวใจความปลอดภัยของ "agency"

ชั้นใครใช้ได้เครื่องมือเกราะ
guestทุกคน ค้นแคมป์ · เช็ควันว่าง อ่านเฉพาะแคมป์ที่เผยแพร่ · จำกัด 10 ใบ · ตรวจ schema ก่อนรันเสมอ
authedผู้ล็อกอิน การจองของฉัน · รายละเอียดการจอง · โปรไฟล์ (เบอร์ mask 081-•••-••XX) · wishlist userId ผูกจาก session ฝั่ง server — ไม่มีช่อง userId ใน schema ที่โมเดลเห็นเลย (มี test ยืนยันถาวร) → โมเดลขอข้อมูลคนอื่นไม่ได้แม้ถูกหลอกด้วย prompt injection
write อนาคตผู้ล็อกอิน + กดยืนยัน เช่น ยกเลิกการจอง (เฟสหลัง) AI ได้แค่ "เสนอ" เป็นการ์ดยืนยัน — การกระทำจริงเกิดเมื่อมนุษย์กดปุ่มผ่านเส้นทางปกติที่ตรวจสิทธิ์เต็ม (แนว OWASP: AI เสนอ มนุษย์อนุมัติ)
จุดที่อยากให้ช่วยตัดสิน

5 การตัดสินใจที่เปิดคุย — มี default ให้แล้ว เปลี่ยนได้ทุกข้อ

1

guest ไม่เก็บประวัติ

เสนอ
เก็บเฉพาะผู้ล็อกอิน — guest เหมือนวันนี้ (ปิดแล้วหาย)
เพราะ
PDPA เก็บน้อยที่สุด + กัน spam เขียน DB จาก endpoint สาธารณะ + guest ไม่มีอะไรให้ personalize
ทางเลือก
เก็บ guest ด้วย cookie นิรนาม แล้ว merge ตอน login — ทำทีหลังได้ (เผื่อ seam ไว้แล้ว)
2

ลบจริง + เก็บ 180 วัน

เสนอ
บทสนทนาที่เงียบเกิน 180 วันถูกลบถาวรอัตโนมัติ · ผู้ใช้กดลบเองได้ทุกเมื่อ
เพราะ
แชทเป็นข้อมูลส่วนบุคคล — การลบจริงคือท่าที่ปลอดภัยสุดตาม PDPA (จงใจต่างจากธรรมเนียม soft-delete ของระบบ)
ทางเลือก
ขยาย/ลดอายุ หรือเก็บถาวรจนกว่าผู้ใช้ลบเอง
3

เพดานเก็บ 200 / 20

เสนอ
200 ข้อความต่อบทสนทนา · 20 บทสนทนาต่อคน (เกิน = ลบอันเก่าสุดอัตโนมัติ)
เพราะ
คุมขนาด DB บน free tier + เกินพอสำหรับการใช้จริง
ทางเลือก
ปรับตัวเลขได้อิสระ (เป็นค่าคงที่ ไม่ใช่โครงสร้าง)
4

ค่าใช้จ่ายต่อคำถาม ~2 เท่า

เสนอ
loop 4 รอบ = แย่สุด ~2 เท่าของวันนี้ต่อคำถามซับซ้อน (ยังหลักสตางค์–สิบสตางค์ต่อคำถาม)
เพราะ
นี่คือราคาของ "ความฉลาด" ที่ขอ — มีเพดาน token/เครื่องมือ/เวลาครบทุกชั้น
ทางเลือก
ลด cap เหลือ 3 หรือคุมด้วยเพดานเครดิตที่ตัว key OpenRouter (แนะนำตั้งคู่กันอยู่แล้ว)
5

ภาษาการ์ดแบบ "blocks"

เสนอ
เพิ่มช่อง blocks[] ระบุ type — client เจอ type ที่ไม่รู้จัก = ข้าม ไม่พัง
เพราะ
ฟองล้ำทุกแบบใน journeys (ตารางเทียบ · แผนทริป · ปุ่ม CTA) เพิ่มได้เรื่อย ๆ โดยไม่รื้ออะไรเลย
ทางเลือก
รื้อ contract ใหม่ทั้งชุดตอนนี้ — ไม่แนะนำ (UI 3 ชิ้นที่เพิ่ง ship ใช้ contract เดิมอยู่)
