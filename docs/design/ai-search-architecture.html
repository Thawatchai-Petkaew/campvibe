CampVibe · AI Camping Assistant แชทตอบทุกเรื่องแคมป์จากข้อมูลในแพลตฟอร์ม → การ์ดในแชท → จองต่อ · Use-case → Feature List → Architecture

หลักการ augment ก่อน disrupt — แชทเป็นชั้นสนทนาที่เสริม search/booking เดิม, ทำสิ่งที่ search เดิมทำไม่ได้ (ภาษาคน/compound/ถามต่อ/วางแผน), ไม่รื้อของเดิม

? คำถาม Architect: ต้อง merge/ปรับสถาปัตยกรรมข้อมูลไหม

ไม่ต้อง merge / ไม่ denormalize / ไม่ warehouse. ตาราง normalized คือ source of truth ที่ถูก (booking/availability = transactional). สิ่งที่ขาดคือ "ชั้น query/tool" ที่ประกอบตารางตอนถาม — AI ไม่ query DB ตรง แต่เรียก typed tools ที่ JOIN ตารางเดิมให้ตามคำถาม.
📚 Normalized tables
CampSite · Booking · BlockedDate · Review · Location → Tool layer (JOIN ตอนถาม)
buildCampSiteWhere · availability · campCardSelect → AI agent (tool-use) → 💬 Chat + 🧩 Cards
  • "วันนี้ลานนี้ว่างไหม" = query สดเสมอ (Booking+BlockedDate+Spot) — ห้าม cache/embed (กัน double-booking)
  • embeddings/pgvector = เลื่อน + เฉพาะ content (vibe/รีวิว) ไม่ใช่ availability/price · ไม่ต้อง data warehouse (เกินตัวที่ N ~ร้อย)
  • web + practice ยืนยัน: structured+live → function-calling ชนะ embeddings-RAG / text-to-SQL
