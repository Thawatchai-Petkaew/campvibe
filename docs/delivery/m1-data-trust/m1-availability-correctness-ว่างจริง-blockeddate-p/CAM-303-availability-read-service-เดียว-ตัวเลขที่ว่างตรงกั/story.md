# Availability read service เดียว ตัวเลขที่ว่างตรงกันทุกจอ (booking + วันปิด + hold) (CAM-303)

## Why

ตัวเลขที่ว่างวันนี้คำนวณกระจายหลายจุด (หน้ารายละเอียดลาน, ปฏิทินโฮสต์, และในอนาคต AI) เสี่ยงไม่ตรงกันเมื่อต้องรวม BlockedDate + Booking + InternalHold พร้อมกัน ทำให้ลูกค้าเห็นเลขหนึ่งแต่โฮสต์เห็นอีกเลข. KPI: ตัวเลขที่ว่างตรงกัน 100% ระหว่างหน้ารายละเอียดลานกับปฏิทินโฮสต์ (cross-check test), เวลาในการคำนวณ p95 ต่ำกว่า 200 มิลลิวินาที.

## Story

ในฐานะทีมพัฒนา (แทนแพลตฟอร์ม) ฉันต้องการจุดคำนวณที่ว่างจุดเดียวที่ทุกหน้าจอเรียกใช้ร่วมกัน เพื่อให้ตัวเลขที่ว่างตรงกันเสมอไม่ว่าจะดูจากหน้าไหน
Scope: สร้างฟังก์ชัน/จุดอ่านข้อมูลกลาง (อ่านอย่างเดียว) คืนสถานะที่ว่างรายวันต่อลาน โดยรวมผล BlockedDate + Booking (ไม่นับที่ยกเลิกแล้ว) + InternalHold (เฉพาะที่ยัง active และไม่หมดอายุ) ต่อยอดจากฟังก์ชันคำนวณเดิม (CAM-267) ให้หน้ารายละเอียดลานและปฏิทินโฮสต์เรียกใช้จุดเดียวกันแทนการคำนวณซ้ำคนละที่. ไม่รวม UI ใหม่ (หน้าจอเดิมแค่สลับไปเรียกจุดคำนวณนี้)

## AC

| # | Given | When | ผลที่ผู้ใช้เห็น | ผลเชิงข้อมูล |
|---|---|---|---|---|
| AC-1 | ลานมี booking บางส่วน + BlockedDate บางวัน + InternalHold บางวัน ในช่วงเวลาเดียวกัน | เปิดหน้ารายละเอียดลานและปฏิทินโฮสต์เทียบช่วงวันเดียวกัน | ตัวเลขที่ว่างที่แสดงทั้งสองหน้าตรงกันทุกวัน | ทั้งสองหน้าอ่านจากฟังก์ชันคำนวณเดียวกันที่รวม booking, BlockedDate และ InternalHold ในคำสั่งเดียว |
| AC-2 | มี InternalHold ที่ยัง active ครอบวันหนึ่ง | camper ดูที่ว่างวันนั้นจากหน้ารายละเอียดลาน | ที่ว่างวันนั้นลดลงตามจำนวนที่ถูกกันไว้ หรือขึ้นข้อความ `เต็มแล้ว` ถ้ากันหมด | การคำนวณหักจำนวนที่จาก InternalHold ที่ยัง active เช่นเดียวกับที่หักจาก booking |
| AC-3 | มี InternalHold ที่หมดอายุแล้ว | ดูที่ว่างวันเดียวกันอีกครั้ง | ที่ว่างกลับมาเป็นปกติ ไม่ถูกหักจากการกันที่ที่หมดอายุแล้ว | การคำนวณกรองเฉพาะ hold ที่ยังไม่หมดอายุ ณ เวลาที่คำนวณ |
| AC-4 | ต้องคำนวณที่ว่างของช่วงวันยาว 30 วัน | วัดเวลาที่ใช้ในการคำนวณ | หน้าโหลดไม่หน่วง ไม่มีสัญลักษณ์กำลังโหลดค้างนาน | เวลาที่ใช้คำนวณ (p95) ต่ำกว่า 200 มิลลิวินาที วัดจริงก่อนปิดงาน ไม่ใช่ประมาณ |

## Rules

- BR-1 เมื่อวันหนึ่งมีทั้ง BlockedDate และ booking พร้อมกัน BlockedDate ชนะเสมอ (แสดงว่าปิด ไม่ใช่คำนวณที่ว่างจาก booking ต่อ)
- BR-2 ต้องมี test เทียบผลลัพธ์เมื่อทั้ง 3 แหล่งข้อมูลผสมกันพร้อมกัน ไม่ใช่แค่ทดสอบทีละแหล่งแยกกัน

## Data

- อ่านอย่างเดียว: CampSite, Spot, Booking, BlockedDate, InternalHold ไม่เพิ่ม field ใหม่ ไม่มี migration ในใบนี้

## Out of scope

- แคชผลลัพธ์ (ถ้า p95 ไม่ผ่านค่อยพิจารณาเพิ่ม cache เป็น follow-up)
- เปิดจุดคำนวณนี้ให้ AI เรียกตรง → รอ epic M2 AI Camping Assistant (CAM-266)
