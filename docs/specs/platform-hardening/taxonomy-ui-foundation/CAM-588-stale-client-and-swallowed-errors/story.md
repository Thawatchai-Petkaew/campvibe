## Story
As the **Platform** (delivery team), I want a running dev server to notice when its already-loaded Prisma client has gone stale relative to the schema, and I want the camp detail page to stop turning every database/infrastructure failure into a 404, so that the next stale-client incident is caught by the process itself (not just by the next `npm run dev`) and a camper reading `ไม่พบหน้านี้` can trust it means the camp genuinely doesn't exist.
Why: right after the CAM-574/580 location migrations landed, opening a camp detail page on the owner's machine threw `PrismaClientKnownRequestError: The column Location.thaiLocationId does not exist in the current database` — the code and the DB were both correct; the RUNNING dev server just held a Prisma client generated before the migration, and Next.js never reloads it when `prisma generate` re-runs. CAM-579's `predev`/`pretypecheck`/`pretest` guard only checks freshness at process START, so a server already running when a migration lands never re-runs it — exactly this case. It took far longer than it should have to diagnose only because `app/campgrounds/[slug]/page.tsx` caught the thrown Prisma error and called `notFound()`, so the real cause never reached a log or a screen — the app was actively lying about what was wrong.
Scope: (1) a dev-only watcher that notices when `prisma/schema.prisma` (or a migration) changes after the current `npm run dev` process started, and warns loudly in the terminal that the client this process already loaded is now stale; (2) `app/campgrounds/[slug]/page.tsx` stops mapping every thrown error from `getCampBySlug` to `notFound()` — a thrown error now propagates to the app's existing generic error boundary (logged loudly server-side, generic Thai copy to the user, never a stack), while a genuine "no such slug" (`null` result) and the SEC-1 non-public-camp gate keep returning 404 exactly as today. Does not touch `prisma/schema.prisma`, `prisma/migrations/**`, any other page's data-fetch, or CI/e2e config — and does not add a watcher or per-request check to any production path.
Depends on: CAM-579 (sibling — the process-START freshness guard this story extends to a process already running)

## Rules
- BR-1 A thrown error from `getCampBySlug` is never caught into `notFound()` — it propagates out of the page, is logged server-side as one structured line (`event`, `slug`, `message` — no secret/PII, per `.claude/rules/observability.md`), and reaches the app's existing generic error boundary (`app/error.tsx` → `ErrorState variant="error"`), which already never renders a stack/message to the client (proves AC-1)
- BR-2 `campSite === null` after a successful `getCampBySlug` call still calls `notFound()` — unchanged (proves AC-2)
- BR-3 The SEC-1 gate (`canViewCampSite(campSite, session)` → `notFound()`) keeps running unconditionally after `getCampBySlug`, on the live per-request session, exactly as before this story — a 🔴-do-not-touch line (proves AC-3)
- BR-4 The freshness watcher wraps `next dev` only (npm `dev` script); it is never invoked by `next build`, `next start`, or `vercel-build`, and refuses to run at all if `NODE_ENV=production` (defense-in-depth) (proves AC-4's dev-only scope)
- BR-5 The watcher's baseline is the normalized schema hash (same normalize/hash the CAM-579 guard uses — line comments stripped, whitespace collapsed) taken at the moment the wrapper starts; it warns when the CURRENT on-disk hash diverges from that baseline while the process is still alive — not merely when it diverges from the last commit, and not suppressed once `prisma generate` re-syncs the files on disk (that resync is exactly what made the real incident confusing: the files matched again, the running process still didn't) (proves AC-4)

## Edge cases
- EC-1 IF a database/infra error would previously have been silently mapped to a 404 THEN it must now propagate to the error boundary instead — this is the story's core regression case (BR-1)
- EC-2 IF `prisma/schema.prisma` is saved with only a whitespace/comment change (normalized content identical to the baseline) THEN no stale-client warning fires — avoids noise on a no-op save (BR-5)
- EC-3 IF a file changes under `prisma/migrations/` while the server is running, even when `prisma/schema.prisma` itself is untouched in that same edit, THEN the watcher still warns (a migration landing is itself the CAM-588 scenario) (BR-5)
- EC-4 IF `NODE_ENV=production` THEN the watcher script refuses to start at all (BR-4)

## Out of scope
- Auto-restarting or killing the dev server on drift detection → the ticket asks to "notice, or fail loudly," not to force a restart; a human-in-the-loop restart is safer and matches this story's own instruction to never restart/kill a running dev server out from under its owner.
- Extending the freshness watcher to wrap `npm test`/`npm run typecheck` as a long-running watch mode → out of scope; those commands are short-lived and already re-checked at start by CAM-579's existing `pretypecheck`/`pretest` hooks.
- Fixing any other catch-all-swallow-into-404 pattern → none found in this codebase today (see Seams & refs); if one is found later, it gets its own ticket.
