## Story
As the **Platform** (delivery team), I want the e2e-regression Playwright suite to actually run on a clean local checkout, so that the next agent or human verifies a spec against real behavior instead of shipping one nobody could execute and having CI catch it — the most expensive place, a full pipeline plus a human reading logs, per round.
Why: `e2e/regression/README.md` has, since CAM-359, documented a `.env.e2e` file the harness needs — but that file never existed anywhere in the repo, not even as a template, so `npx playwright test --project=regression` could not run for anyone who followed the README literally. That silent gap cost two stories real time: CAM-558 wrote a spec that passed against its own throwaway database and failed in CI with 0 elements found (a data-dependent precondition nobody else could check locally); CAM-570 then edited two specs it could not execute and broke six of them, because the accessible-name lookups no longer matched what the app renders (it only found the actual cause, an English lookup against `global.setup.ts`'s forced-Thai session, after first working around the constraint by starting its own dev server on a spare port).
Scope: (1) make the regression suite runnable locally — a committed `.env.e2e.example` template + a one-command setup script that migrates and seeds a dedicated local database; (2) document the direct-browser-only fallback (the technique that actually unblocked CAM-570) prominently in `e2e/README.md`, with a working snippet; (3) name the Thai-forced-language trap in both READMEs so the next author does not rediscover it by breaking specs; (4) confirm the harness already fails loudly (not silently) when its database precondition is unmet, and align its example fix-text with the new setup convention. Does not fix or re-verify any existing regression spec's assertions, does not touch `prisma/schema.prisma` or add a schema/migration, does not flip CI to blocking.
Depends on: CAM-359 (the harness this story repairs the local on-ramp for) · CAM-558 / CAM-570 (the two incidents this ticket exists to prevent from recurring) · CAM-579 (sibling DevOps ticket, same day — shared `node_modules` risk; this story's script deliberately never invokes `prisma generate`)

## Rules
- BR-1 The local e2e database is a DEDICATED database (convention: `campvibe_e2e`), never the shared local dev database (`campvibe`) a developer's own `npm run dev` points at — the regression suite creates/deletes real rows and must never touch data the developer is using for other local work. `.env.e2e.example` and every fix-message in `db-guard.ts` reflect this convention. (proves AC-1, AC-5)
- BR-2 The setup script reuses `e2e/regression/db-guard.ts`'s `assertLocalDatabaseOrExit` (BR-1 of CAM-359) rather than re-implementing the localhost-only check, and runs `prisma migrate deploy` (which creates the target database if missing and does NOT invoke `prisma generate`) followed by the project's existing `tsx prisma/seed.ts` (already proven idempotent, CAM-359 BR-3) — never `migrate dev` or `migrate reset`, both of which trigger `generate` and are unsafe while `node_modules` is a shared symlink with another live agent (CAM-579). (proves AC-1, AC-5)
- BR-3 `.env.e2e.example` ships ONLY placeholder/local-only values — never a real secret — and documents all 4 vars the harness needs (`DATABASE_URL`, `AUTH_SECRET`, `NEXTAUTH_URL`, `AUTH_TRUST_HOST`). `playwright.config.ts` auto-loads `.env.e2e` (dotenv, path-scoped) but never overrides a var already set by the parent shell or the CI job's own hardcoded env. (proves AC-2)
- BR-4 The direct-browser fallback documented in `e2e/README.md` depends on nothing from the regression harness (no `playwright.config.ts` project, no seeded DB, no `storageState`) — plain `chromium.launch()` from `@playwright/test` against an already-running dev server, so it works even when the harness itself is completely unset up. (proves AC-3)
- BR-5 The Thai-forced-language behavior of `global.setup.ts` itself is unchanged (out of scope to alter — it is intentional, so every regression spec asserts Thai copy verbatim per `.claude/rules/qa.md`); this story only documents it as a named trap in both READMEs. (proves AC-4)

## Edge cases
- EC-1 IF `.env.e2e` is absent or `DATABASE_URL` is unset when `npm run e2e:db:setup` runs THEN the guard aborts before any migrate/seed with the existing clear message (verified: exit 1, no DB touched) (BR-1/BR-2)
- EC-2 IF a developer runs the regression suite without ever running the setup script (empty database) THEN the existing suite behavior is unchanged by this story — the specs themselves surface their own failures (out of scope; this story only makes the happy path reachable) (BR-2)

## Out of scope
- Flipping the `e2e-regression` CI job to blocking → still gated on CAM-359 BR-6's stability criterion (≥10 consecutive green runs) → unchanged, future ticket under CAM-46.
- Fixing or re-verifying any existing regression spec's assertions → not this ticket's surface; specs are read-only here.
- A Docker/CI-parity local Postgres for developers without one installed → assumes a local Postgres install per the existing (pre-CAM-578) convention → follow-up if this becomes a real blocker.
- Making `global.setup.ts` support an English session (e.g. a second storageState) → BR-5 keeps the forced-Thai behavior intentional; a spec needing English forces it itself per the documented pattern → follow-up only if a real spec needs it.

## Self-verify
- AC-1, AC-2, AC-5 → verified by hand, end-to-end, from a clean shell (no ambient env vars): `npm run e2e:db:setup` against a freshly-dropped `campvibe_e2e` (created + migrated + seeded), then `PW_REGRESSION=1 npx playwright test --project=regression` — **38/38 specs passed** (all 6 CAM-359 AC specs + cam-540/549/550/558/560/561), including `ac1-edit-round-trip.spec.ts` run in isolation. The guard (AC-5) was proven red-then-green: pointed `.env.e2e` at a fake non-local host first (`staging-db.example.com`) → aborted with exit 1 and the updated message; restored the real local value → green.
- AC-3, AC-4 → doc-only; the fallback snippet in `e2e/README.md` was run for real against a live `localhost:3000` dev server (`npx tsx` a copy of the exact snippet) and printed the expected match count, not just written and assumed to work.
- Story-specific: confirmed `prisma migrate deploy` does not invoke `prisma generate` (checked the installed 5.22.0 CLI's behavior directly — safe under the shared-`node_modules` constraint, CAM-579); confirmed `dotenv`'s `.env.e2e` load never overrides an already-set var (so the CI job's own hardcoded env for `e2e-regression` in `.github/workflows/ci.yml` is unaffected — that job has no `.env.e2e` file in its checkout regardless).
- Gate = `/quality-gate` (lint/typecheck/vitest — this story touches no production code, so coverage is N/A; the e2e-regression job stays advisory, unchanged). Done = the harness runs locally per AC-1/AC-2 (proven above) + merged into `dev`.
