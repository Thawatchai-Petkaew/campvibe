## Story
As a **Host**, I want each Accommodation type option's name and one-line hint to say what it actually means, so that I can pick the right option for my camp without guessing.

Why: the owner opened the host form and could not tell the 6 accommodation-type options apart. Two were real defects, not unfamiliarity — `TSIT` (ลานกางเต็นท์ / Tent site) and `DISP` (กางเต็นท์อิสระ / Dispersed camping) both mean "camper brings their own tent"; the only real difference is whether the ground is divided into marked pitches, and neither label said so. `HCMP` (แคมป์ม้า / Horse camp) is a US-origin member inherited from the original v1 `AccommodationTypeEnum` (a site with corrals and water troughs for people travelling with horses) with no Thai camp relevance.

Scope: rename the 2 ambiguous `AccommodationTypeEnum` display names so the marked-pitch/no-marked-pitch difference is in the NAME, add a one-line description under every option (`MasterData` gets no new column — descriptions live only in `locales/translations.json`), and drop the `HCMP` enum member entirely (5 members remain: `CABI`/`DISP`/`GROU`/`RECR`/`TSIT`). Backfill the 27 dev-DB camps that carried `HCMP` in their `accommodationTypes` CSV. Does not touch `renderOptionGroup`'s selection/toggle logic, `Equipment for rent: TENT`, or `Activity: HORS` (unrelated codes that legitimately own those values).

Depends on: CAM-536 (renamed the colliding `HORS`/`TENT` codes to `HCMP`/`TSIT` — this story amends that outcome).

## Rules
- BR-1 `AccommodationTypeEnum` (`lib/validations/campsite.ts`) drops the `HCMP` member entirely. The remaining 4 untouched-by-rename members (`CABI`/`GROU`/`RECR`) plus the 2 renamed members (`DISP`/`TSIT`) total 5. No new code is introduced (proves AC-4).
- BR-2 `DISP`'s display name changes to make "no marked pitch" explicit: `nameTh: "กางเต็นท์อิสระ (ไม่แบ่งล็อค)"`, `nameEn: "Dispersed camping (no marked pitch)"`. `TSIT`'s display name changes to make "marked pitch" explicit: `nameTh: "ลานกางเต็นท์แบ่งล็อค"`, `nameEn: "Tent site (marked pitch)"`. Both `prisma/seed.ts` (`MasterData.nameTh`/`nameEn`) and `locales/translations.json`'s `filter.<CODE>` keys (en + th) are updated together — `components/FilterModal.tsx` and `components/CampgroundForm.tsx` render `MasterData.nameTh` directly while the camp detail page renders `t.filter[code]`; updating only one side repeats the exact GLAMP-typo bug this taxonomy epic already hit twice (proves AC-1/AC-2).
- BR-3 A new i18n object `filterDescription` (en + th, sibling to `filter` in `locales/translations.json`) carries one short-line hint per remaining Accommodation-type code (`CABI`/`DISP`/`GROU`/`RECR`/`TSIT`). `MasterData` gets **no new column** — the hint is i18n-only, matching the "no migration" constraint. `CampgroundForm.tsx` renders `t.filterDescription[opt.code]` under the option label when present; other MasterData groups have no entry in this object, so their tiles render unchanged (no description row) — `renderOptionGroup`'s selection/toggle logic is untouched (proves AC-1).
- BR-4 `HCMP` is removed from every emitter, not just the enum: `prisma/seed.ts`'s `masterData` array (the seeded row), `locales/translations.json`'s `filter.HCMP` (en+th), `lib/facility-icon-map.ts`'s `FACILITY_ICON_MAP.HCMP` entry, and `scripts/gen-mock-data.mjs`'s `meadow` theme's `accomm` pool (replaced with `DISP`, already a valid, thematically-fitting code for an open field). The pre-existing, UNRELATED `Activity: HORS` (ขี่ม้า) and `Equipment for rent: TENT` (เต็นท์) rows are untouched (proves AC-4).
- BR-5 `scripts/backfill-cam-538-drop-horse-camp.mjs` rewrites every `CampSite.accommodationTypes` CSV value: each comma-separated value is looked up **whole**, never via substring/global replace — `removeAccommodationCode(csv, 'HCMP')` splits on comma, drops an exact `HCMP` match, rejoins; every other value in the same CSV passes through byte-identical and order is preserved. If `HCMP` was the only value, the column becomes `''` (mirrors the existing "everything deselected" state the host form already writes, CAM-526 BR-3) (proves AC-3).
- BR-6 The backfill is idempotent: a row is written only when its transformed CSV differs from the stored value, so a second run against the same database updates 0 rows. It never calls `deleteMany`; it only rewrites the `accommodationTypes` column via targeted `update` calls scoped to rows that actually changed.
- BR-7 The backfill script refuses to run unless `ALLOW_HORSE_CAMP_BACKFILL=1` is set, `DATABASE_URL` is set, and the target does not look like production (URL contains `prod`, or `NODE_ENV`/`VERCEL_ENV=production`) — mirrors `scripts/backfill-cam-536-accommodation-codes.mjs`/`scripts/db-reset.mjs`; console output prints only scheme+hostname (`describeUrlShape`, reused, not re-implemented).
- BR-8 No schema/migration change: `MasterData` gains no description column; this story is a data-only rename + drop + backfill.

## Edge cases
- EC-1 IF a MasterData group other than `Accommodation type` has no `filterDescription` entry for its codes THEN its option tiles render exactly as before (no empty description row, no layout shift) (BR-3)
- EC-2 IF a camp's `accommodationTypes` CSV contains ONLY `HCMP` THEN the backfill rewrites it to `''` (empty), not a stray comma or leftover code (BR-5)
- EC-3 IF a camp's `accommodationTypes` CSV mixes `HCMP` with a safe code (e.g. `"GROU,HCMP"`, `"HCMP,TSIT"`) THEN only `HCMP` is removed; the safe value and comma structure are preserved exactly (BR-5)
- EC-4 IF the backfill script runs a second time against an already-migrated database THEN it updates 0 rows (idempotent — BR-6)
- EC-5 IF `ALLOW_HORSE_CAMP_BACKFILL` is unset, or `DATABASE_URL` is unset, or the target URL/env looks like production THEN the script refuses and exits non-zero before touching any row (BR-7)
