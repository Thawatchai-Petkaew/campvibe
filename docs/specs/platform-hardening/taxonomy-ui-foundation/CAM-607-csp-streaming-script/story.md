## Story
As the **Host**, I want Next.js's own streaming/hydration scripts to run under our nonce-based Content-Security-Policy without weakening it, so that a `/dashboard/**` page never leaves a stray, un-relocated copy of itself in the DOM (duplicated ids, duplicated form controls, handlers possibly bound to the copy I'm not looking at).
Why: found by CAM-604 while investigating an unrelated hydration bug, and deliberately not fixed there because the true source is shared security middleware (`proxy.ts`), not the one screen CAM-604 was looking at.
Scope: make the existing nonce reach Next.js's own render pipeline (so it can stamp its own inline scripts, including the Flight streaming-segment relocation script) — without adding, removing, or loosening a single CSP directive. Touches `proxy.ts` only; no schema/migration, no new endpoint, no UI.
Depends on: CAM-604 (found and reported this, folded in as this ticket) · CAM-203 (introduced the nonce-based CSP) · CAM-218 (the same family of defect: a nonce that doesn't reach where Next.js expects it, silently, with no thrown error)

## Rules
- BR-1 `proxy.ts` sets the identical `csp` string (same variable, not a re-derived copy) on the request headers via `requestHeaders.set('Content-Security-Policy', csp)`, in addition to the pre-existing `response.headers.set('Content-Security-Policy', csp)` — a request-only header ADDITION, zero change to any directive's content. (proves AC-1)
- BR-2 The pre-existing `x-nonce` custom request header is kept as-is (harmless; it is the doc-recommended convention for app code that wants to manually apply the nonce via `headers().get('x-nonce')`, e.g. a future third-party `<Script nonce>` — it was never the mechanism Next.js's OWN framework-emitted scripts rely on, and removing it is out of this fix's scope). (clarifies AC-1; not a behavior change)
- BR-3 The fault-injection production-build verification (AC-2) is performed manually during self-verify (same method as CAM-604's own investigation) and is NOT shipped as a standing automated test — matching both the CAM-604 precedent for this exact defect and `.claude/rules/qa.md`'s flaky-test guidance (a fault-injection assertion in ordinary CI is a documented source of flake). The deterministic, always-true invariant is captured instead in AC-3. (proves AC-2 is verified, not automated)
- BR-4 No CSP directive's allowed origins/keywords change in this diff — `default-src`, `script-src` (`'nonce-{n}' 'strict-dynamic' 'unsafe-inline' https:`), `style-src`, `img-src`, `font-src`, `connect-src`, `media-src`, `object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`, `upgrade-insecure-requests` are byte-identical before and after; regression-guarded by re-asserting every directive's content in `__tests__/cam-607-csp-request-header.test.ts`. (proves no loosening — nothing is re-allowed, no attacker gains anything)

## Edge cases
- EC-1 IF a future edit derives a SECOND, divergent CSP string for the request vs. the response (instead of reusing the same `csp` variable) THEN the request-side and response-side policies could silently drift — guarded by a source-inspection test asserting both `.set(` calls pass the identical `csp` variable, and both are built from the one `buildCsp(nonce)` call per request.
- EC-2 IF the fault-injection production-build check is automated into the standing CI suite THEN it risks flaking under ordinary CI hardware load (the CAM-604/`.claude/rules/qa.md` trap) — guarded by keeping it a documented, evidenced manual self-verify step instead (BR-3), with the deterministic AC-3 invariant as the permanent regression guard.
- EC-3 IF a route is NOT dynamically rendered (statically prerendered at build time) THEN no per-request nonce exists at all and this fix does not apply to it — that is CAM-218's family, out of this ticket's scope. Every `/dashboard/**` route is already dynamically rendered (each reads the session via `auth()`), so this does not affect this ticket's routes; the fix itself, however, is scoped in shared `proxy.ts` and therefore benefits every dynamically-rendered route site-wide, not only `/dashboard/**`.
- EC-4 IF `requestHeaders.set('Content-Security-Policy', ...)` were placed inside or after the `isRouteAllowed()` authz/redirect branch THEN it would risk conflating the propagation fix with the auth logic — guarded by placing it in the existing pass-through block only (after the authz check has already succeeded), never touching the redirect-to-login branch.
- EC-5 IF the AC-3 test asserted ZERO CSP violations THEN it would be a permanent false-red: this story's own manual verification found ONE pre-existing, unrelated violation on every page load — `next-themes`'s FOUC-prevention script (`components/Providers.tsx`) has never had a `nonce` prop wired and has been blocked since CAM-203 enforced the CSP — outside this story's file surface, reported not fixed (see `tech.md` "Out-of-surface finding"), matching the CAM-604 precedent. AC-3/the e2e spec caps the violation count at `<= 1` instead, so a genuine NEW (2nd+) violation still fails the test.
