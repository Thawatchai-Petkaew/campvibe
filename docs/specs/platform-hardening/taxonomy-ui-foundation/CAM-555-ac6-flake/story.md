## Story
As a **Host**, I want a spot I just created to actually appear in my spots list right after saving it, so that I do not have to guess whether the save worked and reload the page to find out.
Why: `e2e/regression/ac6-spot-lifecycle.spec.ts` failed intermittently on two unrelated PRs (#631 CAM-546 a colour-token change, #645 CAM-558 a className touch-target change) with the identical symptom — `getByTestId(row--spot-{id}) toContainText` times out with "element(s) not found" — then passed on a plain re-run both times. `.claude/rules/qa.md` treats a flaky test as a defect report until root-caused, and both prior `ac6` flakes in this codebase (CAM-359) turned out to be real product races, not harness problems. Root-caused here: it IS a real product race, in `components/spot-management-section.tsx`'s `loadData()`, not the harness or either of the two unrelated PRs.
Scope: fix the shared `loadData()` fetch-isolation gap in `components/spot-management-section.tsx` (+ the extracted `lib/safe-fetch.ts` helper) only. No change to the e2e spec's assertion, the create/spots API routes, or any other component.
Depends on: CAM-359 (the prior stale-response-guard fix in the same `loadData()`; this fix is additive to it, not a replacement) · CAM-362 (the zones-isolation G3 fix this generalizes to camp/session)

## Rules
- BR-1 `loadData()`'s `Promise.all` fetches 4 sources: spots (hard-required — its own failure legitimately blanks the list, AC-3), camp-detail, session, and zones (already isolated since CAM-362). Camp-detail and session must ALSO resolve to `{ ok: false }` on any failure (bad status OR network-level rejection) instead of throwing/rejecting, via `lib/safe-fetch.ts`'s `fetchJsonSafe` — mirroring the exact never-throw contract `fetchZonesSafe` already established.
- BR-2 `canManage` (edit/delete button visibility) is the ONLY thing camp/session data feeds. A camp/session hiccup must fail `canManage` closed to `false` for that load, never open — BR-4 (`requireCampSitePermission`, server-side) remains the sole authoritative check regardless of what this client gate shows.

## Edge cases
- EC-1 IF the session fetch OR the camp-detail fetch rejects at the network level during a `loadData()` call THEN the spots list still commits from the (independently successful) spots fetch — proved by fault-injecting a network-level `route.abort("failed")` on exactly the second `/api/auth/session` call (the post-create refetch, not the initial mount load) and separately on the second `/api/campsites/{id}` call; both reproduced the exact reported symptom before this fix (100% reproduction rate, 1/1 and 1/1) and both are green after it (5/5 and 5/5, plus a further 5/5 clean run of the unmodified re-run of the RED case immediately re-confirming red-before-green).
- EC-2 IF the spots fetch itself fails (bad status or network rejection) THEN `loadError` is still set and the error banner still renders — this story does not weaken the one failure mode that legitimately should blank the list (spots data is hard-required, unlike camp/session).

## Data
- No schema/data change. Client-side fetch-isolation fix only: `components/spot-management-section.tsx` (`loadData`) + new `lib/safe-fetch.ts` (a generic, exported `fetchJsonSafe<T>`, mirroring `lib/zone-client.ts`'s `fetchZonesSafe`). Migration: none.

## Seams & refs
- Reuse: `lib/zone-client.ts`'s `fetchZonesSafe` (CAM-362 G3 fix) is the existing precedent for "never-throw GET+JSON" — `lib/safe-fetch.ts`'s `fetchJsonSafe<T>` generalizes the exact same contract so camp-detail and session can share it too, instead of duplicating the try/catch inline per call site.
- Root cause (verified empirically, not guessed — see `test.md` for the full repro log): `loadData()` placed 4 requests inside ONE `Promise.all` with ONE shared `catch`. The CAM-362 G3 fix already isolated `zonesResult` (never throws), but `campRes`/`sessionRes` were still plain `fetch()` calls. `Promise.all` rejects as soon as ANY one of its entries rejects, regardless of the others' outcomes — so a network-level hiccup on EITHER `campRes` or `sessionRes` (nothing to do with spot data) rejected the whole batch before `setSpots(...)` ever ran, and the shared `catch` set `loadError=true`, replacing the list with the error banner even though `spotsRes` itself had already succeeded and contained the spot the host had just created. This is the identical *shape* of bug the CAM-362 G3 fix closed for zones (documented in that fix's own code comment: "a zones failure is isolated to its own state — it must never throw here, or the shared catch below would blank the whole section") — camp/session simply never received the same treatment.
- Reader/writer sweep (architecture.md §15b — is this a shape change?): NO. `campRes`/`sessionRes` fed exactly one derived value (`canManage`) before and after; nothing about what `canManage` MEANS or how it is consumed downstream changes — only the failure mode of the two fetches that feed it. No other reader of `spots`/`canManage` exists outside this component (grep-confirmed: `canManage` is component-local state, never exported/read elsewhere).
- Refs: — (no ADR; a scoped fetch-isolation bugfix, additive to CAM-359/CAM-362 in the same function).
