## Story
As a **Camper** using the น้องกองไฟ chat assistant, I want the result cards to paginate clearly and show information that actually reflects what I searched for, so that I can trust the cards and tell at a glance which one I'm looking at while scrolling.
Why: six real defects the owner found testing the live (now dark-by-default, CAM-544; now full-screen on mobile, CAM-550) chat surface on 2026-07-26 — an indicator that looks broken, a shadow that looks clipped, a redundant line, a badge that lies about the search, a rating buried below the fold, and (found + reported mid-story by the coordinator, same surface) the first card sitting flush against the mobile screen edge with no gutter.
Scope: `components/ai-chat/AiChatCardCarousel.tsx` (pagination indicator + track shadow clipping + the mobile edge gutter) · `components/ai-chat/AiChatCampCard.tsx` (redundant line removal + rating relocation) · investigation-only for the search-aware badge (no code change; see Out of scope). Does NOT touch `AiChatPanel.tsx`/`AiChatLauncher.tsx` (CAM-550 just landed there), `AiChatMessageList.tsx`, `CampgroundCard.tsx`, `lib/read-models/camp-card.ts`, or any token/`app/globals.css` value. Does NOT re-solve CAM-541 (assistant light-mode legibility / orange border-glow / duplicate avatar) — those stay exactly as they are.
Depends on: CAM-409 (carousel + indicator, this story's AC-1/AC-2/AC-7 territory) · CAM-428 (the dedicated card, this story's AC-3/AC-5 territory) · CAM-427 (`AiChatCardResponse`/`options[0]` first-tag, the field AC-4 investigates) · CAM-537/CAM-546/CAM-544 (the dark-theme tokens this story measures, none of which this story changes) · CAM-550 (mobile full-screen assistant, rebased onto; AC-7's gutter only exists inside CAM-550's `max-sm:` full-screen branch)

## Rules
- BR-1 The active-position indicator's PRIMARY signal is shape, not colour: the current dot renders wider (`h-1.5 w-4`) than the inactive dots (`h-1.5 w-1.5`), both `rounded-full bg-primary`/`bg-muted-foreground` respectively (proves AC-1). Colour alone is deliberately NOT relied on — measured dot-to-dot contrast never exceeds ~2.17:1 at any inactive-dot opacity tried (30-100%), because `--primary` and `--muted-foreground` sit close in perceptual lightness in the shipped dark theme; this matches design.md's own pre-existing "never colour alone" a11y note for this exact indicator.
- BR-2 The inactive dot's own opacity moves `muted-foreground/30` -> `muted-foreground/60` (measured 1.78:1 -> 3.40:1 against the panel surface `--ai-surface`, clearing the WCAG 1.4.11 3:1 non-text floor on its own) — a real, secondary, additive improvement, not the primary fix (BR-1 is).
- BR-3 The `{cur}/{N}` counter fallback above `MAX_DOTS` (5) is UNCHANGED — confirmed as documented, intentional design.md behaviour (not a wiring defect); redesigning that threshold or unifying the two indicator styles is a Designer decision, out of this bug-fix's scope (proves AC-2).
- BR-4 The multi-card track's bottom padding (`pb-14`, was `py-4`) is sized to the real `--ai-glow` (dark) token's dominant shadow layer's measured downward reach (~52px: `offset 22px + blur 56px - spread 26px`); top padding (`pt-4`) is unchanged because the same layer's upward reach (~8px) already fit (proves AC-3).
- BR-5 The visible `ดูรายละเอียด` line is removed from the card body; the identical copy key stays wired into the button's `aria-label` (unchanged expression: `` `${name} ${t.aiChat.card.viewDetail}` ``) so the accessible name is provably unaffected (proves AC-4).
- BR-6 The rating renders as an image-overlay badge (top-left, `Badge variant="overlay"`) ONLY when `hasReviews && avgRating != null` (the same condition the pre-existing inline rating used) — the `noReviews` empty state is UNMOVED (stays inline, below the image) and the two never render simultaneously (proves AC-5/EC-4).
- BR-7 The card's first-tag badge continues to read `card.options[0]` (the camp's own fixed Terrain-group tag) — confirmed, not changed, because no search-matched-filter data reaches `AiChatCardResponse`/the client anywhere in the current wire contract (proves AC-6; see Seams & refs for the exact gap).
- BR-8 The track carries `scroll-px-4` alongside its existing `px-4`/`-mx-4` pairing — measured with a real Chromium render (Playwright, 390x844, against the actual compiled Tailwind CSS) that WITHOUT it, `scroll-snap-type:mandatory` + `scroll-snap-align:start` children forces the resting `scrollLeft` to 16px (the padding width) on load instead of 0, visually eating the entire leading gutter (card measured flush at 0px from the true edge; WITH `scroll-px-4`, resting `scrollLeft` returns to 0 and the card measures 16px, matching the surrounding text). This is a DIFFERENT mechanism from the shadow clip (BR-4, `overflow-x-auto` forcing `overflow-y:auto`) — the two live on the same element but do not share a root cause, confirmed by measurement, not assumed (proves AC-7).

**On the safe-area-inset question (investigated, not implemented):** the coordinator asked whether the left/right gutter should also account for `env(safe-area-inset-left/right)` on a notched phone in landscape. Checked against the real breakpoint: this carousel's mobile edge-bleed classes are only active inside CAM-550's `max-sm:` (below 640px) branch. The narrowest realistic phone LANDSCAPE width (iPhone SE, ~667px) already exceeds 640px, so on every real device this carousel's mobile treatment only ever renders in PORTRAIT — where a notch's safe-area-inset only ever affects the TOP, never the left/right. `env(safe-area-inset-left/right)` is therefore always `0` everywhere `max-sm:` is active today; adding explicit handling for it would be unreachable, untestable defensive code (code.md "no future-proofing"). If the `sm:` breakpoint ever changes, or a foldable/odd form factor is added to the support matrix, this reasoning should be re-checked.

## Edge cases
- EC-1 IF a search returns exactly `MAX_DOTS` (5) cards THEN dots still render (not the counter) — the existing `cards.length > MAX_DOTS` boundary is unchanged (BR-3).
- EC-2 IF a card sits at the FIRST or LAST position in the strip (no neighbour on one side) THEN its shadow still gets the same widened bottom clearance — the fix is on the shared track, not per-card position (BR-4).
- EC-3 IF a screen-reader user tabs to a card THEN the announced name is `"<camp name> ดูรายละเอียด"`, identical before and after this story (BR-5) — asserted directly, not inferred.
- EC-4 IF a card has zero reviews (`hasReviews` false or `avgRating` null) THEN no rating badge renders on the image, and the pre-existing `t.aiChat.card.noReviews` (`ยังไม่มีรีวิว`) text still renders inline below, unmoved (BR-6).
- EC-5 IF the search intent were ever threaded to the card (future work, not this story) THEN the badge should prefer the matched taxonomy tag over the fixed first tag — noted as the exact seam for the follow-up ticket (BR-7).
- EC-6 IF the strip is scrolled all the way to the last card THEN the trailing gutter after it is also 16px (symmetric with the leading gutter) — `scroll-px-4` applies to both inline edges, not just the start (BR-8).

## Data
- No schema/migration. `AiChatCardResponse.options` (existing, `lib/api-client.ts`) is read exactly as before (`options[0]`) — not touched. No new field added this story (AC-6 is investigation-only).

## Seams & refs
- Reuse: `components/ui/badge.tsx` `variant="overlay"` — the SAME idiom `components/CampgroundCard.tsx` already uses for its own image-overlay badges (New Listing / availability status); no new component. `scripts/check-contrast.mjs`'s own colour-space maths (`parseTokens`/`resolveSurface`/`resolveOver`/`compositeOver`/`contrastRatio`) was reused (imported, read-only) to measure the dot/shadow numbers in this story's investigation — not modified. Tailwind's own core `scroll-p*` scroll-snap utilities (BR-8) — no custom CSS.
- AC-7's gutter cause lives ENTIRELY inside `AiChatCardCarousel.tsx` (the track's own `scroll-snap-type`/padding pairing) — it does NOT require touching `AiChatMessageList.tsx`'s `p-4` (the ancestor the track bleeds against) or `AiChatPanel.tsx` (out of bounds, CAM-550's surface). Confirmed by measurement: the reference message text's own 16px gutter was UNCHANGED throughout the investigation; only the card's position needed correcting.
- The AC-6 gap, precisely: `lib/ai/tools/search-campsites.ts` accepts structured taxonomy args (`terrain`/`activities`/`facilities`/`camperStyle`/etc.) and builds a `where` clause from them, but the rows it fetches back go through `lib/read-models/ai-camp-card.ts`'s `toAiCampCard`, whose `options` select is HARDCODED to `where: { group: 'Terrain' }, take: 1` — it does not know or carry which argument (if any) actually matched this particular card. Closing this needs: (a) a new optional field on `AiChatCardResponse` (e.g. a per-card "matched tag"), additive per api.md rule 12; (b) `search-campsites.ts` (or `ai-camp-card.ts`) deriving that matched tag from the SAME args it already has in scope, per card. Both are backend/API-contract changes outside this story's frontend-only file surface — proposed as a follow-up ticket, not built here.
- Refs: CAM-409 design.md (the indicator/track spec this story amends) · CAM-428 design.md (the card frame spec this story amends) · CAM-537 (`check:contrast`, the measurement tool reused) — pointers only, no implementation duplicated here.
