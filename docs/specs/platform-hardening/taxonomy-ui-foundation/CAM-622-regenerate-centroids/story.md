# Half the province centres are kilometres from where the camps actually are (CAM-622)

## Story
As the **Camper**, I want "ใกล้ X" / "แถว X" proximity search to sort from a point that actually reflects where X's camps are today, so that the "nearest" camp shown is genuinely the nearest one, not the nearest one to a stale mean.
Why: CAM-620's new drift check found, on its first real run, that 38 of 77 committed province centroids have moved 5.1km-20.2km from the live camp distribution — 0 provinces added/removed, only drifted. `scripts/backfill-cam-571-coordinates-inside-thailand.mjs`'s own comment says the committed file "is itself derived from the CURRENT, partly-wrong seed coordinates"; CAM-571 (18 camps moved inside Thailand), CAM-583 (~100 camps aligned to their stored province) and a staging-to-dev sync (~650 → 795 camps) have each moved a mean the committed file never re-learned. A centroid this far off does not fail loudly — it quietly re-ranks which camps a camper sees first.
Scope: regenerate `prisma/data/province-centroids.json` via the existing, unmodified `scripts/build-province-centroids.mjs` against the current dev DB, and confirm `scripts/check-province-centroid-drift.mjs` (CAM-620, also unmodified) reports 0 drift afterwards. Does not touch `lib/ai/tools/search-campsites.ts`, its near-path logic, or either script — this story is a data regeneration + behavioral proof, not a code change.
Depends on: CAM-502 (P2 geo proximity, the centroid table + near-path) · CAM-620 (the drift check that found the drift).

## Rules
- BR-1 The regenerated artifact is produced ONLY by re-running the existing, unmodified `scripts/build-province-centroids.mjs` — never hand-edited. A hand-edit cannot be trusted to match the live mean and defeats the point of a generated, build-step-derived artifact (CAM-502 tech.md/BR-1).
- BR-2 No code changes to `scripts/build-province-centroids.mjs`, `scripts/check-province-centroid-drift.mjs`, or `lib/ai/tools/search-campsites.ts`'s near-path. This story regenerates data under the EXISTING rules (mean lat/lng, `MIN_CAMPS_FOR_CENTROID = 2` sparse guard, deterministic sorted-key output) — a disagreement with those rules (e.g. the threshold, the averaging method) is a separate conversation, reported, not acted on here.
- BR-3 The regeneration must not silently drop a province: the key set of the regenerated file must be compared against the pre-regeneration key set, and any province present before but missing after is a blocking finding, not a footnote — this is the ticket's own named "invisible" failure mode (a dropped centroid loses proximity behaviour entirely, with no error).
- BR-4 The behavioral claim ("proximity ranking changed for a camper") is proven against real camp rows for at least 2-3 of the most-shifted provinces — not inferred from the coordinate delta alone. If the ranking happens to be identical despite a large coordinate shift, that is reported honestly as a finding, not glossed over.
- BR-5 The CAM-502/503 golden vitest suites are re-run against the regenerated file, never edited to match new output. A moved golden case is reported as a finding for the ticket/PR, not silently patched.

## Edge cases
- EC-1 IF the regenerated file's province-key count changes (added or removed) THEN this is NOT the pure-drift case this story addresses — investigate before committing. Measured here: 77 → 77 keys, 0 added, 0 removed (confirmed by `check-province-centroid-drift.mjs`'s own `added`/`removed` report AND an independent key-set diff).
- EC-2 IF `check:province-centroid-drift` reports anything other than "0 drift" after regeneration THEN the regeneration is incomplete or the DB changed between the build and check calls — re-run both against a stable snapshot.
- EC-3 IF a "ใกล้ X" comparison shows the SAME top-ranked camp under both the old and the new centroid THEN that is reported as a real, honest finding (the shift did not change the practical answer for that province) rather than asserted as a universal "everything changed."
- EC-4 IF a province held a centroid before regeneration (≥2 camps) but drops out after (its live camp count fell below 2) THEN this is a `removed` case, not a `shifted` one, and must be called out explicitly as a behavior change (proximity search for that province now falls back to an exact-province filter) — not found in this run (0 removed).
- EC-5 IF a CAM-502/CAM-503 vitest assertion fails after regeneration THEN it is reported as a moved golden case for the ticket/PR to resolve — never silently edited to match the new output under this story.
