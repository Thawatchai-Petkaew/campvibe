## Story
As the **Platform** (delivery team), I want the e2e-regression harness's mid-run "socket hang up" investigated to a NAMED mechanism (or an honest non-reproduction) and hardened so it cannot silently hide a real server crash, so that `e2e-regression` can keep accumulating the 10 consecutive green runs BR-6 (CAM-359) needs to become a blocking gate — an unexplained abort resets that clock every time it happens.
Why: `.claude/rules/qa.md` treats a flaky test as a DEFECT REPORT until root-caused (CAM-359/CAM-346 were both real product races, not noise) — so "this is just CI flakiness" has to be proven, not assumed, even though the first sighting (PR #667, a `scripts/ticket-sync.mjs`-only diff) is strong evidence the cause cannot be product code.
Scope: investigate why the `next dev` webServer used by `e2e-regression` occasionally emits `Error: aborted {code:'ECONNRESET'}` mid-suite, and — if the cause is confirmed environmental/harness-level — hardens the harness's own Node-side `request.*` calls against exactly the failure mode observed, without masking a real webServer crash. Does not touch `app/**`, `lib/**`, `components/**`, `prisma/**` — if the investigation had found the cause inside product code, this story would stop and report it, not fix it there (none was found).
Depends on: CAM-586 (superseded/cancelled — first sighting + escalation instruction, folded into this ticket) · CAM-359 (BR-6, the 10-consecutive-green-runs criterion this story protects) · CAM-578 (made the regression suite runnable locally, which is what made this investigation possible without waiting on CI)

## Rules
- BR-1 The retry predicate (`isTransientKeepAliveRace`) matches ONLY a message containing "ECONNRESET", "socket hang up", or "aborted" — AND NEVER a message containing "ECONNREFUSED" (checked first, short-circuits) — no broader match, no blanket "any network error retries." Matched on message TEXT, not a `.code` property (Playwright relays this failure to the test process as a plain `Error` with no `.code` set — verified directly, see tech.md §5). (proves AC-2, AC-3)
- BR-2 The retry is capped at exactly one attempt; a second failure of any kind (including the same narrow class recurring) propagates unchanged — never a loop, never swallowed silently. (proves AC-2)
- BR-3 A retry that fires is always recorded as a `cam-603-transient-retry` test annotation (visible in the HTML report) — never a silent pass indistinguishable from a run that needed no retry at all. (proves AC-2)
- BR-4 `ECONNREFUSED` is excluded from the retry predicate on purpose — it is the signature of a webServer process that is actually down, and every subsequent request during that condition also gets `ECONNREFUSED`, so excluding it here is what keeps a real crash failing loudly across the whole remaining run. (proves AC-3)

## Edge cases
- EC-1 IF the exact client-visible failure cannot be forced to reproduce within a reasonable investigation budget THEN it is reported honestly as "not fully reproduced," alongside what WAS ruled in/out and the mechanism named with its supporting evidence — never presented as a confirmed root cause it isn't; in THIS investigation it DID reproduce (`apiRequestContext.get: read ECONNRESET` on a real `request.get` call, caught while self-verifying the fix — see tech.md §5), which also caught and corrected a real gap in the retry predicate's first draft (BR-1..4, tech.md)
- EC-2 IF a spec's own `request.*` call fails for a reason unrelated to the narrow class (e.g. a real `404`/`500`, or an assertion on the response body) THEN `withKeepAliveRaceRetry` does not intercept it at all — the original error/assertion failure surfaces exactly as it would have before this story (BR-1)
- EC-3 IF the retry itself throws a DIFFERENT error than the first attempt (e.g. first attempt: transient reset; retry: a real `500`) THEN that second error is the one that propagates — the wrapper never manufactures a misleading message (BR-2)
- EC-4 IF a `request.put` call being wrapped is not idempotent THEN it must not go through this retry (checked case-by-case; the one PUT wrapped here — `cam-558-touch-targets.spec.ts`'s `giveCampTwoImages` — sends a fixed, deterministic body, so retrying it once is safe) (BR-1)
