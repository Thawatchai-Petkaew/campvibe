## Story
As a **Host**, I want to record which accommodation types my camp offers (cabin, dispersed, group, RV, etc.), and as a **Camper**, I want to see those types on the camp detail page, so that a scalar field that already round-trips correctly through validation stops being invisible on both ends of the product.

Why: `accommodationTypes` was fully wired in the middle (zod `AccommodationTypeEnum`, POST write, edit prefill) but dead on both ends — the host form calls `renderOptionGroup(t.filter["Accommodation type"], "Accommodation type", "accommodationTypes")` against a MasterData group that was never seeded (options.length===0 guard returns null, so the control renders as nothing), the camper detail page never had a display section for it at all, and the PUT route's `data.accommodationTypes?.length` guard treats an intentional "host cleared every selection" the same as "host didn't touch this field" — the CAM-341/CAM-360 collapse-to-skip bug class — so a previously-set value could never be removed.

Scope: seed the `Accommodation type` MasterData group (bringing the existing, unmodified host-form control to life), fix the PUT clearing bug, add a detail-page display section via the CAM-528 `OptionGroupSection` primitive, and fix the `GLAMP` `nameTh` transliteration typo in the seed data. No schema change, no migration, no relation conversion — `accommodationTypes` stays the scalar CSV string column it already is. `components/CampgroundForm.tsx`, `app/api/campsites/route.ts` (POST), and `lib/validations/campsite.ts` are unmodified (already correct).

Depends on: CAM-528 (`OptionGroupSection` primitive, merged to `dev` first).

## Rules
- BR-1 The `Accommodation type` MasterData group is seeded with exactly the `AccommodationTypeEnum` members that do NOT collide with an existing MasterData code: `CABI` (Cabin/กระท่อม), `DISP` (Dispersed/กางเต็นท์อิสระ), `GROU` (Group/ที่พักแบบกลุ่ม), `RECR` (RV, per the original v1 plan's "Bigrig→RECR" reconciliation/รถบ้าน). Each row carries a real Thai + English name and reuses an existing icon name already in `lib/facility-icon-map.ts`'s `ICON_BY_NAME` (Bed / Trees / Users / Car respectively) — `lib/facility-icon-map.ts` itself is not modified by this story (proves AC-1).
- BR-2 (real conflict found during research, not assumed) `HORS` and `TENT` — 2 of the 6 `AccommodationTypeEnum` members — are **excluded** from this seeding. `MasterData.code` is a global `@id` (not scoped per group): `HORS` already exists as `group: 'Activity'` (ขี่ม้า / Horseback riding) and `TENT` already exists as `group: 'Equipment for rent'` (เต็นท์ / Tent, itself referenced by seeded camp `equipment` values). Upserting either code under `group: 'Accommodation type'` would silently move that row OUT of its current, live group — breaking the Activity and Equipment-for-rent pickers/displays for every camp already using them. Both codes remain valid in the zod enum (unchanged — `lib/validations/campsite.ts` is out of this story's file surface) and a host/camp CAN still store them in the CSV column (round-trips through POST/PUT unaffected), but neither is selectable via the Accommodation-type picker nor renders a labeled tile in that section until a follow-up resolves the collision (rename the 2 enum members + backfill existing `TENT`-valued rows, or another approach — an architecture decision, not made here). This is a real, partial-completion gap, flagged for a decision rather than silently worked around.
- BR-3 The PUT route (`app/api/campsites/[id]/route.ts`) gates the `accommodationTypes` write on `data.accommodationTypes !== undefined` (key present in the parsed body — CSV-array field omitted from partial `.partial()` parse stays `undefined`, matching the `annotatedFeatures`/`camperStyle` presence-gate pattern already used for the `options` relation), not on truthy `.length`. An explicit empty array writes `''` (the column is non-nullable `String`, no MasterData relation involved) via `arrayToCsv(data.accommodationTypes) ?? ''` — `arrayToCsv([])` returns `undefined`, which Prisma would otherwise treat as "leave the column untouched" (proves AC-3).
- BR-4 The detail-page section renders via the CAM-528 `OptionGroupSection` primitive (unmodified), fed `codes={csvToArray(campground.accommodationTypes)}` (the existing `lib/api-utils.ts` helper — never hand-split the CSV string) and the page's existing shared `getLabel`/`getIcon` — same empty-gate pattern (`codes.length > 0`) as every other taxonomy section (proves AC-2).
- BR-5 `prisma/seed.ts`'s `GLAMP` row `nameTh` is corrected from `'กลามปิ้ง'` to `'แกลมปิ้ง'` (the translations-side key was already fixed by CAM-531; the seed source was not). Since `FilterModal.tsx`/`CampgroundForm.tsx` render `MasterData.nameTh` directly (not the i18n key), this fix only reaches a live host/filter UI after a re-seed — `npx prisma db seed` is idempotent-upsert (never deletes), safe to re-run, but is NOT run against staging/prod from this story (owner/devops runs it) (proves AC-4).

## Edge cases
- EC-1 IF the `Accommodation type` MasterData group has zero rows (pre-this-story state) THEN the host form section renders nothing (`options.length === 0` guard, unchanged, pre-existing `CampgroundForm.tsx` behavior) (BR-1)
- EC-2 IF a camp's `accommodationTypes` column is empty (`''`) THEN no Accommodation-type section renders on the detail page (no heading, no empty grid) (BR-4)
- EC-3 IF a PUT body omits the `accommodationTypes` key entirely THEN the column is left untouched (a price-only or unrelated-field edit must never wipe a previously-set accommodation selection) (BR-3)

## Data
- No schema/migration change. `CampSite.accommodationTypes` stays a scalar CSV `String` column (not converted to a `MasterData[]` relation). New `MasterData` rows: `CABI`/`DISP`/`GROU`/`RECR` under `group: 'Accommodation type'` (upsert via `prisma/seed.ts`, idempotent). `GLAMP` row's `nameTh` corrected in place (same upsert). Migration: none — a seed change only reaches a live DB on the next `npx prisma db seed` run (dev/staging/prod re-seed is out of this PR's scope).
