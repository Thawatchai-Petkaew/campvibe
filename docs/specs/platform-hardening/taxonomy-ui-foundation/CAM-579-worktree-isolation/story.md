## Story
As the **Platform** (delivery team), I want every agent worktree's generated Prisma client isolated instead of shared, so that a concurrent `prisma generate` in one worktree can never silently overwrite the type definitions and runtime metadata another worktree's agent is reading — turning a cross-agent corruption into a structural impossibility instead of a dispatch-time reminder.
Why: the old instruction (`ln -s <main tree>/node_modules node_modules`) puts every worktree's `node_modules/.prisma/client` on the SAME physical folder. While CAM-555's agent worked, CAM-574's concurrent agent ran `prisma generate` against its own (schema-shrinking) branch and clobbered that shared folder — CAM-555's dev server started 500ing on a field it never touched, and 4 typecheck errors appeared in code it had never edited. It diagnosed the stack trace correctly and moved on, but the next agent might not: the failure looks exactly like a bug in the victim's own work.
Scope: (1) a worktree bootstrap script (`scripts/worktree-setup.sh`) that symlinks the bulk of `node_modules` (cheap, same speed as before) but gives each worktree its OWN real `node_modules/.prisma` + `node_modules/@prisma/client`, generated fresh from that worktree's own schema; (2) a fast, automatic loud-failure guard (`scripts/verify-prisma-client-fresh.mjs`), wired as an npm pre-hook, that fails immediately and unmistakably if a client ever goes stale relative to its own worktree's schema; (3) the dispatch guidance in `.claude/commands/camper.md` updated so the next orchestrator inherits the fix. Does not touch `prisma/schema.prisma`, `prisma/migrations/**`, or any application code (`app/`, `lib/`, `components/`) — this is a tooling/process fix, not a schema change.
Depends on: CAM-577 (sibling, same family — `ticket-sync.mjs` failing inside a worktree because `STATUS_TOKEN` is missing; a related but separate gap, not fixed here) · CAM-578 (sibling, same day — its own local-e2e-DB setup script deliberately avoids `prisma generate`/`migrate dev` specifically because of this ticket's hazard, and names CAM-579 explicitly in its own spec)

## Rules
- BR-1 `worktree-setup.sh` symlinks every top-level `node_modules` entry from the main tree EXCEPT `.prisma` and `@prisma` — the two whose real (symlink-resolved) location decides where `prisma generate` places its output (`.prisma/client`, as a sibling of wherever `@prisma/client`'s `package.json` resolves to). (proves AC-1, AC-2)
- BR-2 `@prisma/client` itself is a real, local copy (~180KB, never mutated by `generate` — only `.prisma/client` is) so its realpath — and therefore the sibling `.prisma/client` `generate` writes to — stays inside the worktree; every other `@prisma/*` package (`engines`, `debug`, `engines-version`, `fetch-engine`, `get-platform`) is still symlinked, since none of them anchor `generate`'s output. (proves AC-1, AC-2)
- BR-3 After linking, the script always runs `npx prisma generate` (+ `npm run delivery:generate` when `prisma/delivery/schema.prisma` exists) so the worktree's client matches its OWN checked-out schema from the very first run — isolation alone is not enough if the client is never generated. (proves AC-1)
- BR-4 `verify-prisma-client-fresh.mjs` compares a NORMALIZED hash (line comments stripped, whitespace collapsed) of `prisma/schema.prisma` (and the delivery schema) against the schema copy `prisma generate` embeds in its own output — a raw byte-for-byte hash is rejected because `prisma generate` re-formats the embedded copy (re-aligns columns, re-wraps comments) even when the schema content is unchanged, which produced a false "STALE" verdict on a genuinely fresh client during this story's own verification. (proves AC-3)
- BR-5 The guard is wired through npm's built-in pre-hook convention (`predev`/`pretypecheck`/`pretest` in `package.json`) — a mechanism that fires on every `npm run dev|typecheck|test` automatically, not a line in a doc someone has to remember to follow. (proves AC-3)
- BR-6 The script refuses to run from the main tree (`MAIN_TREE == cwd`) — the main tree already owns its real `node_modules`; running the isolation step there is a no-op error, never a silent write into the tree the owner's dev server reads. (proves AC-1's safety precondition)

## Edge cases
- EC-1 IF the script is re-run in a worktree that is already isolated (real `node_modules` + real `node_modules/@prisma`) THEN it skips re-linking and only re-runs the two `generate` calls — idempotent, no wasted relinking (BR-1)
- EC-2 IF a worktree is still bootstrapped with the OLD bare `ln -s <main tree>/node_modules node_modules` (pre-fix, or a bypass of the new doc) THEN the exact collision this story reproduces recurs — the fix is not retroactive to a worktree that skips `worktree-setup.sh` (BR-1, BR-2)
- EC-3 IF a client's embedded schema matches its own source schema only after `prisma generate`'s own whitespace/comment reformatting (not byte-identical) THEN the guard reports OK, not a false failure (BR-4)
- EC-4 IF `prisma/delivery/schema.prisma` does not exist in a given checkout (an older branch) THEN the delivery-client half of the guard is skipped, not treated as a failure (BR-4)

## Out of scope
- Making a real `npm ci` per worktree the default → rejected on cost: a full `npm ci` (network + dependency resolution) is minutes; this fix's per-worktree cost is symlinking ~600 entries + copying one ~180KB folder + two `prisma generate` calls (a few seconds total, no network — the query-engine binary is already cached from the main tree's install). Not planned; this ticket IS the leaner alternative.
- Fixing CAM-577 (`STATUS_TOKEN` missing in worktrees so `ticket-sync.mjs show`/`audit` fail) → CAM-577 (separate ticket, same family, different root cause and fix).
- Extending isolation to any OTHER regenerable/mutable file under a shared `node_modules` → no second such artifact exists in this codebase today (the delivery-ticket Prisma client already writes outside `node_modules`, to `prisma/delivery/generated/`, and is naturally per-worktree already); revisit only if one appears.

## Self-verify
- AC-1, AC-2 → reproduced then proven fixed end-to-end in two disposable git worktrees (`git worktree add`, later removed) sharing a cloned `node_modules`, isolated from the repo's own `.claude/worktrees/*` tree so no real in-flight agent work was touched: (a) **before the fix** (old whole-tree symlink) — both worktrees generated clean (0 typecheck errors); one worktree removed `CampSite.minimumAge` + the `location` relation from its OWN schema and ran `prisma generate`; the OTHER, untouched worktree's `npx tsc --noEmit -p tsconfig.json` went from **0 → 92 errors** across ~30 real files it never edited, including `app/api/operator/dashboard/route.ts` — the exact route named in the CAM-555 incident — with no code change on its side. (b) **after the fix** (`worktree-setup.sh`) — the identical sequence (schema edit + `prisma generate` in one worktree) left the other worktree at **0 errors, unchanged**, and its own generated client still correctly declared the field/relation the first worktree had removed (`grep -c minimumAge` on each worktree's own `.d.ts`: 88 in the untouched one, 0 in the edited one).
- A real bug in this story's OWN first draft was caught this way, not guessed: an early version of `worktree-setup.sh` symlinked the whole `@prisma` scope directory to the main tree; `prisma generate`'s "no explicit `output`" placement follows the REALPATH of `@prisma/client`, so that draft's first run wrote the regenerated client into the MAIN TREE's `node_modules/.prisma/client` — confirmed via the main tree's file mtime changing during a routine test, caught and fixed (per-package copy of `@prisma/client` only) before this ever reached a commit. The resulting main-tree content was verified semantically unchanged (same fields/models — `prisma generate` had only reformatted whitespace) using the same normalization described in BR-4, so no real corruption occurred, but the near-miss is the reason `worktree-setup.sh`'s BR-1/BR-2 comments spell out exactly why `@prisma` (not just `.prisma`) needs the special case.
- AC-3 → the guard was proven red-then-green: edited a worktree's own `prisma/schema.prisma` without regenerating → `bash -c` invocation of the guard exits 1 with the STOP block naming the exact mismatched file and fix command; `npm run typecheck` in the same state auto-ran `pretypecheck` and stopped BEFORE `tsc` executed at all (proving the hook wiring, not just the script). Regenerating cleared it back to a clean pass, and `npm run typecheck` then proceeded normally to `tsc` (which then reported an expected, self-consistent error from the test's own intentionally-removed field — not a false CAM-579 alarm).
- Story-specific: confirmed the raw-hash approach produces a false positive (main tree's own real schema.prisma vs its own freshly-generated embedded copy differ byte-for-byte due to Prisma's re-formatting, but are identical after the BR-4 normalization) before shipping the normalized version.
- Gate = `/quality-gate` (`npm run lint` · `npm run typecheck` · `npx vitest run` — this story touches scripts/config only, no application code, so coverage is N/A for new production code). Done = merged into `dev`; this PR is NOT self-merged (opened into `dev`, left for review per the dispatch contract).
