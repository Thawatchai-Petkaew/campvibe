## Story
As a **Camper** using the น้องกองไฟ chat assistant, I want each result card's tag badge to reflect what I actually searched for, so that I can trust the badge and quickly tell which camp matches which characteristic while scanning several results.
Why: the owner reported on 2026-07-26 that every result card shows the same badge (`ป่า`) no matter what was searched for — the badge reads the camp's fixed first Terrain-group tag (`options[0]`), a field CAM-547 investigated, confirmed genuinely unreachable from the wire contract, and deliberately left unbuilt (documented as the exact follow-up seam, not faked).
Scope: `lib/ai/tools/search-campsites.ts` (derive the matched tag from the search's own supplied filters, verified against the camp's real MasterData rows) · `lib/read-models/ai-camp-card.ts`/`lib/api-client.ts` (the additive wire field) · `components/ai-chat/AiChatCampCard.tsx` (render `matchedTag` instead of `options[0]`). Does NOT touch `AiChatCardCarousel.tsx` (CAM-547/CAM-569 already settled it), `prisma/schema.prisma` (no schema change — additive TS field only, no migration), `lib/campsite-filters.ts`, or `lib/read-models/camp-card.ts` (the shared catalog select, untouched).
Depends on: CAM-547 (AC-6/BR-7, the investigation this story closes) · CAM-427 (`AiChatCardResponse`/`options[0]`, the field this story does NOT change) · CAM-461 (OR-within-group array semantics for a taxonomy filter, `terrain:["A","B"]`)

## Rules
- BR-1 `matchedTag` is derived ONLY from (a) the taxonomy filter codes the camper's OWN search actually supplied this turn, AND (b) a real, batched read of this specific camp's MasterData rows confirming which of those codes it carries — never inferred from the `where`-clause's own OR-within-group guarantee alone (a card matching `terrain:["RIVE","BEAC"]` is only guaranteed to carry AT LEAST ONE of the two; only a real per-camp read says which) (proves AC-1/AC-3).
- BR-2 Multi-match PRIORITY (highest first, a deliberate editorial order, never data/arrival/DB-return order): **terrain > camperStyle > annotatedFeatures > activities > facilities > access > equipment**. Terrain is the camp's own defining physical character (the same single-descriptor concept the retired fixed badge already used — design continuity); camperStyle is the host's own declared identity, one step less "physical"; annotatedFeatures are a rule/right that can gate whether the camper can even go; activities are what the camper asked to DO there; facilities/access/equipment are logistics/amenities, deliberately least camp-defining. `type` (campSiteType, e.g. GLAMP) is out of this priority list entirely — it is a scalar column matched by equality, not a MasterData `options` relation row, so there is no per-card "does this camp really carry it" fact to verify the way there is for the seven groups above (proves AC-2).
- BR-3 Within a single group's OR-array, the winner is the FIRST code (in the camper's own supplied order) that this camp's real MasterData rows confirm it carries — never the DB/return row order, never a blind `args[0]` (proves AC-3).
- BR-4 The verification read is ONE batched query for the WHOLE page of results (never a per-card query in a loop) — skipped entirely when the search supplied no taxonomy filter at all, so the common free-text/location-only search pays nothing extra (proves AC-4, performance.md no-N+1).
- BR-5 No-match decision (deliberate, not a placeholder): when no supplied filter is confirmed present on a card, `matchedTag` is `null` and the card renders **no badge at all** — it never falls back to the camp's own fixed first Terrain tag. Rationale: a fallback to the fixed tag is indistinguishable from the exact behavior the owner reported as broken (a badge that describes the camp, not the search); rendering nothing is honest, while a plausible-looking invented value is not. The lookup failing outright (e.g. a transient DB error) fails OPEN to the same `null`/no-badge state — the search itself is never blocked by the enrichment step (proves AC-4/AC-5).
- BR-6 `matchedTag` is an ADDITIVE, optional field on `AiChatCardResponse`/`SearchCampsiteCard` (api.md rule 12) — the pre-existing `options` field (the camp's fixed first Terrain tag) is UNCHANGED and still shipped on the wire; only the CARD's badge-rendering source moves off it. `check-availability.ts`/`bulk-availability.ts` (the two other AI tools reusing the same `SearchCampsiteCard` shape) are unaffected — they simply never set `matchedTag`, and the card renders no badge for their results (same as the no-match case).

## Edge cases
- EC-1 IF the search's supplied code does not match this specific card (only possible when the group used an OR-array and the card satisfied a DIFFERENT code in that array) THEN that card's badge shows the code it actually carries, never the searched code it does not have (BR-1/BR-3).
- EC-2 IF a card matches only ONE of the several supplied groups THEN the badge still shows that one group's tag — priority only breaks a tie, it never suppresses the sole match (BR-2).
- EC-3 IF the enrichment lookup itself throws (DB error) THEN every card in that page's results gets `matchedTag: null` and the search still returns its cards — never a rejected/failed turn (BR-5).
- EC-4 IF the search supplies zero result cards (no matches at all) THEN the enrichment lookup never runs (BR-4).
- EC-5 IF `check-availability`/`bulk-availability` reuse the shared card shape THEN their cards simply have no `matchedTag` set and render no badge — no crash, no stale fallback (BR-6).

## Data
- No schema/migration — additive TypeScript fields only: `AiChatCardResponse.matchedTag?: {nameTh,nameEn} | null` (`lib/api-client.ts`), `SearchCampsiteCard.matchedTag?: {nameTh,nameEn} | null` (`lib/ai/tools/search-campsites.ts`). The verification read uses the EXISTING `CampSite.options` (MasterData) relation — no new table/column.

## Seams & refs
- Reuse: the SAME MasterData `options` relation `aiCampCardSelect`/`buildCampSiteWhere` already query (`lib/read-models/ai-camp-card.ts`, `lib/campsite-filters.ts`) — no parallel taxonomy concept introduced. `AiChatCardTag` (`lib/api-client.ts`, already defined for `options`) is reused verbatim for `matchedTag`'s shape — no new type.
- The gap this story closes, precisely (named in CAM-547's Seams & refs as the proposed follow-up): `lib/ai/tools/search-campsites.ts` already builds a `where` clause from the camper's taxonomy args, but the rows it fetched back went through `aiCampCardSelect`'s HARDCODED `where: {group:'Terrain'}, take:1` — it never carried which argument (if any) actually matched a given card. This story adds `deriveMatchedTags` (search-campsites.ts): a second, small, batched `campSite.findMany` scoped to ONLY the codes the camper's own search supplied, confirming per-card which one(s) it really carries.
- Reader/writer sweep (architecture.md 15b) — `SearchCampsiteCard` (the type `matchedTag` was added to) is also imported by `lib/ai/tools/check-availability.ts` and `lib/ai/tools/bulk-availability.ts` (grep: `SearchCampsiteCard` across `lib/ai/tools/*`). Tagged: **NO-CHANGE** — the field is optional, both files continue constructing their cards without it, and their cards simply render no badge (identical to this story's own no-match state) — no edit needed in either file, confirmed by a green `npm run typecheck`.

## Out of scope
- Extending `matchedTag` derivation to `check-availability`/`bulk-availability`'s own card responses (they are not driven by the same taxonomy-filter search args shape) — a future ticket if those surfaces grow a similar badge.
- Including `type` (campSiteType) in the matched-tag priority — it is a scalar equality filter, not a MasterData `options` row (see BR-2); revisit only if `type` itself becomes an `options`-backed field.
- Redesigning the badge's visual treatment (still `Badge variant="secondary"`, same test id `badge--ai-chat-card-tag`) — this story changes the DATA source only.
