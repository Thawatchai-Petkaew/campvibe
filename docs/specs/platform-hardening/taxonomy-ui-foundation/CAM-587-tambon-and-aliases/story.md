# The assistant can search by district, sub-district, and place alias (CAM-587)

## Story
As a **Camper**, I want to ask น้องกองไฟ for camps in a specific อำเภอ (district) or ตำบล (sub-district), or by the common colloquial/nickname name I actually use for a place (e.g. "กรุงเทพ", "ล้านนา", "หัวหิน"), so that my search returns camps that are genuinely in that place — never a coincidental empty result or a silently-wrong province-wide answer.
Why: the tool already accepts `province`/`near`/`region` but nothing reads `district`/`subDistrict`, and camps carry a real `adminAreaId` into a 930-district/7,452-sub-district tree (CAM-553/562) that today's tool never queries. Separately, the owner's 52-province/4-region/22-zone alias dataset (`prisma/data/place-aliases.json`, PR #673) has NOTHING consuming it yet. Building district/sub-district search and alias-consumption as two stories would resolve the same words (a zone alias like "หัวหิน" IS a district) by two different rules that drift apart — exactly what happened to the AdminArea matcher before CAM-566 merged three copies into one; this story does both together, through the ONE shared matcher.
Scope: `searchCampsites` gains `district`/`subDistrict` string args, resolved via CAM-566's shared `matchAdminArea` — never a forked matcher. `place-aliases.json`'s `provinceAliases`/`regionAliases`/`zoneAliases` are wired into province, region, and district resolution respectively (Bangkok's own alias entry is deliberately skipped — see `## Rules` BR-6). District and sub-district are FIRST-CLASS search levels: naming only a district returns every camp in that whole district (not merely a disambiguator narrowing a sub-district lookup). An unresolvable named district/sub-district (or a province supplied only to scope one) returns zero rows honestly — never a silent fallback to a bare province/keyword search (CAM-463 BR-4 precedent). No schema/migration — the data already exists.
Depends on: CAM-566 (shared AdminArea matcher, `lib/geo/admin-area-match.ts`), CAM-553/CAM-562 (Thai admin hierarchy + sub-district backfill), CAM-463 (the honest-empty precedent this story follows), PR #673 (`prisma/data/place-aliases.json`, data only until this story).

## Rules
- BR-1 Precedence (highest wins, decided and pinned by test): `near` (proximity) > `subDistrict` > `district` > `province` > `region`. `near` is a categorically different intent (AROUND, not IN — unchanged from CAM-502/503) and always wins when set. Below `near`: `subDistrict`, when present, wins outright over a bare `district`/`province`/`region` — `district`/`province`, if ALSO given, are consulted only as scoping hints to disambiguate a same-named sub-district, never as a wider filter of their own. `district`, when present (and `subDistrict` absent), wins over `province`/`region` the same way — `province`, if also given, only scopes which district matches. A bare `province` still wins over `region` (unchanged from CAM-463).
- BR-2 Honest failure (proves AC-6): when `district` or `subDistrict` is set and cannot be resolved to a real AdminArea node — OR a `province` supplied alongside it to scope the match cannot itself be resolved — the search returns zero rows directly, without running the candidate query at all. It never falls back to a bare province search, a region search, or a keyword/name-text search. This mirrors the existing CAM-463 BR-4 rule (an unrecognized region never fails validation, it returns zero rows + the assistant's own honest phrasing) applied to the new district/sub-district args.
- BR-3 District/sub-district are resolved through the ONE shared `matchAdminArea` (`lib/geo/admin-area-match.ts`, CAM-566) — bilingual (Thai or English), exact-match only (never a substring match on the administrative name itself — the DEF-1/DEF-2 Thai-substring-collision lesson). A district match includes every sub-district beneath it (a camp's stored `adminAreaId` may point at the deeper sub-district level, the same "deepest resolved level" convention `resolveProvinceAdminAreaIds` already documents for the province case).
- BR-4 `place-aliases.json` is consulted at the level of an ALREADY-ISOLATED tool-argument value (the model already decided this specific word names a place) — never as a free-text scanner over a whole sentence. Each alias's `matchMode` (`exact`/`substring`) is honored exactly as authored. `contextGuard` is NOT separately enforced at this layer: it exists to gate a free-text scanner against an ordinary sentence merely containing the word (see `lib/ai/place-resolver.ts`'s `CONTEXT_GUARDED_LANDMARK_NAMES_TH`), and there is no such surrounding sentence here — the model placing the word into a place-typed argument already IS the place context, the same reasoning `lib/thai-regions.ts`'s own `REGION_ALIASES` table relies on for its own isolated-word, no-`contextGuard` design.
- BR-5 `zoneAliases` entries (e.g. หัวหิน, หาดใหญ่) ARE districts (the file's own framing) and are resolved through the exact same district match BR-3 describes — never a second, parallel "zone" lookup. When a zone alias also names its own province and none was separately supplied, that province is used only as a best-effort scoping hint (a failed lookup there never blocks the district match itself).
- BR-6 Known, deliberate collision left unresolved by this story: the data file's own note flags "เมืองเพชร" as colloquially used for BOTH Phetchaburi (the mapped value) and Phetchabun; this story accepts the data file's own choice (Phetchaburi) without adding a disambiguation mechanism — no evidence yet justifies the added complexity. Separately, Bangkok's own alias entry (`canonicalCode "10"`) is SKIPPED by this story's province-alias consumption: Bangkok is already fully handled by the pre-existing, tested `BANGKOK_ALIASES` map (CAM-458), and wiring the alias file's own "บางกอก" (substring mode) would newly match "บางกอกน้อย" — a real, DIFFERENT Bangkok district name that happens to start with "บางกอก" — the same substring-collision risk this codebase has been bitten by before (DEF-1/DEF-2). Retiring `BANGKOK_ALIASES` in favor of the alias file (with a real disambiguation guard for that case) is a deliberate follow-up (see `## Out of scope`), not silently done here.

## Edge cases
- EC-1 IF `subDistrict` is set together with `district` and/or `province` THEN the district/province are used ONLY to scope which sub-district matches (disambiguating a same name under a different district/province) — never combined into a wider filter, never a fallback when the sub-district itself fails to resolve (BR-1/BR-2).
- EC-2 IF only `district` is set (no `subDistrict`) THEN every camp in that district — across all of its sub-districts — is returned; a `province` given alongside it only scopes WHICH district matches, it does not narrow the result further (BR-1/BR-3).
- EC-3 IF an alias (province/region/zone) does not match any known entry THEN the raw value passes through unchanged to the existing (pre-CAM-587) resolution path — byte-identical to before this story for every word the alias file does not cover (BR-4).
- EC-4 IF a named district/sub-district cannot be resolved, or the province supplied to scope it cannot be resolved THEN the search returns zero rows without running the candidate query — never a partial/best-guess match (BR-2).
- EC-5 IF `near` is set together with `district`/`subDistrict` THEN `near` wins outright (unchanged proximity-first rule from CAM-502) — the district/sub-district args are not consulted at all this turn (BR-1).

## Data
No schema/migration — `AdminArea` (930 districts, 7,452 sub-districts, CAM-553/562) and `prisma/data/place-aliases.json` (PR #673) both already exist; this story only adds two optional string args to the `searchCampsites` tool's existing zod schema and consumes the alias file at runtime (same "committed JSON, no DB table" pattern as `landmark-gazetteer.json`/`province-centroids.json`).

## Seams & refs
- Reuse: `matchAdminArea`/`lib/geo/admin-area-match.ts` (CAM-566) — the ONE district/sub-district matcher, extended with a new `listChildAdminAreaIds` helper (a district's own sub-district subtree) rather than a second hand-rolled subtree walk. `resolveProvinceForSearch`/`resolveRegionForSearch` (existing, unchanged signatures) still own province/region resolution; this story layers alias-normalization ahead of them via a new `lib/ai/place-aliases.ts`, never forking either resolver. `lib/campsite-filters.ts`'s `buildCampSiteWhere`/`resolveProvinceAdminAreaIds` are reused unchanged (out of this story's file surface) — the district/sub-district id-set is ANDed onto its output the same way the existing `near` geo-path already ANDs its own bbox clause on, never a parallel where-builder.
- Refs: CAM-566 tech.md (the shared matcher's own consolidation rationale); CAM-463 story.md BR-4 (the honest-empty precedent this story extends to district/sub-district); `docs/reference/place-aliases-fill-guide.md` (the alias dataset's own authoring contract, referenced for `matchMode`/`contextGuard` semantics).

## Out of scope
- A deterministic free-text pre-pass hint for district/sub-district (mirroring `lib/ai/place-resolver.ts`'s existing province/region/landmark hints, which defend specifically against the CAM-500 terrain-anchoring regression) — the model relies on the tool's own `jsonSchema` description for these new args, the same way `near`'s landmark-without-proximity-word case already works today with no pre-pass of its own. Follow-up only if evals show a systematic miss → a new CAM ticket.
- Retiring the hardcoded `BANGKOK_ALIASES` map in favor of `place-aliases.json`'s own (superset) Bangkok entry, with a real disambiguation guard for the "บางกอกน้อย" collision (BR-6) → a follow-up CAM ticket once a guard design exists.
- A code-level disambiguation mechanism for the "เมืองเพชร" (Phetchaburi vs Phetchabun) collision (BR-6) — no evidence yet that this miss is real/frequent enough to justify one.
