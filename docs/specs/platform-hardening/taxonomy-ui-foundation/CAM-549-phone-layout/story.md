## Story
As a **Camper** browsing CampVibe on my phone, I want the page to never scroll sideways and only the search bar to stay pinned while I scroll, so that the layout reads as intentional chrome instead of a rendering bug.
Why: owner-reported (2026-07-26, testing on a real phone) two live defects: (1) the navbar's right-side icon row runs past the right edge of the screen, causing the whole page to scroll horizontally and clip content at the left edge; (2) scrolling leaves a second, unintended sticky element (a ~14px sliver of `CategoryBar` peeking out from behind the taller mobile navbar) alongside the search bar.
Scope: `components/Navbar.tsx` (the shared navbar + its mobile search row) and the `CategoryBar` sticky wrapper in `app/page.tsx`. No change to `CategoryBar.tsx` itself (CAM-552 just tuned its mobile scale) and no change to desktop (`md:` and above) behavior, which was not reported broken and measured correct before this fix.
Depends on: CAM-552 (mobile scale/breakpoint) — rebased on top of it.

## Rules
- BR-1 Mobile-first, single breakpoint (`md` = 768px, per `DESIGN.md` §2.0) — no `sm:`/`lg:`/`xl:` introduced for layout/scroll behavior in this fix.
- BR-2 The 44px touch-target floor is never reduced to buy horizontal space — every existing control (wishlist `w-11 h-11`, notification bell `h-11 w-11`) keeps its height; only horizontal gutter/gap is compacted (`px-6`→`px-4 md:px-6`, `gap-4`→`gap-3 md:gap-4`), per `DESIGN.md` §2.0's compaction budget ("padding, gaps, section rhythm… never a tap target").
- BR-3 Owner-authorized drop order: the language switcher is the ONLY nav item removed from the mobile row (AC-2); no other icon (wishlist, notifications, profile menu) is hidden or removed — dropping further items is out of this ticket's authorization.
- BR-4 The sticky search-bar element must be a DOM sibling of `<nav>` (not nested inside it) so its containing block is tall enough to keep it pinned for the entire scroll, not just for the height of `<nav>` itself (see Seams & refs — root cause of the "stuck for 80px then unstuck" failure mode found while building the fix).

## Edge cases
- EC-1 IF the viewport is exactly at the classic 320px width (iPhone SE 1st-gen class) THEN a residual ~15px of horizontal overflow remains, traced to the SAME profile-menu button already tracked as under the 44px floor in CAM-558 (measured: `p-1 pl-3` avatar+hamburger button, ~78px wide, ~42px tall) — fixing it further would mean resizing a CAM-558-owned element or dropping a second nav item beyond the owner's named casualty (BR-3); flagged as a known, narrow residual for CAM-558 or a follow-up, not silently claimed as fixed. All realistic modern phone widths (360–428px) measure 0px overflow.
- EC-2 IF the camper is logged out THEN the navbar was already not overflowing (no wishlist/notification icons render) — AC-1/AC-2 still hold trivially (fewer icons than the logged-in worst case).
- EC-3 IF the camper is on a desktop-width viewport THEN the language switcher stays visible (AC-2 is mobile-only) and both sticky bars behave exactly as before this fix (AC-4).

## Data
- No schema/data change. Pure client-side layout/CSS fix in `components/Navbar.tsx` and `app/page.tsx`. Migration: none.

## Seams & refs
- Reuse: `components/CategoryBar.tsx` is NOT modified — CAM-552 just tuned its mobile tab gap/gutter; this story only changes the STICKY WRAPPER around it in `app/page.tsx`, leaving the component itself untouched.
- Root cause 1 (horizontal overflow, AC-1): measured in a real Chromium browser at 390px width, logged in — `document.documentElement.scrollWidth` = 422px vs `clientWidth` = 390px (32px overflow). The overflowing element was the navbar's right-side icon row (`div.flex.items-center.gap-2.flex-shrink-0`), specifically its rightmost child, the profile/hamburger menu button, whose right edge sat at x=422 (32px past the viewport). The row does not wrap (`flex … justify-between`, both flex children `flex-shrink-0`) and its total content width (logo + gap + language-switcher + wishlist + notification-bell + profile-menu, each with `gap-2`/`gap-4` between) exceeded the available content width (`viewport − 2×px-6 gutter`) once a camper is logged in. `px-6` (24px/side) was also a `DESIGN.md` §2.0 non-compliance on its own — the documented "page/bar gutter" role is `px-4` mobile / `md:px-6` desktop, and this navbar hard-coded `px-6` at every width.
- Root cause 2 (two sticky bars, AC-3): `CategoryBar`'s wrapper in `app/page.tsx` used `sticky top-20` (assuming an 80px navbar) unconditionally. That assumption is only true at `md:` and above — on mobile, `<nav>` was taller (~151px measured: the 80px title row PLUS the mobile-only search row below it, both inside one `sticky top-0` `<nav>`), so `CategoryBar`'s wrapper stuck at `top:80px`, landing BEHIND the taller navbar (`z-40` vs the navbar's `z-50`) for most of its height, with only a ~14px sliver (its own bottom border/padding) visible below the navbar's bottom edge — the "stray line" the owner reported.
- Root cause 2, attempt 1 (documented so it is not re-tried): first tried keeping the mobile search row nested inside `<nav>` and just adding `sticky top-0` to it directly. This stuck for only the first ~80px of scroll then detached and scrolled away — CSS `position: sticky` can only stay pinned while its **containing block** (here, `<nav>`, only ~160px tall) still has room; once `<nav>`'s own bottom edge scrolls past the pinned offset, a sticky child bound to that small parent is dragged away with it. Fix: moved the mobile search row to be a DOM SIBLING of `<nav>` (both returned from the same `<>` fragment in `Navbar.tsx`, so React renders them as siblings under `app/page.tsx`'s `<main>`) — its containing block is now the whole page, tall enough to keep it pinned for the entire scroll (BR-4).
- Refs: — (no ADR; a scoped layout/CSS bugfix, no data-model or contract change).
- CAM-558 (touch-target floor, not fixed here): the profile-menu button (measured ~42px tall) and the logo link (measured ~32px tall) both remain under the 44px floor after this story — unchanged by this fix, still tracked there. The language switcher's own CAM-558 entry (36px tall) is narrowed by this story: it no longer renders at all on mobile (AC-2), so its touch-target violation only exists at `md:` and above going forward — noted for CAM-558 to re-scope.

## Out of scope
- Fixing the CAM-558 touch-target violations (profile menu, logo link, language switcher at desktop width) — tracked there, not this ticket.
- Closing the residual ~15px overflow at the 320px viewport (EC-1) — would require either resizing the CAM-558-owned profile-menu button or dropping a second nav item beyond the owner's named casualty; flagged, not fixed, pending an owner decision.
- Any change to `CategoryBar.tsx`'s own markup/scale (CAM-552's work) — only its sticky wrapper in `app/page.tsx` changed.
- A JS-driven "collapse on scroll" navbar (shrinking/animating the title row away) — the CSS-only sibling-sticky approach achieves the same visible result (only the search bar remains) with no new JS/state.
