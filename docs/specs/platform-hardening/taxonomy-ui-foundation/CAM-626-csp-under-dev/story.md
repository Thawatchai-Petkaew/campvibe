## Story
As the **Host**, I want CAM-607's CSP-nonce propagation to hold under `next dev` — the mode the regression suite runs against and every developer works in all day — not only under a production build, so that the streaming-relocation defect CAM-604 found does not quietly persist in the one environment nobody re-checked.
Why: CAM-607 was verified only under a production build under CPU-pressure fault injection, because that is where the defect had been observed; `next dev` was never in scope. CAM-621, while measuring e2e-suite stability, found the suite green 29/29 in CI but 2 FAILED of 3 local CI-faithful runs (fresh seed, `workers:1`) — both carrying the duplicate-DOM signature — and refused to flip the suite to blocking on that contradiction.
Scope: determine whether CAM-607's fix (the enforced CSP set on the request headers, not only the response) actually holds under `next dev`, and if the duplicate-DOM signature still reproduces there, root-cause it — not assume it is the same mechanism. No schema/migration, no new endpoint/UI. Touches `proxy.ts`/`app/dashboard/loading.tsx`/`next.config.*`/`lib/auth.config.ts` only if the investigation finds something to fix there.
Depends on: CAM-607 (the fix under investigation) · CAM-604 (found + root-caused the original defect under production) · CAM-608 (independently observed the same DOM signature recurring on `dev`, against both the fixed and unmodified code, and correctly left it unfixed as out of its own surface) · CAM-621 (measured the local-vs-CI contradiction this ticket exists to close)

## Rules
- BR-1 The investigation is evidence-first (per `.claude/rules/code.md`'s "measure, don't reason" lesson): every claim about dev-mode behavior is backed by a real, run-and-recorded `next dev` reproduction (Playwright against a real dev server), never inferred from reading source alone. (proves AC-1/AC-2)
- BR-2 No CSP directive is loosened, and no code changes in `proxy.ts`/`app/dashboard/loading.tsx`/`next.config.*`/`lib/auth.config.ts` are made unless the investigation finds an actual defect in one of them — a "does not need fixing" finding, honestly reported, is a complete, acceptable answer (per the ticket's own instruction). (governs the whole story)
- BR-3 A regression guard is added (unit + e2e) asserting the request-header CSP-propagation fix is NOT gated behind any `NODE_ENV`/dev conditional, and that any transient streaming container resolves within a bounded time rather than staying permanently stuck — so a FUTURE change that re-introduces a dev-only (or prod-only) skip of the fix is caught automatically. (proves AC-1/AC-2 stay proven going forward)

## Edge cases
- EC-1 IF a future edit special-cases the request-header CSP propagation behind `NODE_ENV === 'development'` (or any other mode conditional) THEN the fix would silently stop propagating in exactly one mode again — guarded by a source-inspection test asserting the fix line sits outside any such conditional block.
- EC-2 IF the transient streaming-container window is ever unbounded (never resolves) under `next dev` THEN that would be a regression of the ORIGINAL pre-CAM-607 defect (a permanently CSP-blocked script) — guarded by an e2e assertion with a bounded wait (3s), which fails loudly if the container never clears, and passes if it clears within the bound (the harmless, current, correct behavior).
- EC-3 IF a spec in `e2e/regression/` needs its OWN assertion changed to pass (e.g. `cam-540-dialog-select-dismiss.spec.ts` or `ac6-spot-lifecycle.spec.ts`) THEN that is reported as a finding, not silently fixed — those files are outside this story's allowed surface; see `tech.md`'s recommendation for their owner instead.
- EC-4 IF the redirect-to-login branch in `proxy.ts` were reordered relative to the request-header CSP set THEN authz could be affected by an unrelated propagation change — guarded by re-running the existing `isRouteAllowed()` ordering test (`__tests__/cam-607-csp-request-header.test.ts`) unmodified, plus this story's own route-protection assertion.
