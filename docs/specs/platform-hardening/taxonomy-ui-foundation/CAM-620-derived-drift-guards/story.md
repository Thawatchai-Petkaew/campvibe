# Two more derived files can go stale with nothing watching (CAM-620)

## Story
As the **Admin** (the person who re-runs `scripts/build-province-centroids.mjs` / reseeds `prisma/data/thailand-locations.json` before a release train), I want three separate, cheap signals — one that actually runs the alias validator that already exists, one that tells me on demand whether the committed province-centroid file still matches the live camp distribution, and one that tells me whether the AdminArea province/district rows still match the committed seed file — so that a stale derived artifact produces a visible signal instead of a silent wrong answer that looks exactly like the system working (CAM-605's own opening line, extended to two more artifacts and one dead validator).
Why: CAM-605 built exactly this mechanism for the sub-district shortlist and closed it as Done; this ticket is its two missing siblings plus one validator CAM-605 itself named as a sibling of the ALREADY-wired `validate-landmark-gazetteer.mjs` but never wired.
Scope: (1) wire `scripts/validate-place-aliases.mjs`'s already-exported, already pure `validatePlaceAliases` into `npm test` via a real-data assertion, mirroring `__tests__/cam-503-landmark.test.ts` exactly — zero DB, zero new code in the validator itself. (2) a new `scripts/check-province-centroid-drift.mjs` that recomputes each province's live mean camp coordinate and diffs it against the committed `prisma/data/province-centroids.json`, reporting a province that newly qualifies for a centroid but has no committed key (`added`), a committed province whose live camp count has dropped below the sparse floor (`removed`), and a province present on both sides whose centroid has moved more than a tolerance (`shifted`) — read-only, never regenerates the file. (3) a new `scripts/check-adminarea-drift.mjs` that diffs `prisma/data/thailand-locations.json`'s PROVINCE/DISTRICT-level `code`/`nameTh`/`nameEn` against the live `AdminArea` table, naming any code missing on either side or any code present on both sides with a different name. All three follow CAM-605's decided shape: manual `check:*` scripts (not CI-blocking, no DB in `quality-gate`), a non-blocking report-mode ride-along warning appended to `scripts/db-sync-from-staging.mjs`'s existing success path for the two DB-backed checks, and SKIP (never crash, never false-pass) when `DATABASE_URL` is absent or unreachable.
Depends on: CAM-605 (the mechanism/shape this story reuses) · CAM-600 (`build-province-centroids.mjs`, `thailand-locations.json` as seed source) · CAM-553 (the AdminArea/thailand-locations.json seed pipeline).

## Rules
- BR-1 `validatePlaceAliases` (already exported, already pure, `scripts/validate-place-aliases.mjs`) is asserted against the real committed `place-aliases.json` + `thailand-locations.json` inside `__tests__/cam-620-place-aliases-wired.test.ts`, the same convention `__tests__/cam-503-landmark.test.ts` already uses for `validateGazetteer` — zero lines changed in `validate-place-aliases.mjs` itself (its rules are out of scope; see story's own header comment "Sibling of validate-landmark-gazetteer.mjs").
- BR-2 `scripts/check-province-centroid-drift.mjs` imports `computeCentroids` + `MIN_CAMPS_FOR_CENTROID` (both already exported, pure, no I/O) directly from `scripts/build-province-centroids.mjs` rather than re-deriving the mean-computation math — that file is out of this story's editable file surface, so it is imported read-only, never modified. Only the trivial Prisma query that produces the raw camp rows (inline in that file's own `main()`, not itself exported) is mirrored/duplicated here, with a cross-reference comment naming the accepted, bounded duplication risk — the same shape CAM-605 used for `lib/ai/place-resolver.ts`'s guard constants (BR-2 there).
- BR-3 The centroid diff is three-way, not two-way (unlike CAM-605's boolean membership diff), because a centroid is a continuous mean, not a yes/no fact: `added` (live-qualifying, no committed key — the exact "falls back to exact-province filter with no proximity behavior and no error" consequence the ticket names), `removed` (committed key, live camp count now below `MIN_CAMPS_FOR_CENTROID`), `shifted` (present on both sides, haversine distance between the committed and live centroid exceeds `CENTROID_DRIFT_THRESHOLD_KM`).
- BR-4 `CENTROID_DRIFT_THRESHOLD_KM = 5` — a first-cut, explicitly tunable report-mode threshold (documented in tech.md), chosen so an organic mean-shift from ordinary catalog growth (a few new camps near the existing cluster) does not fire, while a real cluster move (a coordinate-correction backfill, a whole new region of camps) does. Never used to block anything; tuning it is a cheap, no-migration follow-up.
- BR-5 `scripts/check-adminarea-drift.mjs` diffs `thailand-locations.json`'s PROVINCE + DISTRICT level entries (by `code`) against a fresh `prisma.adminArea.findMany` at those two levels — `missingLive` (a committed code the live table has never seeded), `missingCommitted` (a live code the current file no longer lists), `renamed` (a code present on both sides where `nameTh` or `nameEn` differs). SUBDISTRICT level is explicitly out of scope (CAM-605 already covers it).
- BR-6 Both new DB-backed checks: `DATABASE_URL` unset → named SKIP notice, exit `0` (not a pass). `DATABASE_URL` set but the connection/query throws → the same SKIP treatment, exit `0`, no partial/garbled diff. A real, actionable difference (any of the three/three categories non-empty) → every name printed, exit `1` — the only path that exits non-zero. Exactly CAM-605's BR-3/BR-4/BR-5 shape, applied to two more artifacts.
- BR-7 Neither new check is wired into `.github/workflows/ci.yml`'s `quality-gate` job (no Postgres service/`DATABASE_URL` there, confirmed the same way CAM-605's tech.md confirmed it) — manual `check:*` scripts only (`npm run check:province-centroid-drift`, `npm run check:adminarea-drift`), same cadence as the generators/seed they check (before a release train, or after a host-onboarding batch). Report-mode (`.claude/rules/ops.md` "report-mode → clear the backlog to 0 → flip to blocking") — flipping either to blocking is an explicit, separate follow-up decision.
- BR-8 Both new checks additionally ride along `scripts/db-sync-from-staging.mjs`'s existing success path (the moment real, current camp/AdminArea data most recently lands in the local dev DB) — a non-blocking, own-try/catch warning per check, reusing this story's own exported `computeCentroidDrift`/`computeAdminAreaDrift` with no edit to either check script's exit codes/logic. A finding, or a failure to check at all, never sets `db-sync-from-staging.mjs`'s own `process.exitCode` (mirrors CAM-605 BR-7 exactly).
- BR-9 This story is detect-only for all three items — `prisma/data/province-centroids.json`, `prisma/data/thailand-locations.json`, and the live `AdminArea` table are never written to by any file this story touches. If the real dev-DB run below finds drift, that count is reported honestly in the PR, never silently corrected here (CAM-605's own "Out of scope" precedent; a regeneration is its own follow-up story with its own verification, since regenerating `province-centroids.json` changes real proximity-sort results).

## Edge cases
- EC-1 IF a future `place-aliases.json` edit adds a `canonicalCode` absent from `thailand-locations.json` THEN `npm test` fails naming the bad reference (BR-1, proven with a constructed fixture, not only the real file).
- EC-2 IF a province's live camp count crosses `MIN_CAMPS_FOR_CENTROID` but has no committed key THEN it is named under `added` and the command exits `1` (BR-3).
- EC-3 IF a committed province's live camp count drops below `MIN_CAMPS_FOR_CENTROID` THEN it is named under `removed` (BR-3).
- EC-4 IF a province present on both sides has moved more than `CENTROID_DRIFT_THRESHOLD_KM` THEN it is named under `shifted` with the distance; IF the move is at or below the threshold THEN it is NOT reported (a small, organic shift is not actionable drift — mirrors CAM-605 EC-4's "a difference that is deliberate").
- EC-5 IF the committed and live centroid facts agree (within tolerance) and cover the same province set THEN the command exits `0` with an explicit "0 drift" line — never a bare silent exit.
- EC-6 IF `DATABASE_URL` is empty/unset THEN neither new check constructs a Prisma client at all and exits `0` with a named SKIP notice; IF it is set but the query throws THEN the same SKIP notice fires with the same exit code, no partial output (BR-6).
- EC-7 IF a PROVINCE/DISTRICT `code` exists in the committed file with a different `nameTh`/`nameEn` than its live `AdminArea` row THEN it is named under `renamed` and the command exits `1` (BR-5).
- EC-8 IF every committed PROVINCE/DISTRICT code+name matches its live row exactly THEN the command exits `0` with an explicit "0 drift" line.
- EC-9 IF a ride-along check (inside `db-sync-from-staging.mjs`) itself throws (e.g. a malformed JSON file) THEN the sync still reports success and its own exit code is unaffected — only a non-blocking warning is printed, never a build/sync failure (BR-8).

## Out of scope
- Regenerating/correcting `prisma/data/province-centroids.json` or re-seeding `AdminArea` from `thailand-locations.json` — this story detects drift, it does not fix it (BR-9). A non-zero real-DB finding is reported honestly in the PR; fixing it (if the owner wants it fixed) is its own follow-up story with its own verification, exactly as CAM-605 found drift and CAM-606 fixed it as a separate story.
- SUBDISTRICT-level AdminArea drift — CAM-605 already covers it; this story is PROVINCE/DISTRICT only (BR-5).
- Wiring either new check into CI as blocking or advisory — `quality-gate` has no DB service at all (same fact CAM-605's tech.md already confirmed); a follow-up ticket only if the owner wants a scheduled (not per-PR) job with its own seeded-from-a-real-snapshot DB.
- Changing `validate-place-aliases.mjs`'s own validation rules — out of scope; this story only wires its already-correct, already-exported validator into a test (BR-1).
- A ride-along site other than `scripts/db-sync-from-staging.mjs` (e.g. `promote-release`) — CAM-605's tech.md already evaluated and rejected `promote-release` as a ride-along site for the same structural reason (a documented workflow, not a single running process with a resolved local DB connection); unchanged here.
