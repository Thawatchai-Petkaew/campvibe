# AI Camping Assistant (A1-A4, B1-B3, C·Inquiry)

## Overview
A conversational assistant over CampVibe's own data: campers ask camping questions in natural language and get answers as clickable campsite cards, backed by live availability. Serves campers (discover + decide) and, later, hosts (inquiry handoff). ↑ Master-Plan: `docs/project/master-plan.md` · roadmap item: `docs/project/ai-product-roadmap.md` (AI-1/2/3, train M2).

## Architecture overview
- Entities: no new entity — reuses `CampSite`/`Spot`/`Booking`/`BlockedDate`/`InternalHold`/`Location`/`MasterData` joined by ID at question time. The normalized schema stays the single source of truth (ADR-009: no merge, no warehouse, no embeddings in v1).
- API surface: a read-only tool layer (`searchCampsites`, `checkAvailability`) invoked by function-calling; a single-turn chat endpoint (CAM-271), whose success body extends by addition to `{ answer, cards, suggestions }` at CAM-410 (optional follow-up chips). Availability is always a live query.
- ADRs: `docs/adr/ADR-009-ai-assistant-data-architecture.md` (+ `ADR-011` amendment: C-cluster → HostLead, deferred in the POC) · schema: `prisma/schema.prisma`.

## Design overview
Discover-only chat surface — a floating entry + a home entry; in-chat cards reuse `components/CampgroundCard` and link to `/campgrounds/[slug]`. Tokens + states per `DESIGN.md`; loading/empty/error states per `.claude/rules/loading.md`. Follow-up suggestion chips (CAM-410) reuse the existing welcome-pill visual + send path.

## Appetite
POC budget: G1 (scope) + G2 (spend approval) owner review-rounds; model spend gated to owner-key-only with `max_tokens` + single-round + per-IP rate-limit caps. Blowing the appetite means cutting scope (fewer tools / no live calls), not extending.

## No-gos
No DB merge / warehouse / sync pipeline; no embeddings or vector store in v1; no text-to-SQL; no write path from the model (read-only tools only); no HostLead / booking write in the POC; no multi-turn agent loop or streaming in the foundation story; no second (paid) model call to generate follow-up suggestions (CAM-410 rides the same single completion).

## Live status
Rollup lives on `/status` + `docs/specs/INDEX.md` (generated by `node scripts/ticket-sync.mjs index`) — not hand-maintained here.

## Key decisions
- Tool-use over the normalized DB, not RAG/embeddings/text-to-SQL (ADR-009).
- Availability is always a live query — never cached/embedded — to avoid stale double-booking answers.
- OpenRouter (owner's key) as the model gateway; spend owner-gated at G2.
- POC ends the funnel at the campground page; HostLead handoff waits on HostOS M1.2 (ADR-011).
- Follow-up suggestions are generated in-band (one completion) and sanitized as untrusted model output (CAM-410).
