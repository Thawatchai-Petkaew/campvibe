# Assistant answers stream in word by word (CAM-412)

<!-- Gate class: FULL spec-first (ops.md Gate v2) — a NEW response contract (a streaming `text/event-stream` variant of POST /api/ai/chat) never qualifies for spec-lite. Spec authored FIRST on this branch; spec + code land in the same PR into dev. -->

## Story
As a **Camper**, I want the assistant's answer to appear progressively as it is written instead of waiting for the whole reply, so that I see the answer starting within a moment on the ~3-5s turn rather than staring at a typing dot for the full wait (lower perceived latency in the guest Discover funnel, not measured).
Why: the model turn takes ~3-5s end to end today; streaming the final answer text cuts time-to-first-visible-text without adding a model call — the same single turn, delivered progressively.
Scope: stream ONLY the final answer text of `POST /api/ai/chat` progressively; the tool round stays non-streamed; cards + follow-up chips arrive together in one terminal structured event after the text. The existing non-streaming JSON response stays byte-stable and is the automatic fallback. No new model call, no schema, no persistence, no new dependency.
Depends on: CAM-271 (chat endpoint contract this extends) · CAM-270 (single-round turn + spend guard) · CAM-405 (plain-text-only answer) · CAM-406 (dev server survives a client abort — the abort safety net) · CAM-409 (in-chat card carousel) · CAM-410 (suggestions extraction, reused verbatim).

## Rules
- BR-1 Streaming is OPT-IN by content negotiation, additive and backward-compatible (api.md §12): a request carrying `Accept: text/event-stream` from a client that supports response-body streaming gets a streamed response; every other request (Accept absent or `application/json`, and every older client) gets the existing JSON body `{ answer, cards, suggestions? }` byte-for-byte unchanged. The URL and method are unchanged. (proves AC-1, AC-3)
- BR-2 Guard order is unchanged and runs BEFORE any commitment to streaming: per-IP rate limit FIRST (`429` `rate_limited` + `Retry-After`), then zod caps (`400` `invalid_request`), then the key check (`503` `assistant_disabled`) — each as a normal HTTP status + code, never a streamed `200`. The `text/event-stream 200` headers are committed only once the first cleaned text delta is ready; ANY failure before the first delta (including a model call that fails on both primary and fallback) returns the existing JSON status + code, so a client that requested streaming falls back automatically by reading the response `Content-Type`. (proves AC-3, AC-5, AC-6, EC-3, EC-4)
- BR-3 Only CLEANED answer text is ever streamed. The `<suggestions>[...]</suggestions>` tail block is NEVER emitted as delta text — the server withholds a trailing buffer large enough to detect a suggestions delimiter that may be split across chunks, and parses suggestions from the FULL buffered completion using the existing `extractSuggestions` (lib/ai/openrouter-client.ts) — no parallel parser. Cards + suggestions are delivered only in the terminal `meta` event, after the last text delta. (proves AC-1, AC-2, EC-2)
- BR-4 Event framing (SSE-style over a `ReadableStream`): zero-or-more `delta` events (each carries only cleaned text) → exactly one terminal `meta` event `{cards, suggestions}` (cards ≤10 from the single tool round; suggestions ≤3, each server-sanitized) → one `done` event. A mid-stream failure (after ≥1 delta) emits a terminal `error` event carrying a stable code (`assistant_error`) and no `done`; the client discards any partial answer and shows the error notice + retry. Cards + chips render together only at stream end (never before or during the text) so the layout settles once (protects CLS). (proves AC-1, AC-4)
- BR-5 All spend + prompt-injection guards are UNCHANGED: exactly ONE tool-call round (the tool round stays non-streamed), MAX_TOKENS = 680, per-input sanitize + `<user_message>` DATA wrap, and per-suggestion server-side sanitize before the `meta` event. Streaming introduces NO new model call and NO second paid round. (proves AC-1, AC-2)
- BR-6 On a client abort (panel closed / navigation / reader cancel), the client aborts the fetch and the server propagates that abort to the upstream OpenRouter stream so the paid generation is torn down (spend bounded — no continued billing) and the `ReadableStream` is cancelled. The abort is a clean no-op that never crashes the dev server (the CAM-406 `uncaughtException` guard remains the safety net). A second/duplicate abort is idempotent. (proves AC-7, EC-6)
- BR-7 Exactly one turn streams at a time: while a stream is in flight (`sending` = true) the composer, send button, and chips are disabled and any new send is ignored by the existing in-flight guard (use-ai-chat.ts) — there is never more than one concurrent stream and never a duplicate user bubble. (proves AC-8, EC-7)
- BR-8 The visible answer grows as deltas append; a streaming affordance (a caret / the existing typing indicator) shows until `done`; under `prefers-reduced-motion` there is NO per-character cosmetic animation (the text still appends, just without the effect). The `aria-live` log announces the SETTLED answer once (not per-delta) to avoid flooding a screen reader. NO new fixed Thai copy is introduced — every state reuses the existing `aiChat` i18n keys (`typing` / `error` / `rateLimited` / `disabled` / `retry`). (proves AC-1, AC-4)

## Edge cases
<!-- cover: invalid · empty/zero · concurrent/duplicate · permission · boundary. -->
- EC-1 IF the model fails mid-stream (after ≥1 delta) THEN the partial answer is discarded, a terminal `error` event (`assistant_error`) is emitted, and the camper sees `ผู้ช่วยขัดข้อง กรุณาลองใหม่อีกครั้ง` + `ลองใหม่` (BR-4)
- EC-2 IF the `<suggestions>` delimiter is split across two text chunks THEN the withheld tail buffer stops any partial delimiter from ever reaching the camper, and suggestions still parse correctly from the full buffered completion (BR-3)
- EC-3 IF the IP is over the rate limit THEN a normal `429` `rate_limited` + `Retry-After` is returned before any paid call and before any stream header — never a streamed 200 (BR-2)
- EC-4 IF `OPENROUTER_API_KEY` is unset THEN the turn self-skips (no network) and a normal `503` `assistant_disabled` is returned with no stream started (BR-2)
- EC-5 IF a streamed frame cannot be parsed (malformed / undecodable) after the stream has started THEN it is treated as a stream failure and the turn resolves to the error notice + retry `ผู้ช่วยขัดข้อง กรุณาลองใหม่อีกครั้ง` — the camper never sees raw frame text; a failure BEFORE the first delta instead returns the JSON path (BR-2, BR-4)
- EC-6 IF the panel is closed (or the request aborted) while a stream is in flight THEN the client aborts the fetch, the server tears down the upstream OpenRouter stream (no extra billing), a second/duplicate abort is a no-op, and the dev server never crashes (BR-6)
- EC-7 IF the camper tries to send a second message or tap a chip while a stream is in flight THEN the in-flight guard ignores it — only one stream runs at a time, no duplicate user bubble (BR-7)

## Data
- No schema change, no migration, no persistence. Transport-only: a new streaming media-type variant (`text/event-stream`) of the existing `POST /api/ai/chat`, framed as SSE-style events over a `ReadableStream` — `delta` `{ text: string }` (cleaned prose only) · `meta` `{ cards, suggestions }` · `error` `{ code: string }` · `done`. The existing JSON body `{ answer, cards, suggestions? }` is unchanged and is the fallback. Client streaming-answer state is in-memory only (a transient "streaming" chat entry that finalizes into the existing answer entry carrying cards + suggestions). All payloads are Public, plain-text/structured Pixels — no PII/Financial/Geo data. migration: none.

## Out of scope
- Streaming the TOOL round / an interim "กำลังค้นหา…" progress status → deferred; the tool round stays non-streamed and cards arrive with the `meta` event (propose a follow-up only if the wait proves noticeable).
- Streaming cards progressively (card-by-card before the text ends) → out of scope; cards render once at stream end (ratified UX, settles layout once).
- Server-side conversation persistence or resuming an interrupted stream → out of scope (stateless POC per CAM-271).
- Adding any new dependency (an SSE/eventsource parser library) → out of scope; a `ReadableStream` + a small hand-parser only. If the architect finds a parser genuinely necessary, that is a G2 stop-and-ask, not this story.
- Real OpenRouter paid spend in tests → all tests MOCK the client / `fetch` (zero real spend); the progressive visual is owner-verified in a real browser.
