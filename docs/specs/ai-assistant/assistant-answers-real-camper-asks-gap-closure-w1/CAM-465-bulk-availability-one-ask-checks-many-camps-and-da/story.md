## Story
As a **Camper**, I want to ask น้องกองไฟ one question that checks many camps across several dates at once (`มีลานไหนว่างวีคเอนด์เดือนนี้`, `ถูกสุดที่ยังว่างเสาร์นี้`), so that I see in one answer which camps are free for which dates instead of asking camp-by-camp (epic KPI = 40-case golden pass-rate, P3/P4/P12 temporal+aggregate groups; baseline: not measured).
Why: today `checkAvailability` takes ONE camp × ONE range, so "which camp is free this weekend" forces the model to fan out N separate tool calls — it blows the 6-calls/turn budget (ADR-013/CAM-416) and still can't answer a date-SET ask. This story gives the model ONE batched tool so the ask lands in a bounded number of live reads.
Scope: a NEW read-only `bulkAvailability` tool that takes a candidate-camp FILTER (the same taxonomy/province/price args `searchCampsites` already accepts) + a date-SET (the `DateRange[]` `resolveDates` returns, CAM-462) and returns a camp × date-range availability matrix (per cell: free-with-N-left / full), computed by LIVE batched reads with a HARD CAP checked BEFORE the batch runs. Reuses the existing batched availability core; inherits the CAM-469 public-visibility gate. No schema, no materialized table, no new UI.
Depends on: research §5 phase-1 item 1-6 · CAM-462 (resolveDates — the `DateRange[]` date-set this consumes) · CAM-427 (`getRemainingCapacityForCamps` — the batched live core reused) · CAM-469 (the visibility gate inherited) · CAM-344 (pre-loop MAX cap) · CAM-457 (eval harness — the P3/P4/P12 groups this is measured by) · ADR-013 (bounded loop + guest tier)

## Rules
- BR-1 `bulkAvailability` is a read-only `guest`-tier tool (same tier as `checkAvailability`/`searchCampsites` — no identity needed, `userId` unused). Input = a candidate-camp FILTER (a subset of the `searchCampsites` arg shape: province/region/type/price/petFriendly/taxonomy) + `dates: DateRange[]` (the `resolveDates` output, `startDate` inclusive check-in, `endDate` EXCLUSIVE checkout). Output = a discriminated result `{ ok: true, matrix } | { ok: false, reason: 'over_cap' | 'no_match' | 'error' }`.
- BR-2 Availability is ALWAYS a LIVE query — computed fresh on every call from Booking (CONFIRMED/PENDING) + ACTIVE non-expired InternalHold + whole-camp BlockedDate; NEVER cached, NEVER read from a materialized table (ADR-009 tool-use principle; the epic's core rule). Reuses `getRemainingCapacityForCamps` (`lib/campsite-availability.ts`, CAM-427) — the SAME batched core `searchCampsites` already uses — one call per range, never a per-camp-per-range loop and never a parallel capacity formula.
- BR-3 HARD CAP (load-bearing, CAM-344) — the two candidate dimensions are asymmetric BY DESIGN (ratified at G2, tech.md Decision 2): the RANGE count is a model-controlled array and is REFUSED over its cap (`{ ok: false, reason: 'over_cap' }`, checked BEFORE any batched read) because a partial date-set silently answers a different question; the CANDIDATE-CAMP count is a filter-RESULT page (like `searchCampsites`) and is `take`-BOUND to the top-N, never refused, because returning the top-10 matching camps is a complete honest answer to a filter, not a silent partial of an enumerated list. The tool NEVER runs an unbounded batch. Values: candidate camps capped at `SEARCH_CAMPSITES_MAX_RESULTS` (=10, reuse) · ranges capped at `MAX_DATE_SET_RANGES` (=12, reuse from CAM-462) · the product (cells ≤ 120) is a structural invariant of the two caps above, not a separate runtime check.
- BR-4 Visibility gate (inherited, security) — only publicly visible camps (`isActive: true AND isPublished: true AND deletedAt: null`) ever enter the matrix, so a forged/guessed id can never leak an unpublished camp's numbers (CAM-469, BR-2). The candidate set is resolved via `buildCampSiteWhere` (which ALREADY gates visibility, same as `searchCampsites`), so the gate is inherited for free. No raw model-supplied `campId[]` input exists in v1 (G2-ratified, tech.md Decision 3) — a phase-2 `campId[]` addition would need its own explicit CAM-469 re-gate before `getRemainingCapacityForCamps` (which is itself ungated); documented, not built.
- BR-5 Full vs free per cell — a (camp, range) cell is "full" when `remaining === 0` OR `blockedByHost === true` OR `remaining < guests`; "free (N left)" when `remaining !== null && remaining >= guests`; "unknown" when `remaining === null` (whole-camp with no explicit capacity and not host-blocked, or a fail-open range) — reuses `RemainingCapacityResult` verbatim (capacity/bookedGuests/heldGuests/remaining/blockedByHost, CAM-427), no new availability math (G2-ratified wire shape, tech.md Decision 5: positional camp × range matrix, cells aligned by index to the echoed `ranges` array).
- BR-6 No silent guess / no fabrication — an empty candidate set returns `{ ok: false, reason: 'no_match' }` (never `{ ok: true, matrix: [] }` pretending a check ran); a live-read failure returns `{ ok: false, reason: 'error' }` and the model tells the camper it couldn't check right now — availability is NEVER fabricated as "free" (BR-2).
- BR-7 Guests default — "free" is judged against a requested party size; absent → default 1 (same default `getAvailabilityStatusForCamps` uses; G2-ratified, tech.md Decision 3/6).

## Edge cases
- EC-1 IF a candidate camp is full (numerically full OR host-blocked) for one or more requested ranges THEN it is shown as full for those ranges and PRESENT in the matrix — never silently dropped, so the camper learns it was considered and is full, not just absent (BR-5, AC-2/AC-3).
- EC-2 IF the candidate filter matches no published camp THEN return `{ ok: false, reason: 'no_match' }` — no availability query runs and no camp is fabricated; the model asks the camper to relax the filter (BR-6, AC-4).
- EC-3 IF the range count exceeds its cap (>12) THEN the cap is enforced BEFORE any batched read and the tool returns `{ ok: false, reason: 'over_cap' }` — it never allocates an unbounded batch; a candidate-camp count over 10 is NOT this failure mode — it is bound to the top-10 page and the tool still runs (BR-3/CAM-344, AC-5).
- EC-4 IF a live batched read throws (DB error) THEN return `{ ok: false, reason: 'error' }` — the tool NEVER falls back to a fabricated "free"/"available" or to a stale/cached value; the model tells the camper it couldn't check availability right now and to try again (BR-2/BR-6).
- EC-5 IF a matching camp is unpublished/inactive/soft-deleted THEN it never enters the candidate set (visibility inherited from `buildCampSiteWhere`) and its numbers are never returned — indistinguishable from "not a match" (BR-4/CAM-469, AC-6).
- EC-6 IF a single range within the set is degenerate (same-day/inverted/over-`MAX_STATUS_RANGE_NIGHTS`) THEN that range fails open to "unknown" for every camp (the existing `getRemainingCapacityForCamps` fail-open contract) WITHOUT failing the whole matrix — the other ranges still return live status (BR-2).

## Data
- No new model, no migration. `bulkAvailability` is CODE only (a new `lib/ai/tools/bulk-availability.ts` + its tool registration in `lib/ai/tools/index.ts`) — it READS the existing Booking / InternalHold / BlockedDate / CampSite / Spot tables via the existing batched core and writes nothing.
- NO materialized `AvailabilityCalendar` table this story (PREP-6 reconciliation — see the header note + Out of scope). Every read is live.

## Out of scope
- A materialized `AvailabilityCalendar` table (schema-gap-analysis §PREP-6) → phase-2 follow-up; build only when live-batch query volume proves it earns its keep (CAM-344/CAM-355 no-premature-materialization). No CAM-id yet — a phase-2 candidate.
- Superlative/aggregate ranking on top of the matrix ("ถูกสุดที่ยังว่างเสาร์นี้" = free-filter THEN cheapest) → the model composes bulkAvailability + `searchCampsites` sort; a dedicated ranking tool is not built here.
- Adding the P3/P4/P12 GOLDEN CASES to the eval fixture + lifting the current `cases.length <= 8` ceiling (`__tests__/cam-457-eval-harness.test.ts` line ~102) → blocked on the owner corpus import (not yet in repo). This story ships the CAPABILITY those cases will measure, not the cases.
- Party model (adults/children/pets/vehicles) beyond a single `guests` count → phase-2 (PREP-7).
- Raw model-supplied `campId[]` input (G2-ratified deferral, tech.md Decision 3) → v1 is filter-only; a phase-2 `campId[]` needs its own explicit CAM-469 re-gate + cap.

## Self-verify
- AC-1..AC-6 → unit/integration tests of `bulkAvailability` over a seeded fixture (published + unpublished camps, mixed Booking/Hold/BlockedDate): matrix correctness per range (AC-1/AC-3), a full camp stays present (AC-2/EC-1), empty candidate set → no_match (AC-4/EC-2), ranges-over-cap refused before any read while camps-over-10 pages to top-10 not refused (AC-5/EC-3), unpublished camp never in the matrix (AC-6/EC-5), a live-read throw → error not fabricated-free (EC-4), a degenerate single range fails open without failing the matrix (EC-6).
- Story-specific: CAM-344 pre-loop cap asserted (over-cap on RANGES refuses BEFORE any batched read runs; over-cap on CAMPS pages to top-10 and still runs) · visibility gate asserted (unpublished/inactive/deleted id absent) · numbers agree with single-camp `checkAvailability` and with `searchCampsites`' "เหลือ N ที่" for the same (camp, range) (ADR-009 no-forked-data-path) · EXCLUSIVE-checkout preserved from `DateRange` · no N+1 (`getRemainingCapacityForCamps` called O(rangeCount) times, never O(camps×ranges)).
