## Story
As a **Camper**, I want น้องกองไฟ to put two or three camps I was just shown side by side on the things I care about — price, capacity, facilities, "เหมาะครอบครัว/มือใหม่/รถเก๋งเข้าถึง", verified, policy — with the real reason for each difference, so that I can decide between them without opening each camp one by one (grounds P2 comparative "เปรียบเทียบอันที่ 1 กับ 2 อันไหนเหมาะกับครอบครัว"; not measured).
Why: today the assistant can only read ONE camp at a time (`getCampDetail` is single-id) and has no comparison capability at all (research §2 P2, §5 phase-1 item 1-2) — so "เทียบสองอันนี้" forces the camper to ask about each camp separately and hold the differences in their head; this story adds a batch read + a `compareCamps` tool that tables the shown set on named criteria, each facet difference carrying its CAM-464 evidence (P13 "why"), never a fabricated value.
Scope: a NEW read-only `compareCamps(campIds[], criteria[]?)` guest-tier tool + a LEAN batch read model behind it. The model resolves 2–4 campIds from CAM-460's injected shown-state and passes them + the requested criteria; the tool batch-reads their guest-safe fields (visibility-gated per id) + computes the 3 facets, and returns a per-camp × per-criterion matrix of VALUES + evidence. NO new UI screen (the model presents the comparison in prose over the existing card surface). NO facet/criteria SEARCH filter. NO "winner" field (honesty — the model phrases the recommendation from the evidence).
Depends on: CAM-460 (`ConversationShownState` — the model resolves campIds from the injected shown-set) · CAM-464 (`computeFacetScores` — the facet criteria + their evidence) · CAM-469 (the AI-tool public-visibility gate this batch read inherits) · CAM-457 (eval harness — the P2 golden-case format) · research `docs/research/campvibe-ai-gap-closure-data-layer.md` §2 (P2) + §5 phase-1 item 1-2 · ADR-009 (no-forked-data-path) · ADR-003 (closed criteria vocabulary = engineering enum)

## Rules
- BR-1 NEW TOOL `compareCamps(campIds: string[], criteria?: CriterionId[])` — a read-only `guest`-tier tool registered alongside `getCampDetail`/`checkAvailability` (same registry, ADR-009). `campIds` = the ids the model resolves from CAM-460's injected `<shown_results>` ordinals; zod: array of UUID, `min 2`, `max MAX_COMPARE_CAMPS`. A too-short (<2) or too-long (>max) array fails the tool's zod schema → `invalid_args` via the existing `dispatchTool`, with NO DB query (same as CAM-408/CAM-461). (proves AC-1/AC-4, EC-1/EC-2)
- BR-2 HARD CAP `MAX_COMPARE_CAMPS` — 🟡 default `4` (a comparison of 10 camps is not a comparison; 2–3 is the sweet spot, 4 the ceiling — confirm exact ceiling at G2). A model/state-controlled array length gets a hard cap checked BEFORE the batch read (CAM-344 lesson). Over-cap → refuse (BR-1) and the model asks the camper to narrow (AC-4); NEVER silently truncate a named set to a partial compare (misleads the camper). (proves AC-4, EC-1)
- BR-3 VISIBILITY GATE — inherit, do not reinvent. The batch read is a single `findMany({ where: { id: { in: campIds }, isActive: true, isPublished: true, deletedAt: null } })` — the SAME public predicate `getCampDetail`/`checkAvailability` already apply (CAM-469, reused verbatim). An id that fails the gate (or does not exist) is simply absent from the result — there is NO way for a caller to distinguish "unpublished" from "nonexistent" (no existence oracle); a non-public camp is never read into the matrix. (proves AC-5, EC-3)
- BR-4 CRITERIA VOCABULARY — a closed, engineering-owned set (ADR-003): 🟡 candidate = `price | capacity | facilities | family | beginner | road_access | verified | cancellation_policy | distance | rating` (each maps to a guest-safe `getCampDetail` field the read already returns). An unknown criterion → zod rejects the whole call as `invalid_args` before any query. When `criteria` is omitted → the DEFAULT set: 🟡 recommend the decision core `["price","capacity","family","verified","rating"]` (confirm exact vocabulary + default at G2 — behavior fixed either way). (proves AC-2/AC-3/AC-6, EC-6)
- BR-5 MATRIX = VALUES + EVIDENCE, NO WINNER (honesty, P13). Per camp × requested criterion the tool returns the raw comparable value — for the 3 facet criteria the CAM-464 `{score, confidence, answerable, evidence}` UNCHANGED (evidence mandatory, an absent facet ⇒ the honest "ไม่มีข้อมูล" cell); for the rest the atomic field(s) (`priceLow`/`isFree`/`extraFee*`, `maxGuestsPerDay`/`maxTentsPerDay`, `isVerified`, `cancellationPolicy` `null`=ไม่มีข้อมูล, `distanceFromBangkokKm`, `avgRating`/`reviewCount`). The tool NEVER emits a `winner`/ranking field — the model phrases which camp is more suitable, grounded in the returned evidence, never a tool-asserted verdict (a camp's "family suitability" depends on the camper's unstated priorities). 🟡 present-values-only recommended (confirm at G2). (proves AC-1, EC-4)
- BR-6 ATOMIC + REUSE (api.md rule 4 + ADR-009 no-forked-data-path). Price cells stay atomic (never a merged string); facet cells reuse `computeFacetScores` (CAM-464) verbatim; the batch read reuses `getCampDetail`'s guest-safe field selection — 🟡 recommend a DEDICATED LEAN batch read model (drop the per-weekend availability + full-review computations `getCampDetail` runs — a comparison does not need them, and batching N × those is N×~10 queries) that leaves `getCampDetail`'s single read UNCHANGED (CAM-355 shared-fn caution); confirm store/read path at G2. (proves all)
- BR-7 MODEL-PHRASED ANSWER (AI-assistant convention). Thai in the "Then" column is REPRESENTATIVE (เรียบเรียงเอง), not char-for-char; the testable contract = eval P2 comparative BEHAVIOR (correct tool + campIds resolved from CAM-460 shown-state + criteria) + the SYSTEM EFFECT matrix data + owner-verify on localhost. `compareCamps` returns only public camp fields — no new PII surface (mirrors `getCampDetail`'s guest-safe boundary). (proves all)

## Edge cases
- EC-1 IF `campIds` exceeds `MAX_COMPARE_CAMPS` THEN the tool rejects it (`invalid_args`) BEFORE any DB read (CAM-344 cap-before-loop) and the assistant asks the camper to pick 2–`MAX_COMPARE_CAMPS` — it never truncates a named set to a partial compare (AC-4). (BR-1/BR-2)
- EC-2 IF fewer than 2 campIds resolve to visible camps (only one was given, or the rest were gated out) THEN it is not a comparison → the assistant answers about the single camp or asks for a second, and NEVER fabricates a second camp. (BR-1/BR-3)
- EC-3 IF a campId is unpublished / inactive / soft-deleted / forged / nonexistent THEN the batch read excludes it via the CAM-469 visibility gate (absent, no existence oracle); if this drops the visible set below 2 → EC-2. (BR-3)
- EC-4 IF a camp has no data for a requested criterion (a facet absent per CAM-464 BR-5, or `cancellationPolicy` null, or no price) THEN that cell is an honest "ไม่มีข้อมูล", never a fabricated value or a fake 0-score, e.g. `ลานที่ 2 ยังไม่ได้ระบุนโยบายยกเลิก เลยเทียบข้อนี้ให้ไม่ได้` (เรียบเรียงเอง). (BR-5)
- EC-5 IF the same campIds + criteria are compared again with unchanged source fields THEN the matrix DATA is identical (deterministic — facets via `computeFacetScores`, atomic fields read straight); only the model's wording may vary. (BR-7)
- EC-6 IF no criteria are specified THEN the DEFAULT criteria set (BR-4) is used, not an empty comparison or a guess at intent. (BR-4)

## Data
- No schema change, no migration — all reads are existing `CampSite` rows via a NEW batch read: `findMany({ where: { id: { in: campIds }, isActive: true, isPublished: true, deletedAt: null }, select: <lean guest-safe comparison fields> })` + `computeFacetScores` per camp (pure, on the already-selected `options`/`minimumAge` — no extra query, CAM-464). Bounded input (`MAX_COMPARE_CAMPS`) ⇒ no unbounded scan (CAM-344).
- Guest-safe fields ONLY — the comparison read selects the SAME public subset `getCampDetail` returns (price/capacity/amenities/facets/verified/cancellationPolicy/distance/rating/location); NO operator/contact/payout/KYC field is ever selected (PDPA, mirrors the CAM-427/CAM-449 boundary).
- 🟡 batch-read path (dedicated lean read model vs reuse `getCampDetail`'s heavier select) = architect G2 (see ## Seams & refs); either way = no migration.

## Out of scope
- A dedicated side-by-side comparison-TABLE UI component → the model presents the comparison in prose over the existing card surface; a visual comparison table is a follow-up (designer/frontend) → CAM-id TBD.
- Facet/criteria-based SEARCH or ranking ("หาลานเหมาะครอบครัวสุด") → CAM-464 out-of-scope / follow-up (compute + expose first).
- Criteria that need phase-2 data (season conditions, mosquito/quiet/fog, cancellation-policy TIERS beyond the current enum) → phase-2 → follow-up (research §5 phase-2 items 2-2/2-4).
- Availability-across-dates comparison (which of these is free next weekend) → CAM-465 (`bulkAvailability`), not this tool.
- Persisted / shareable comparison, or comparing more than `MAX_COMPARE_CAMPS` → out (violates the cap).
