## Story
As a **Camper**, I want the assistant to remember the camps it just showed me, so that I can say "เอาอันที่ 2" or "อันที่ถูกกว่า" and it acts on the right camp instead of making me search again.
Why: today the assistant's only "memory" is a replay of the last 10 messages (`loadWindow`), and the system prompt forbids it from naming camps in its answer text (CAM-405/437) — so the ordinal/name of a shown result is nowhere the model can read it back, and every follow-up restarts from zero (research §2: P1/P11/P16, ~15% of the corpus).
Scope: capture the shown-results state after a `searchCampsites` result + inject it into `buildSystemPrompt` each turn so a back-reference resolves to the right campId and acts on it WITHOUT re-searching. Covers ordinal reference, superlative-over-the-shown-set, retained constraints across an interleaved question, and the clarify-when-nothing-was-shown path. Slot EDITING and result EXCLUSION are CAM-461.
Depends on: CAM-457 (eval harness — the `seededState` multi-turn golden-case format this ties to) · CAM-420 (the guest `{messages}` vs authed `{conversationId, message}` request split this behavior must serve both of) · ADR-013 (chat persistence + D2 180-day retention/hard-delete) · research `docs/research/campvibe-ai-gap-closure-data-layer.md` §5 phase-1 item 1-1 (D1 state) + §2

## Rules
- BR-1 What is remembered (the D1 state shape captured after every `searchCampsites` result): `last_results` = an ordered list `[{ ordinal (1-based, matching the card display order the camper saw), campId, name, aiMentioned }]`; `shown_ids` = the union of every campId shown so far this conversation (captured HERE as the hand-off input for CAM-461's `excludeIds` — using it to exclude is out of scope); plus `focus`/`constraints`/`party` (the active province/type/price/party the camper stated). `last_results` is OVERWRITTEN by the most-recent search (single slot); `shown_ids` accumulates (proves AC-1/AC-5/AC-6).
- BR-2 Reference resolution: an ordinal (`อันที่ N` / `อันแรก`=1 / `อันสุดท้าย`=N) resolves to `last_results[N].campId`; a superlative over the shown set (`ถูกกว่า`/`ถูกที่สุด`/`แพงสุด`) resolves over `last_results` by the named attribute — always scoped to the SHOWN set, never a new search. A resolved reference is acted on via `getCampDetail`/`checkAvailability` on that campId — a real tool call THIS turn, which re-satisfies the CAM-437 grounding rule (the model may only name a camp a tool returned this turn) (proves AC-1/AC-2).
- BR-3 No prior results, an out-of-range ordinal, or an attribute the shown data doesn't carry → ask back (clarify), never guess or invent a camp. This EXTENDS the CAM-437 grounding + persona honest-fallback seam from "zero-result search" to "referenced-but-nothing-was-shown". Representative: `ยังไม่ได้ค้นหาลานไหนเลย ลองบอกจังหวัดหรือแบบที่อยากได้ก่อนได้ไหม` / `ตอนนี้แสดงไปแค่ {N} ที่ ลองเลือกจากในนั้นได้ไหม` (proves AC-3, EC-3/EC-7).
- BR-4 Guest vs authed mechanism (stated honestly, not decided here — architect G2): **authed** = state lives server-side, either a new `ChatConversation.state Json?` column OR derived from the already-persisted `ChatMessage.blocks` (the cards the camper saw) — read per turn through `lib/ai/conversation-store.ts` (the ONE store owner); **guest** = the server is stateless (the `{messages}` path persists nothing), so the client must resend `last_results` in the request body — a wire-contract addition that is untrusted input and MUST be re-validated/sanitized at the boundary (security G2). In BOTH cases the state is serialized into `buildSystemPrompt` each turn (the single prompt-assembly seam). 🟡 Default if unresolved at G2 = defer the storage mechanism to the architect; behavior/AC above are fixed regardless of which mechanism is chosen (proves AC-4).
- BR-5 Depth of memory: `last_results` = the most-recent search only (overwritten); `shown_ids` accumulates across the conversation. Remembering more than one prior shown set (a multi-search result history) is out of scope. 🟡 Default = single most-recent-search slot (proves AC-5).
- BR-6 Model wording is generated per turn, so Thai in the AC "Then" column is representative, not char-for-char; the testable contract = eval BEHAVIOR (P1 `seededState` cases: ordinal → correct tool + resolved campId; no-prior → `kind:"no_tool"` clarify) + owner-verify reading a real answer on localhost. State stores PUBLIC camp data only (campId/name/price) plus the camper's own stated search constraints — no new PII surface; authed state inherits the existing 180-day chat retention + hard-delete (`conversation-store.ts`), so no separate PDPA handling is added.

## Edge cases
- EC-1 IF a resolved ordinal camp exists THEN act on it via a tool call on its campId (no new search); IF the model would describe result N WITHOUT a tool call THEN that breaks CAM-437 grounding — resolution MUST route through a `getCampDetail`/`checkAvailability` call on the campId (BR-2).
- EC-2 IF a superlative is asked but the shown set has only one camp THEN act on that one; IF the named attribute is not in the shown card data THEN clarify, never guess a value (BR-2/BR-3).
- EC-3 IF no `searchCampsites` has run this conversation THEN ask what to search for; name or invent NO camp (BR-3, CAM-437).
- EC-4 IF a guest request carries no client-provided `last_results` THEN the server has no memory to resolve against → fall to the clarify path (EC-3), never fabricate a prior result (BR-4).
- EC-5 IF a newer search replaced the shown set THEN ordinals resolve against the newest set only; the older ordinals are gone (BR-5).
- EC-6 IF the ordinal exceeds the shown count (e.g. `อันที่ 9` when 5 were shown) THEN say only {N} were shown and ask which, never resolve to a non-existent slot (BR-3).
- EC-7 IF the authed state is unavailable (a `loadWindow` failure, or `blocks` were dropped as oversize per the store's `MAX_BLOCKS_BYTES`) THEN the turn degrades to no-memory (clarify / re-search), never errors the turn (BR-3/BR-4).

## Data
- `ChatConversation` MAY gain a `state Json?` column (holding `last_results`/`shown_ids`/`focus`/`constraints`/`party`), OR the state is DERIVED from the existing `ChatMessage.blocks` (already persisted per turn) — the storage mechanism is the architect's G2 decision (both were researched: derive-from-blocks avoids a migration; a dedicated column is simpler to inject and read). No new PII field either way.
- migration: IF a `state Json?` column is chosen THEN ONE additive nullable column (reversible, no backfill needed); IF derive-from-`blocks` THEN none. Decided at G2.
- Guest path: no server storage; `last_results` travels in the request body (a wire-contract addition — architect/api G2, validated as untrusted input).

## Seams & refs
- Reuse: `lib/ai/openrouter-client.ts` → `buildSystemPrompt` — the ONE place per-turn context is injected (today: today's-date line, น้องกองไฟ persona, the CAM-437 grounding rule); the state serialization is added HERE, never a parallel prompt. `lib/ai/conversation-store.ts` owns every `ChatConversation`/`ChatMessage` read/write (`loadWindow` already returns `blocks`) — a `state` column read/write, or the blocks-derivation, lives in this store, never in the route. `lib/ai/build-turn-messages.ts` assembles turns from `contentText` today (blocks are NOT yet threaded). `lib/ai/tools/search-campsites.ts` `SearchCampsiteCard` (`id`/`name`/price) are the fields `last_results` captures.
- Grep-inventory of the shown-results pipeline (architecture.md 15b): cards are produced in `executeToolCalls` → `collectCardsFromToolData` (openrouter-client), persisted for authed via the route's `appendTurn` → `blocks` (conversation-store), and loaded via `loadWindow`. Tag: `buildSystemPrompt` = **CHANGE** (inject state) · `conversation-store` = **CHANGE** (capture + read state — column or derive) · `build-turn-messages` = **MAYBE** (only if blocks thread through — architect G2) · the three `buildSystemPrompt` callers (`runAssistantTurn` / `…FromMessages` / `…FromMessagesStreaming`) = **NO-CHANGE** (they inherit the injected state for free) · the CAM-437 grounding rule = **NO-CHANGE** but INTERACTS (a resolution must go through a tool call to stay grounded, EC-1).
- Eval: `scripts/ai-eval/golden-cases.json` + `scripts/ai-eval/case-schema.ts` — the `seededState` (prior-turn + canned tool-result) discriminant already exists (CAM-457 BR-1), so P1 ordinal-reference cases are ADDED the same way CAM-459 added its zone-A cases; the current fixture is small (7 cases) and `MAX_EVAL_CASES = 500`, so no ceiling blocks adding them (no hard dependency — flag only if a later corpus-freeze story lands first).
- Refs: research §5 (D1 phase-1 1-1) + §2 (P1/P11/P16) · ADR-013 (persistence, D2 retention) · CAM-437 (grounding) · CAM-420 (guest/authed request split) · CAM-457 (eval `seededState`).

## Out of scope
- `excludeIds` result EXCLUSION (`อันอื่นบ้าง` / `ที่ยังไม่เห็น`) + `sort` + OR-within-facet-group + batch `getCampDetails` + `compareCamps` → CAM-461 (story 5). `shown_ids` is CAPTURED here as CAM-461's input; USING it to exclude is CAM-461.
- Slot EDITING (`เปลี่ยนเป็น 4 คน` rewriting a live constraint mid-flow, P11) → CAM-461 / a later story. This story only CAPTURES and RETAINS `focus`/`constraints`/`party` (so they are not re-asked, AC-6), it does not implement editing them.
- Multi-search result history (remembering more than the most-recent shown set) + long-term user memory (D5) → phase 3.
- No new UI — reference-resolution rides the existing plain-text answer + card surfaces; no new component/state.

- AC-3, AC-4 → eval (`kind:"no_tool"` clarify case) + owner-verify (a guest with no carried state gets the clarify path, not a fabricated result).
- Story-specific: a resolution always routes through a tool call on the resolved campId (CAM-437 grounding upheld, EC-1) · `last_results` overwritten per search / `shown_ids` accumulates (BR-1/BR-5) · guest with no carried state degrades to clarify, never fabricates (EC-4) · unavailable/oversize state degrades, never errors the turn (EC-7) · IF the architect's G2 storage decision (column vs derive) or the guest wire mechanism turns out to contradict this behavior THEN STOP and re-open at G2 — do not improvise a redesign.
