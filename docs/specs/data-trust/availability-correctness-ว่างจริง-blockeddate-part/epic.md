# Availability Correctness — ว่างจริง (BlockedDate + partial capacity + hold) (CAM-22)

## Why
A host must see and control the TRUE remaining capacity of a camp — bookings, host blocks, partial-capacity nights, and now negotiation holds — computed from one source so the same dates are never double-sold. **KPI:** double-booking incidents caused by the negotiation window = 0 (not measured — no baseline yet).

## Scope
- In: every real consumer of "how much room is left" reads one function set (`lib/campsite-availability.ts`): confirmed/pending bookings (CAM-57), host `BlockedDate` coverage (CAM-56/CAM-190), partial remaining capacity (CAM-267), the read-only month calendar (CAM-55), and temporary negotiation holds with lazy expiry (CAM-302).
- Out: lead → quote → deposit → manual-stay funnel around a hold → CAM-311 + the ManualStay story (HostOS M1.2, ADR-012) · public/guest hold surfaces · scheduled-job expiry (lazy expiry is the chosen design).
