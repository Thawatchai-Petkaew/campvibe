## Story
As a **Host**, I want a screen to manage the individual spots of my own camp — list, add, edit, remove, each with its own photos — so that a per-spot camp can actually be built (today PER-SPOT mode is a dead end because there is no in-app way to manage spots).
Why: the owner asked to "create the Table Support and Screen" for spots. Ground-truth correction: the **`Spot` table already exists and is rich** (`zone`, `name`, `viewType`, `maxCampers` = people-per-spot, `maxTents`, `pricePerNight`/`pricePerSite`, `environment`, `nearFacilities`, `images` gallery, `bookings`/`blockedDates`/`holds` relations, `deletedAt` soft-delete). The full CRUD **API also exists** (`app/api/campsites/[id]/spots`). The genuinely missing pieces are (a) the host-facing CRUD **screen**, (b) two API-behavior fixes (hard-delete → soft-delete; list must exclude soft-deleted), and (c) wiring the existing photo-upload pipeline into a per-spot form. **No schema change.**
Scope: the host spot-management screen at `/dashboard/campsites/[id]/spots` — list / create / edit / soft-delete a camp's spots (fields: zone, name, viewType, maxCampers, maxTents, pricePerNight, pricePerSite, and per-spot photos) + the two API-behavior fixes + the **360/panorama structural groundwork**: an additive `Image.kind` enum (`PHOTO` | `PANORAMA`) so a host can mark a photo as a panorama at upload, with the marker carried through the detail/spot read payloads (the interactive viewer is a later story). Reuses `<ImageUpload>`, the modal/confirm primitives, and the existing spots API verbs.
Depends on: — (unblocks CAM-351 PER-SPOT usability). **Build CAM-352 first or in the same wave as CAM-351.**
Sequencing: CAM-352 is the prerequisite that makes CAM-351's PER-SPOT mode usable end-to-end. The camper-facing display of spot photos + zone section on the detail page is a **separate follow-up (recommended CAM-354)** — this story populates the data; that story shows it to campers. The interactive 360/panorama **viewer** is a further follow-up (recommended CAM-355) — this story lays the schema + upload marker so the viewer story only adds rendering.

## Rules
- BR-1 The screen lists **non-deleted spots only**. Fix the existing `GET /api/campsites/[id]/spots` list to filter `deletedAt: null` (today it returns soft-deleted rows). This keeps the screen, the availability page's spot selector, the CAM-351 derived total, and CAM-304's `spotCount` all consistent. (proves AC-1, EC-4)
- BR-2 Removing a spot is a **soft-delete**: `DELETE /api/campsites/[id]/spots/[spotId]` sets `deletedAt` instead of `prisma.spot.delete` (a hard delete). A spot may have `Booking`/`InternalHold`/`BlockedDate` rows; a hard delete either fails on the FK or orphans booking history. Soft-delete preserves history and matches every other model in the schema. Confirm copy: `ลบจุดนี้ใช่หรือไม่ ประวัติการจองจะยังถูกเก็บไว้`. (proves AC-7, EC-5) **[Architect note, G2: confirm soft-delete on DELETE — this is a contract-behavior change, no schema change since `Spot.deletedAt` already exists.]**
- BR-3 Field validation reuses the existing `spotSchema` (`lib/validations/spot.ts`): `name` required (min 1) → `กรุณากรอกชื่อจุด`; `maxCampers` integer ≥ 1 (one spot holds many people) → `จำนวนผู้เข้าพักต้องมากกว่า 0`; `maxTents` integer ≥ 1 optional; `pricePerNight` ≥ 0 → `ราคาต้องอยู่ระหว่าง 0–100,000 บาท`; `pricePerSite` optional. Client + server share the schema. (proves AC-5, AC-6, EC-1)
- BR-4 Authz reuses the existing camp-permission seam (`requireCampSitePermission`): create/edit require `CAMPSITE_UPDATE`; delete requires `CAMPSITE_DELETE`; every spot mutation is IDOR-scoped `where: { id: spotId, campSiteId }`. A user lacking the permission sees `คุณไม่มีสิทธิ์จัดการจุดของแคมป์นี้`; the API returns `403`. (proves AC-9, EC-8)
- BR-5 Per-spot photos reuse the existing pipeline: the `<ImageUpload>` component + the spots API's existing `imageCreateNested`/`imageReplaceNested` handling + `spotSchema.images`. No new upload endpoint. Each photo is a regular image file; whether it is tagged `PANORAMA` is a metadata flag on the image (BR-7), NOT a different file format or a different upload path. (proves AC-8, EC-7)
- BR-6 The screen is the entry point CAM-351's PER-SPOT Capacity card links to (`/dashboard/campsites/{id}/spots`), replacing CAM-351's currently-404 CTA. (proves AC-10)
- BR-7 **360/panorama groundwork (schema — architect owns at G2).** Add an additive `Image.kind` enum `ImageKind` = `PHOTO` | `PANORAMA`, default `PHOTO`. Named `PANORAMA` (not `PANO_360`) deliberately: an iPhone Pano is a **wide-strip panorama, not a spherical/equirectangular 360** — the value + the future viewer must not assume a sphere. Classification stays [Public]. At upload the host may toggle a photo to `PANORAMA` (label `ภาพพาโนรามา`); default is `PHOTO`. Optional lean nicety (not required): pre-suggest `PANORAMA` when a photo's aspect ratio is extreme (e.g. width ≥ ~2.5× height), always with a manual override. (proves AC-11, EC-9)
- BR-8 **Read-path (the CAM-342 field-rides-through trap).** `Image.kind` must reach the DETAIL and SPOT read payloads so the future viewer can branch on it: the camp detail (`getCampSiteWithCapacity`) and spot routes already use `include: { images }` (full rows) so `kind` rides at runtime once the column exists — but the response TYPE `types/api.ts` `images?: { url: string }[]` enumerates only `url`, so add `kind?` there (backward-compatible, additive). The catalog card select `lib/read-models/camp-card.ts` enumerates `url` + `sortOrder` only and must **stay that way** — catalog cards do not branch on `kind` (no over-fetch). The image-input contract on spot create/update changes from `string[]` to carry per-image `kind` (e.g. `{ url, kind }[]`); this touches the shared `<ImageUpload>` component + `imageCreateNested`/`imageReplaceNested`. (proves AC-11)

## Edge cases
<!-- cover: invalid · empty/zero · concurrent/duplicate · permission · boundary. -->
- EC-1 IF the host saves a spot with an empty `name` or `maxCampers < 1` THEN block save and show the field error from `spotSchema` (`กรุณากรอกชื่อจุด` / `จำนวนผู้เข้าพักต้องมากกว่า 0`) (BR-3)
- EC-2 IF the create/edit save request fails (network/500) THEN keep the form open, show `บันทึกไม่สำเร็จ ลองใหม่อีกครั้ง`, and do not drop the host's input (BR-3)
- EC-3 IF the host edits/deletes a spot that belongs to a DIFFERENT camp (tampered id) THEN the API returns `404` (IDOR-scoped by `campSiteId`); the UI shows `ไม่พบจุดนี้` (BR-4)
- EC-4 IF a spot was previously soft-deleted THEN it never appears in the list, the availability spot selector, or the capacity derived total (BR-1)
- EC-5 IF the host deletes a spot that has active bookings/holds THEN soft-delete succeeds and the existing `Booking`/`InternalHold` rows remain intact (no orphan, no FK error) (BR-2)
- EC-6 IF the list is loading THEN show a skeleton; IF it errors THEN show a retry state — never a blank screen (AC-3, AC-4)
- EC-7 IF a per-spot photo upload fails THEN show the upload error inline and keep the rest of the spot form intact (do not lose entered fields) (BR-5)
- EC-8 IF a viewer-role team member opens the screen THEN it is read-only (no add/edit/delete controls) and any direct API call returns `403` (BR-4)
- EC-9 IF a photo is uploaded without touching the panorama toggle THEN it defaults to `kind = PHOTO`; every pre-existing image row backfills to `PHOTO` implicitly via the column default (no data migration of values needed) (BR-7)

## Data
- Reused, no schema change: `Spot` (all fields already exist: `zone`, `name`, `viewType`, `maxCampers`, `maxTents`, `environment`, `pricePerNight`, `pricePerSite`, `priceCurrency`, `nearFacilities`, `deletedAt`) · `Spot.images` (S4b gallery relation — already persisted by the spots API) · `Booking`/`InternalHold`/`BlockedDate` spot relations (preserved on soft-delete).
- API-behavior changes (no schema): `DELETE /spots/[spotId]` → soft-delete (`update { deletedAt }`) instead of hard `delete` (BR-2). `GET /spots` list → add `where: { deletedAt: null }` (BR-1).
- **Schema change (360 groundwork, architect-reviewed at G2):** add `Image.kind ImageKind @default(PHOTO)` with `enum ImageKind { PHOTO PANORAMA }`. **Reversible + additive** (new column with a default; existing rows read as `PHOTO` implicitly — no value backfill, drop-column reverses it). **Blast radius: `Image` is SHARED** — one row can belong to a `CampSite`, a `Spot`, OR a `Review` gallery (three nullable FKs `campSiteId`/`spotId`/`reviewId`). The migration is model-wide; the upload marker + read plumbing land on the CampSite + Spot galleries (Review galleries inherit the column, default `PHOTO`, no behavior change). Diff against `prisma/schema.prisma` `model Image`.
- Read-path plumbing (no schema): `types/api.ts` image shape gains `kind?: ImageKind` (additive, backward-compatible) so DETAIL + SPOT payloads carry it. Catalog `campCardSelect` (`lib/read-models/camp-card.ts`) stays `url` + `sortOrder` only (cards do not need `kind`). Spot image-input contract changes `string[]` → `{ url, kind }[]` on create/update.
- migration: **`Image.kind` = reversible additive** (this is the only schema change; the Spot table + all CRUD verbs already exist, `Spot.deletedAt` already present).
