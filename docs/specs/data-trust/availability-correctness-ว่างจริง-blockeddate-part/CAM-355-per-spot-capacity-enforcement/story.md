## Story
As a **Camper**, I want a per-spot camp to accept exactly as many bookings as its real spot-derived capacity — no more — so that I never over-book a camp past its actual total and never see a "full" or "available" signal that disagrees with what the host really has.
Why: pre-existing gap found in CAM-351/352 Discovery — every booking/availability ENFORCEMENT reader queries the raw stored `CampSite.maxGuestsPerDay` column and is blind to spot-derived capacity, so a PER-SPOT camp (`useSpotView = true`) whose stored column is stale, zero, or null is effectively uncapped or wrongly capped. The camper-facing DISPLAY already derives correctly (`getCampSiteWithCapacity` / `calculateSpotCapacity`); enforcement is the parity gap. High blast radius (the booking write path), so it is its own story per the CAM-351 "Capacity-enforcement parity" follow-up.
Scope: make the PER-SPOT effective capacity (= sum of non-deleted spots' `maxCampers` / `maxTents`) the number that the booking write gate, the detail-page remaining badge, and the catalog search badge all enforce and reflect — from ONE derivation source, never the stale column. WHOLE-CAMP enforcement is unchanged (the manual column stays the truth). Does NOT add per-spot booking selection (campers still book at camp level) and does NOT change the locking/transaction model (ADR-006 unchanged).
Depends on: **CAM-351** (mode choice — `useSpotView` semantics, and the rule that the manual `maxGuestsPerDay` is PRESERVED in-row while in PER-SPOT mode) · **CAM-352** (spot management + the `deletedAt: null` filter already added to `calculateSpotCapacity`) · ADR-006 (serializable booking tx) · ADR-009 (single availability source, no forked data path) · ADR-005 (booking snapshot) · ADR-012 (holds/availability).

## Rules
- BR-1 **Effective capacity** is defined once, mode-driven: WHOLE-CAMP (`useSpotView = false`) → the stored `CampSite.maxGuestsPerDay` (guests) / `maxTentsPerDay` (tents), unchanged. PER-SPOT (`useSpotView = true`) → the **sum of `Spot.maxCampers` (guests) / `Spot.maxTents` (tents) over non-deleted spots (`deletedAt = null`)**. A spot with a null per-spot value contributes 0. This is the SAME derivation the display already uses (`lib/spot-aggregation.ts:calculateSpotCapacity`); there must be ONE derivation function feeding both display and enforcement — no parallel capacity math (ADR-009 no-forked-data-path). (proves AC-1, AC-4, AC-6)
- BR-2 **Recommended mechanism = T-B read-through (owner/architect-vetoable at G2).** The three enforcement readers compute effective capacity live at read: WHOLE-CAMP reads the column; PER-SPOT sums non-deleted spots. NO denormalized column, NO backfill, NO change to the stored `maxGuestsPerDay` (which in PER-SPOT mode holds the PRESERVED whole-camp manual value per CAM-351 BR-4/AC-6 and MUST stay untouched). The rejected alternative, T-A persist (recompute the column on every spot write), was weighed and NOT recommended — rationale + the write-path inventory it would require are in `## Seams & refs`. The final persist-vs-read-through mechanics belong to the architect at G2; this story records the recommended approach + rationale so G2 does not start from zero. (proves AC-6; the AC behavior itself is T-choice-independent — a booking over the real total is rejected under either mechanism)
- BR-3 **Soft-delete filter is part of the sum.** The PER-SPOT sum MUST filter `deletedAt = null` (the CAM-352 trap — a soft-deleted spot must not count toward enforceable capacity, exactly as it must not count toward the display). `calculateSpotCapacity` already applies this filter; the enforcement read must not re-introduce an unfiltered sum. (proves AC-1, EC-1)
- BR-4 **The three enforcement/reflection readers each become mode-aware** (under T-B): (a) `checkDateAvailabilityInTx` — the booking write gate inside the ADR-006 serializable tx — rejects when `booked + held + requested > effective capacity` (guests AND tents), reading the PER-SPOT sum inside the SAME transaction boundary so it is snapshot-consistent with the booking/hold reads; (b) `getRemainingCapacity` — the detail-page `เหลือ {n} ที่` / `เต็มแล้ว` badge — computes `remaining = effective capacity − (booked + held)`; (c) `getAvailabilityStatusForCamps` — the catalog search badge — classifies each night against the effective capacity (one added grouped spot-sum query for the whole page, O(1) per page, never O(N)). `getCampSiteDailyAvailability` is a per-day building block that does not read the capacity column and is unchanged. (proves AC-2, AC-3, AC-5)
- BR-5 **The static guest-capacity search FILTER (`lib/campsite-filters.ts` step 5) stays a column-based coarse pre-filter** — RULED unchanged. Prisma cannot express "sum of related spots ≥ N" in a where-clause without raw SQL, and this filter is NOT the over-book vector: its imprecision fails in the safe direction (a stale-high column over-includes a camp that the accurate badge + write gate then correctly reject; a stale-low/null column only false-hides — over-inclusive `OR maxGuestsPerDay IS NULL` already keeps capacity-unknown camps visible). Making it fully spot-aware (raw SQL) is Out of scope. (proves AC-5's coarse-gate boundary)
- BR-6 **Zero derived total (PER-SPOT camp, no live spots or all per-spot values 0/null) → effective capacity = 0 = closed for booking.** Every booking is rejected with the existing full-capacity path; the detail badge shows `เต็มแล้ว`. Enforcement does NOT fall back to the stale column for the 0 case (that fallback is precisely the bug). NOTE: this deliberately diverges from `getCampSiteWithCapacity`'s current `maxGuestsPerDay: spotCapacity.maxGuestsPerDay || campSite.maxGuestsPerDay` DISPLAY fallback (line ~72), which for a zero-spot PER-SPOT camp still shows the stale column as if it were a real capacity — a narrow pre-existing display inconsistency. The enforcement helper this story introduces must NOT carry that fallback. Whether to also align that one-line detail-page display for true parity is a small G2 fold-in (recommended) or a display follow-up — see Out of scope; it is flagged, not silently redesigned here. (proves AC-7)
- BR-7 **The rejection copy is the existing full-capacity copy** — no new user-facing string. The camper's primary "full" signal is `เต็มแล้ว` (the disabled-Reserve badge, from `getRemainingCapacity`); the hard write-gate backstop surfaces as the reserve toast `จองไม่สำเร็จ` on the 409. The internal reject `reason` interpolated in the write gate must reflect the DERIVED effective number for a PER-SPOT camp (not the stale column), but that is an internal detail string, not user-facing. (proves AC-3, AC-7)
- BR-8 **WHOLE-CAMP is unchanged-by-construction.** For `useSpotView = false` every reader reads the stored column exactly as today; no per-spot branch executes. This is a hard regression boundary, asserted by test (Self-verify). (proves AC-4)

## Edge cases
<!-- cover: invalid · empty/zero · concurrent/duplicate · permission · boundary. -->
- EC-1 IF a spot is added, edited, or soft-deleted for a PER-SPOT camp between the moment the camper loaded the page and the moment the booking transaction runs THEN the effective capacity is evaluated LIVE inside the booking serializable transaction (the spot-sum is read with `deletedAt = null` inside the tx) — a committed spot change counts, and a stale form re-checks against the live derived total and is rejected with `จองไม่สำเร็จ` if it now exceeds it (server-authoritative, same as bookings/holds) (BR-3, BR-4)
- EC-2 IF two campers try to book the last remaining capacity of a PER-SPOT camp at the same instant THEN the existing ADR-006 serializable transaction + bounded P2034 retry resolves it exactly as for a whole-camp camp — one succeeds, the other gets a 409 (`จองไม่สำเร็จ`); the spot-sum read stays INSIDE the tx so it is snapshot-consistent with the booking/hold reads and no over-book slips through the boundary (BR-4)
- EC-3 IF a PER-SPOT camp's stored `maxGuestsPerDay` column is stale (`0`, `null`, or an old higher/lower number) THEN enforcement ignores the column entirely and uses the derived non-deleted-spot sum; the column is neither read for capacity nor written/synced (T-B) (BR-2, BR-6)
- EC-4 IF the derived per-spot sum is exactly at the boundary (`booked + held + requested = effective total`) THEN the booking is ACCEPTED (the cap is inclusive of the total, `> total` rejects — identical `>` semantics to the current whole-camp check) and `เหลือ {n} ที่` shows `0` only after that booking commits (BR-4)
- EC-5 IF the PER-SPOT spot-sum read fails on the booking WRITE path (DB error inside the tx) THEN the booking fails CLOSED — the transaction errors and no booking is created (never allow an unbounded/over-book on a read failure); this contrasts with the catalog badge, which fails OPEN (no badge, existing `getAvailabilityStatusForCamps` fail-open contract) since a missing badge is a display gap, not an over-book (BR-4)
- EC-6 IF a camp's mode is switched after bookings already exist (PER-SPOT ⇄ WHOLE-CAMP) THEN the switch only changes which capacity SOURCE future enforcement reads (spots vs the manual column); existing bookings' snapshots (ADR-005) are never invalidated or cancelled, and if the new source yields a lower cap than the current load the camp simply accepts no new bookings until load drops — identical to a host manually lowering `maxGuestsPerDay` today (no retroactive re-check) (BR-1, BR-8)
- EC-7 IF a PER-SPOT camp has spots whose `maxCampers` are all null/unset THEN the derived sum is 0, handled by the zero-total rule (BR-6): the camp is closed for booking (`เต็มแล้ว`), not treated as unbounded (BR-1, BR-6)

## Data
- Read-only under the recommended T-B: `CampSite.useSpotView` (mode selector, read) · `CampSite.maxGuestsPerDay` / `maxTentsPerDay` (read for WHOLE-CAMP only; UNTOUCHED — holds the preserved manual value while in PER-SPOT per CAM-351) · `Spot.maxCampers` / `Spot.maxTents` / `Spot.deletedAt` (summed with `deletedAt = null` for PER-SPOT). **migration: none** (no denormalized column, no backfill).
- Honest note on the rejected T-A: it would instead WRITE `maxGuestsPerDay` / `maxTentsPerDay` (or a new derived column) on every spot mutation, requiring a one-time backfill sync of stale columns for existing PER-SPOT camps. Reversibility is imperfect — writing the derived sum into `maxGuestsPerDay` overwrites and permanently loses the CAM-351-preserved manual value, so the DOWN cannot restore it (another reason T-A is not recommended). Stated for the G2 decision only; no migration is authored by this story under the recommendation.
