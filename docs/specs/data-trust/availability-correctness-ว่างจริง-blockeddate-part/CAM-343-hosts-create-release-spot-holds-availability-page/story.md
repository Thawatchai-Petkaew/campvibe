# Hosts create and release spot holds from the availability page (CAM-343)

## Story
As a **Host**, I want to create a temporary hold on a date range (whole camp or a single spot) and release it again from the availability page I already manage, so that I can reserve inventory while I close a deal over LINE / Facebook / phone without that inventory being double-sold, and free it the moment the deal falls through.
Why: CAM-302 shipped the InternalHold API + data model and folded holds into the availability math, but cut the host WRITE UI to a follow-up (this story) — until it exists a host has no way to actually place or release a hold. Holds are host-internal only (feature No-go: no public/guest-facing hold surfaces).
Scope: a hold create-form + a live-holds list + a release action, added to the EXISTING host availability page (`app/dashboard/campsites/[id]/availability`) alongside the CAM-55 month calendar and the CAM-56 blocked-dates manager. Reads/writes go through the EXISTING CAM-302 API only — no new endpoint, no schema change, no migration.
Depends on: CAM-302 (InternalHold API + data model + availability integration, shipped) · CAM-55/56 (availability page + month calendar, shipped) · ADR-012 §4 · ADR-006 · ADR-009.

## Rules
- BR-1 Scope of a hold = whole camp (no spot) OR one of THIS camp's own spots. The spot selector reuses the camp's spots list already fetched on this page (blocked-dates precedent) and is hidden when the camp has no spots — then the hold applies to the whole camp. Guests defaults to 1, integer ≥ 1; on a value below 1 the form shows `จำนวนผู้เข้าพักต้องมากกว่า 0` (validation catalog `capacity`). (proves AC-1, EC-10)
- BR-2 Capacity is enforced server-side ONLY, inside CAM-302's serializable transaction (`checkDateAvailabilityInTx`, ADR-006) — never re-computed in the UI (ADR-009, no parallel availability math). The UI submits and, on a 409, surfaces the server's verbatim Thai `ช่วงวันที่นี้ถูกกันไว้แล้ว` inline; the form stays open so the host can adjust the dates or guests. (proves AC-1, EC-1)
- BR-3 Expiry = creation time + 48 hours by default (the CAM-302 schema default, applied when the host keeps the default preset and the UI sends no explicit expiry). The host may extend it with bounded presets `48 ชั่วโมง` / `3 วัน` / `7 วัน` / `14 วัน` (computed as now + preset, always ≤ 14 days), so a create never trips the server's range check. If the server ever rejects an out-of-range expiry it returns `กำหนดหมดอายุต้องอยู่ระหว่างตอนนี้ถึง 14 วันข้างหน้า` verbatim (defensive, CAM-302-owned copy). Each live hold row shows `หมดอายุ {datetime}`. (proves AC-1, AC-3, EC-2)
- BR-4 The live-holds list shows ONLY holds where status = ACTIVE AND expiresAt > now — the exact predicate `getActiveHoldsForRange` uses (`lib/campsite-availability.ts`). Expired-by-time holds (still status ACTIVE, past their expiry — the ADR-012 §4 lazy-expiry "zombie" row) and RELEASED / CONVERTED holds are NOT listed. This keeps the list byte-consistent with the availability math: everything shown is currently reserving capacity, and nothing shown reserves nothing. No cron ever flips a row. FILTERING ON `status` ALONE IS WRONG — it would list dead holds and misrepresent availability (the CAM-342 trace trap: `status === 'ACTIVE'` is not "active"; it must AND the timestamp). (proves AC-3, EC-3, EC-4)
- BR-5 A live hold row shows: scope (`ทั้งลาน` for whole-camp, or the spot name resolved from the page's spots list — the holds read returns `spotId` only, no spot relation), guests `{n} คน`, the date range, and `หมดอายุ {datetime}`. The host's private `note` is host-internal and may be shown to the host but is never rendered on any camper-facing surface (feature No-go). (proves AC-1, AC-3)
- BR-6 Release requires a confirmation step via the existing `ConfirmDialog` primitive (`ปล่อยการกันที่นี้ใช่หรือไม่` / `เมื่อปล่อยแล้ว วันที่ที่กันไว้จะกลับมาว่างให้จองทันที`), mirroring the blocked-dates delete pattern. Rationale for the confirm: a release instantly reopens inventory the host was protecting mid-negotiation, so an accidental tap could let the spot be booked out from under a live deal. On confirm, status → RELEASED (append-only, never deleted); it stops counting immediately. (proves AC-4)
- BR-7 After any create or release, the holds list AND the month calendar both re-fetch from their live sources so remaining capacity reflects the change at once — the calendar's `เหลือ {n} ที่` drops on create and rises on release. No optimistic update: refetch, matching the blocked-dates precedent. (proves AC-2, AC-5)
- BR-8 Release is an atomic compare-and-swap scoped to `{id, campSiteId, status ACTIVE}` (CAM-302). A hold that another actor already released, or one that never existed / belongs to another camp, returns 404 and the UI shows `ไม่พบการกันที่นี้ (อาจถูกปล่อยไปแล้ว)`. A hold that merely expired-by-time is still status ACTIVE, so releasing it still succeeds harmlessly (it was already inert). (proves EC-5, EC-8)
- BR-9 Every hold read / create / release is authorized server-side by CAM-302's `requireCampSitePermission(campSiteId, 'BOOKING_UPDATE')` (camp owner, platform admin, or a team member with BOOKING_UPDATE). A user without it sees the page's forbidden state and no create / release control; the UI never substitutes for the server check. Spot ownership is enforced server-side — a spotId that does not belong to this camp returns 404. (proves AC-8, EC-6, EC-9)
- BR-10 Copy: all hold copy lives in `locales/` (TH/EN), never hardcoded; no em-dash separators, no technical jargon. Error copy the CAM-302 API already owns is surfaced verbatim, not re-worded: `ช่วงวันที่นี้ถูกกันไว้แล้ว` (409), `กำหนดหมดอายุต้องอยู่ระหว่างตอนนี้ถึง 14 วันข้างหน้า` (400 expiry range). Reused validation-catalog copy: guests `จำนวนผู้เข้าพักต้องมากกว่า 0`, date range `วันเช็คเอาท์ต้องหลังวันเช็คอิน`. Action failures show `กันที่ไม่สำเร็จ กรุณาลองอีกครั้ง` / `ปล่อยการกันที่ไม่สำเร็จ กรุณาลองอีกครั้ง`; a load failure shows `โหลดรายการกันที่ไม่สำเร็จ`. (proves AC-9, AC-10, EC-1, EC-7)

## Edge cases
<!-- cover: invalid · empty/zero · concurrent/duplicate · permission · boundary. -->
- EC-1 IF the requested hold would exceed remaining capacity on any night (from bookings and/or overlapping active holds) THEN the server rejects with 409 and the form shows `ช่วงวันที่นี้ถูกกันไว้แล้ว` inline; no row is written and the form stays open (BR-2)
- EC-2 IF the check-out is on or before the check-in, OR an expiry lands not-in-the-future or more than 14 days ahead THEN the create is rejected: the range fails the shared client pre-check with `วันเช็คเอาท์ต้องหลังวันเช็คอิน`, and an out-of-range expiry (defensively, since presets are bounded) returns the server's `กำหนดหมดอายุต้องอยู่ระหว่างตอนนี้ถึง 14 วันข้างหน้า`; nothing is written (BR-3, BR-10)
- EC-3 IF a hold's expiry has passed while its status is still ACTIVE (the ADR-012 §4 lazy-expiry "zombie" row, no cron flips it) THEN it is treated as expired: excluded from the list and from the availability math, and it never gets a release control (BR-4)
- EC-4 IF a hold has status RELEASED or CONVERTED THEN it is not shown in the live-holds list — there is no history view in this story; the list is live holds only (BR-4)
- EC-5 IF the host confirms release on a hold that expired-by-time after the list rendered (still status ACTIVE in storage) THEN the release still succeeds, the row leaves the list, and no error is shown — releasing an already-inert hold is harmless (BR-8)
- EC-6 IF a user without booking-management permission for the camp requests the hold list / create / release THEN the server refuses (permission required) and the UI shows the forbidden state; no hold data is exposed and no write occurs (BR-9)
- EC-7 IF the hold list, create, or release request fails or times out THEN the relevant surface shows its failure copy (`โหลดรายการกันที่ไม่สำเร็จ` + a `ลองอีกครั้ง` retry for the list; `กันที่ไม่สำเร็จ กรุณาลองอีกครั้ง` / `ปล่อยการกันที่ไม่สำเร็จ กรุณาลองอีกครั้ง` for the actions) and no partial state is shown (BR-7, BR-10)
- EC-8 IF the same hold is released twice at once (two tabs / two actors) THEN the first release wins (status → RELEASED) and the second returns 404 `ไม่พบการกันที่นี้ (อาจถูกปล่อยไปแล้ว)`; after refresh the row is gone either way (BR-8)
- EC-9 IF a create request names a spot that does not belong to this camp (tampered request) THEN the server rejects with 404 and no hold is written; the UI only ever offers this camp's own spots (BR-1, BR-9)
- EC-10 IF the camp has no defined spots THEN the spot selector is hidden and the hold applies to the whole camp (no spot), mirroring the blocked-dates form (BR-1)

## Data
- Read / write through the EXISTING CAM-302 API only — no new endpoint, no schema change, no migration.
  - Create: `POST /api/campsites/[id]/holds` — body `{ spotId?: uuid|null, startDate, endDate (EXCLUSIVE checkout day), guests: int≥1 (default 1), note?: string|null, expiresAt?: date }`. Responses: `201 { hold }`; `400` validation (endDate must be after startDate; expiry must be future and ≤ 14 days → `กำหนดหมดอายุต้องอยู่ระหว่างตอนนี้ถึง 14 วันข้างหน้า`); `404` spot-not-found; `409` capacity/overlap → `ช่วงวันที่นี้ถูกกันไว้แล้ว`; `401/403` authz.
  - List: `GET /api/campsites/[id]/holds` — returns ALL InternalHold rows for the camp (every status), ordered by startDate ascending. Each row = `{ id, campSiteId, spotId, startDate, endDate, guests, note, status, expiresAt, createdById, createdAt, updatedAt }`. The client filters to live (status ACTIVE AND expiresAt > now) and resolves spot names from the page's spots list — the read returns `spotId` only, no spot relation.
  - Release: `DELETE /api/campsites/[id]/holds/[holdId]` — status ACTIVE → RELEASED; `404` if not found / not this camp / already released; success `{ success: true }`.
  - `InternalHold.status` enum = `ACTIVE | RELEASED | CONVERTED` — there is NO `EXPIRED` state; expiry is lazy read-time only (ADR-012 §4). `guests` sums into availability exactly like `Booking.guests`; `endDate` is the EXCLUSIVE checkout day (identical to Booking).
- migration: none.

## Out of scope
- Editing an existing hold in place (change dates / guests / expiry) — the CAM-302 API has no PATCH; a hold is released and re-created instead → follow-up if the owner wants in-place edit (a new API contract → architect first, do not spec it here).
- Any camper / guest-facing hold surface — holds are host-internal; the feature No-go forbids disclosing a hold's existence to campers (CAM-344 BR-8 already folds a hold into an anonymous "unavailable" signal) → not applicable.
- Converting a hold into a ManualStay Booking (status CONVERTED) — belongs to the HostOS lead → quote → ManualStay funnel → CAM-311 + the ManualStay story (ADR-012 §6).
- A history view of expired / released holds — the list is live holds only; a "past holds" log is a follow-up if hosts ask.
- An explicit "held {n}" number per day on the month calendar — the calendar reflects holds only through the existing `เหลือ {n} ที่` remaining drop; a dedicated held count is a calendar-enhancement follow-up.
- A cron / scheduled job to flip expired holds to a terminal status — deliberately excluded (ADR-012 §4 lazy expiry; feature No-go).
- Refining the 409 copy to distinguish "capacity full" from "overlapping hold" — the message is CAM-302 API-owned → a copy refinement is a CAM-302 follow-up, not this UI story.
