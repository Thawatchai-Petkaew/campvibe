# Portability manifest — copying the self-hosted delivery ticket system to a new project

> Written in CAM-282 (T-6, the conventions-rewrite story that closes out the "Self-hosted Delivery
> Tickets" epic, CAM-276). Read `docs/adr/ADR-010-self-hosted-delivery-tickets.md` first — this file
> is the practical "how do I actually duplicate this into repo #2" checklist that ADR-010's
> Consequences section promised, not a re-explanation of the design.

## Why this exists

ADR-010 locked "strict separation from the product" as a G1 requirement specifically so this system
could be lifted into a brand-new project later with the least possible tax: copy two folders + a
handful of routes/libs, point one new env var at a fresh database, done — no filtering rows out of a
shared dump, no untangling from product migrations. This file is that checklist, verified against the
actual file tree (not guessed).

## 1. Files to copy

### Data layer (the module boundary — never import the product's `@prisma/client` from here, never import these from product code)

- `prisma/delivery/schema.prisma` — the whole schema (enums `TicketType`/`TicketState`/`DeliveryRole`/`Persona`, models `Ticket`/`TicketEvent`/`TicketComment`/`DeliveryPulse`).
- `prisma/delivery/migrations/` — the migration history (two migrations as of this writing). Copy it so the new project's first `prisma migrate deploy` doesn't have to regenerate from scratch against possibly-different Postgres defaults.
- `prisma/delivery/generated/` — **do not copy**; it's gitignored and regenerated by `npm run delivery:generate` (`postinstall` + `build` already run this).
- `lib/delivery/` (all 8 files): `client.ts` (lazy Prisma singleton) · `errors.ts` (`TicketNotFoundError`/`TicketTransitionError`) · `http.ts` (`ticketErrorResponse` — maps service errors to HTTP status) · `pulse.ts` (`DeliveryPulse` read/bump) · `roles.ts` (`DeliveryRole` ↔ slug) · `status-adapter.ts` (synthesizes the `StatusIssue` shape for `/status` — see caveat in §4) · `tickets.ts` (the one service module every mutation goes through) · `validations.ts` (zod schemas).

### API surface

- `app/api/tickets/route.ts` (GET list, POST create)
- `app/api/tickets/[id]/route.ts` (GET detail, PATCH — the 9-verb + 2-toggle + `updateFields` dispatch)
- `app/api/tickets/[id]/comments/route.ts` (POST comment)

### Dashboard (only if you also want the visual `/status` board — optional, the ticket system works headless via `ticket-sync.mjs` alone)

- `app/status/*` — `page.tsx`, `dashboard-client.tsx`, `dashboard-assets.ts`. The `app/status/map/*` animated 3D board is a separate, much larger, CampVibe-specific visual layer (campsite theme/sprites) — treat it as optional flavor, not part of the portable core.
- `app/api/status/*` — `approve/route.ts`, `reject/route.ts`, `issue/[id]/route.ts`, `pulse/route.ts` (legacy — see §4), `stream/route.ts` (SSE — see §4), `version/route.ts`.
- `app/api/telegram-webhook/route.ts` — the Approve/Reject tap handler + free-text comment routing.
- Supporting libs: `lib/status-auth.ts` (the shared `STATUS_TOKEN` gate — used by every route above), `lib/status-derive.ts` + `lib/status-model.ts` (board-lane/workload derivation the dashboard renders from a `StatusIssue[]`), `lib/notify.ts` + `lib/notify-messages.ts` (Telegram send + event copy), `lib/github-dispatch.ts` (`repository_dispatch` fire), `lib/rate-limit.ts` (in-process rate limiter these routes share).
- `lib/linear.ts` — **only the `StatusIssue` type + the `TICKETS_SOURCE` read-switch pattern are worth keeping** if you want an equivalent rollback lever; strip everything that actually calls the Linear API (`fetchStatusIssues`'s Linear branch) unless the new project also migrated off Linear.

### CLI + automation

- `scripts/ticket-sync.mjs` + `scripts/lib/ticket-sync-args.mjs` + `scripts/lib/ticket-sync-mapping.mjs` — the whole CLI, unmodified (it's already a pure HTTP client with zero product-specific code).
- `.github/workflows/linear-continue.yml` — rename the file/event type eventually (kept as `linear-gate-approved` in this repo only for backward-compat with the workflow trigger — see §3), but the mechanics (checkout → `ticket-sync gates` → headless `claude -p` → `ticket-sync notify`) are portable as-is.
- `.github/workflows/camper-adhoc.yml` — portable as-is (no Linear/ticket-specific env left after CAM-282/T-6).

### What NOT to copy

- `scripts/linear-sync.mjs`, `scripts/import-linear.mjs`, `scripts/parity-check.mjs` — one-time Linear-migration tooling for CampVibe's own cutover. A brand-new project starting fresh on this system has nothing to import.
- `docs/delivery/self-hosted-delivery-tickets/parity-report-2026-07-03.md` — CampVibe's own migration evidence, not a template.

## 2. Env vars needed

| Var | Required | Used by |
|---|---|---|
| `DELIVERY_DATABASE_URL` | yes | `lib/delivery/client.ts` — a **separate** Postgres database from the product's `DATABASE_URL` (own connection pool; provision it with its own connection limit) |
| `STATUS_TOKEN` | yes (every `/api/tickets/*` + `/api/status/*` + `/status*` route default-denies without it — `lib/status-auth.ts`) | shared gate token; in local dev (`NODE_ENV=development`) the gate is bypassed for convenience |
| `APP_BASE_URL` | yes (defaults to `https://campvibe-staging.vercel.app` if unset — **change this default for a new project**, or always set the var) | `scripts/ticket-sync.mjs`, `lib/notify-messages.ts`'s `statusUrl()` |
| `TELEGRAM_BOT_TOKEN` | only if using Telegram notify/approve | `lib/notify.ts`, `scripts/ticket-sync.mjs`'s `notify` command |
| `TELEGRAM_CHAT_ID` | only if using Telegram | same as above |
| `TELEGRAM_WEBHOOK_SECRET` | only if using the Telegram Approve/Reject tap | `app/api/telegram-webhook/route.ts` — verifies the `secret_token` Telegram sends |
| `GITHUB_REPO` (e.g. `"owner/repo"`) | only if using the headless-continuation workflow | `lib/github-dispatch.ts` |
| `GH_DISPATCH_TOKEN` | only if using the headless-continuation workflow | same as above — a fine-grained PAT scoped to `Contents: read & write` on that one repo |
| `ANTHROPIC_API_KEY` | only if you want the headless workflows to actually run Claude (unset = they log and stop, no autonomous action) | `.github/workflows/linear-continue.yml` + `camper-adhoc.yml` |
| `TICKET_SYNC_ACTOR` (optional) | no | `scripts/ticket-sync.mjs` — free-text actor string for the audit ledger when not passed via `--actor`; defaults to `"ticket-sync-cli"` |

None of these are `NEXT_PUBLIC_*` — every one is server-only (never shipped to the client bundle).

## 3. Setup steps (new project, from zero)

1. **Create the database.** A new Postgres database, separate from whatever the product app uses (same provider/workspace is fine, e.g. a second database under the same Prisma Postgres project — that's what CampVibe itself did).
2. **Set `DELIVERY_DATABASE_URL`** in every env you'll run in (local `.env`, Vercel Preview/Staging/Production — or your platform's equivalent), pointing at that new database.
3. **Migrate.** `npm run delivery:migrate` locally the first time (creates + applies the migration against a fresh dev database); `npm run delivery:generate` regenerates the Prisma client (already wired into `postinstall`/`build`/`vercel-build` in `package.json` — copy those script entries too, not just the schema file).
4. **Set `STATUS_TOKEN`** to a fresh random secret (never reuse CampVibe's).
5. **Set `APP_BASE_URL`** to the new project's real deployed URL (or change the hardcoded fallback default inside `scripts/ticket-sync.mjs` / `lib/notify-messages.ts` if you'd rather not always pass it).
6. **(Optional) Telegram.** Create a bot via @BotFather, set `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`/`TELEGRAM_WEBHOOK_SECRET`, then register the webhook once: `POST https://api.telegram.org/bot<TOKEN>/setWebhook` with `url=<APP_BASE_URL>/api/telegram-webhook` and `secret_token=<TELEGRAM_WEBHOOK_SECRET>` (see the header comment in `app/api/telegram-webhook/route.ts`).
7. **(Optional) GitHub headless continuation.** Create a fine-grained PAT scoped to the new repo (`Contents: read & write`), set `GITHUB_REPO`/`GH_DISPATCH_TOKEN` as repo secrets/vars, add `ANTHROPIC_API_KEY` as a repo secret if you want autonomous continuation (otherwise the workflows just log and stop — safe default).
8. **Create the first ticket** to confirm the wire-up: `node scripts/ticket-sync.mjs create --type epic --title "First epic" --feature "my-feature"`, then `node scripts/ticket-sync.mjs list`.

## 4. What to rename / re-check per project (honest gaps, not assumptions)

- **The `"CAM-"` identifier prefix is hardcoded, not configurable.** Verified in `lib/delivery/tickets.ts`'s `createTicket()`: `` const identifier = `CAM-${number}` ``. There is **no** `TICKET_TEAM_KEY`-style env var wired into the new system at all — `LINEAR_TEAM_KEY` only exists in the old/deprecated `scripts/linear-sync.mjs` and the one-time `scripts/import-linear.mjs`/`scripts/parity-check.mjs` migration tools (which read *from* Linear, not from this system). **To rename the prefix for a new project, edit that one literal in `lib/delivery/tickets.ts` directly** — do not assume an env var exists; none does as of this writing. If a second project is ever run from the *same* codebase (multi-project), ADR-010 §"Multi-project, noted but not built" already scopes the additive design (a nullable `projectKey` column + per-project sequence) — not built, because YAGNI with a single project today.
- **The SSE "live nudge" is not yet on the delivery pulse — a real, verified gap.** `app/api/status/stream/route.ts` reads `lib/status-pulse.ts`'s `readPulse()`, which is the **product** schema's `StatusPulse` model (`prisma/schema.prisma`, a different database from `DELIVERY_DATABASE_URL`) — not `lib/delivery/pulse.ts`'s `DeliveryPulse` that ticket mutations actually bump. The dashboard's own list-read freshness is still correct (`lib/delivery/status-adapter.ts`'s `unstable_cache` takes the delivery pulse value as an argument, which Next.js folds into the cache key, so a fresh read after a mutation is never stale) — but a `/status` tab left open in a browser will not auto-refresh the instant a new-style ticket mutation happens, only on its own next poll/reload. A new project that wants true real-time push must either rewire `stream/route.ts` to `readDeliveryPulse()` or bring the legacy `StatusPulse` model + `/api/status/pulse` route along too (and remember to bump it — nothing does automatically anymore, since the Linear webhook that used to is retired). Not fixed here; flagged honestly instead of asserted as working.
- **`STATUS_TOKEN` is one flat shared secret**, not per-user/per-role. Fine for a solo-owner or small-team internal tool (CampVibe's own trust model, see `lib/status-auth.ts`'s header comment); revisit if the new project needs per-person audit identity beyond the free-text `actor` string already on every `TicketEvent`.
- **`actor`/`assigneeName`/`authorName` are free-text `String`, not a foreign key to a real user table** (ADR-010 open trade-off #3, deliberately deferred — "proportionate for a solo-owner, AI-role-driven pipeline"). If the new project has multiple real human approvers who need durable identity, that's a genuine design upgrade to make there, not a copy-paste concern.
- **`legacyUrl`/`legacyLabels` columns exist for CampVibe's own Linear-import safety net** (T-4). A brand-new project with no prior tracker has nothing to import — these columns stay in the schema (harmless, always-null) unless you want to trim them; no code path requires removing them.

## 5. Single-project caveat (today) + multi-project future note

This system, as built, assumes **one project** (`CAM`) and **one global numeric sequence** for `Ticket.number`/`identifier` (see ADR-010 "Separate schema + database (portability)"). Duplicating `lib/delivery/` + `prisma/delivery/` into a second repo (the scenario this file is written for) is the supported path today — each repo gets its own database, its own sequence, its own prefix (after the one hardcoded-string edit in §4).

Running **two projects inside the *same* codebase/database** is explicitly not built (see ADR-010 §Alternatives + §Open trade-offs #4's sibling note): the additive path, when a second project becomes real, is a nullable `projectKey String?` column (backfilled `"CAM"` for every existing row) plus a per-project sequence, with `identifier` kept as "the globally displayed key" so nothing downstream (`lib/status-model.ts`/`lib/status-derive.ts`) has to change. Track this as a future ADR when a second concurrent project actually exists — not speculative work now (Lean, `CLAUDE.md` #6).
